# v0.1.0 行业报告编写数字员工规划

> **简要结论：** v0.1.0 将 AgentSeek Enterprise WeCom 从“企业对话与工具调用助手”
> 升级为“行业报告编写数字员工”。它面向公司战略发展部，围绕持久任务、可信证据、
> 人工审批、报告交付和全程审计完成证券行业及公司专题报告。

## 规划状态

本文是 v0.1.0 的讨论稿，不代表已经冻结的实现合同。

标记规则：

- **已确定**：由 v0.0.9 GA 能力或当前产品方向直接支持。
- **建议**：本规划推荐的 v0.1.0 方案。
- **待确认**：需要产品负责人逐项决定。
- **后续版本**：不进入 v0.1.0 的范围。

## 产品定位

### 服务部门

首个数字员工服务于公司战略发展部。

它承担的核心职责是：

- 编写证券行业发展报告；
- 编写公司发展、经营或专项分析报告；
- 整理内部材料、业务数据和外部公开资料；
- 建立论点、证据、数据和来源之间的可追溯关系；
- 根据评审意见修改报告；
- 形成可审阅、可交付、可归档的报告产物。

### 不是个人研究助手

数字员工不以“帮助某个用户自由搜索和写作”为中心。

它以组织交付为中心：

```text
岗位职责
-> 接收正式任务
-> 明确报告合同
-> 按标准作业流程执行
-> 使用授权数据和工具
-> 记录来源和执行证据
-> 在关键节点等待评审
-> 交付正式报告
-> 留下可审计的任务档案
```

个人 Agent 可以在一次对话中尽力回答。行业报告数字员工必须证明：

- 谁委派了任务；
- 报告服务什么决策；
- 使用了哪些材料；
- 关键结论由哪些证据支持；
- 哪些内容由谁审核；
- 交付的是哪个版本；
- 任务是否满足验收条件。

## 报告场景

### 场景 A：证券行业发展报告

典型任务包括：

- 证券行业年度或季度发展综述；
- 行业政策与监管变化分析；
- 券商数字化转型趋势报告；
- 行业竞争格局与标杆机构分析；
- AI、数据治理、财富管理等专题研究；
- 面向管理层的行业趋势简报。

主要材料来自：

- 公司授权的证券行业数据 MCP；
- 监管机构和行业协会公开材料；
- 上市公司公告、年报和正式披露；
- 战略发展部提供的内部材料；
- 员工上传的 PDF、DOCX、XLSX 和 PPTX；
- 经允许使用的外部检索结果。

### 场景 B：公司专题报告

典型任务包括：

- 公司战略规划专题材料；
- 公司经营发展分析；
- 部门年度总结或专项汇报；
- 数字化建设、数据架构和 AI 应用专题报告；
- 内外部材料对比分析；
- 管理层会议所需的研究底稿。

公司报告可能包含内部数据。系统必须比公开行业报告采用更严格的数据边界。

## 组织角色

v0.1.0 采用简化的三主体模型：

| 主体 | 所属部门 | 责任 |
| --- | --- | --- |
| 业务负责人 `requester` | 战略发展部 | 委派任务，同时承担业务评审、最终批准、数据所有者和报告接收责任。 |
| 行业报告数字员工 `digital_worker` | 战略发展部数字岗位 | 执行研究、分析、写作、检查和版本整理。 |
| Agent 运维 `operator` | 信息技术部 | 管理运行状态、任务故障、策略、审计和人工恢复。 |

v0.1.0 固定以下角色映射：

```text
reviewer    = requester
approver    = requester
data_owner  = requester
beneficiary = requester
```

系统仍分别保存这些角色字段，确保评审、批准、数据授权和交付事件可审计。
它们在 v0.1.0 必须解析为同一个战略发展部员工，不能由模型自行改成其他人员。

信息技术部 Agent 运维默认只查看任务元数据、状态、错误和脱敏日志。
运维不因管理员身份自动获得报告正文和业务数据访问权。需要内容级排障时，
应由委派人显式授权，并记录一次有时效的人工接管事件。

v0.1.0 只覆盖战略发展部有权使用的数据。跨部门材料仍需原数据所属部门授权，
不把战略发展部委派人自动视为其他部门的数据所有者。

## DigitalEmployeePack 复用模型

### 为什么需要角色包

`deepagents/enterprise-wecom` 应保持通用企业数字员工 runtime 模板。

行业报告数字员工只是运行在该底座上的第一个岗位实例。未来的智能办公数字员工
应复用相同插件和 Work Runtime，只替换岗位职责、技能、流程、工具授权和资产。

因此建议新增逻辑概念：

```text
DigitalEmployeePack
- profile
- skills
- playbooks
- tool grants
- assets
- policies
- evals
```

DigitalEmployeePack 是项目内的纵向角色包，不是新的 Bub 插件。

通用能力继续由 contrib 插件提供：

```text
agentseek-enterprise
agentseek-work
agentseek-files
agentseek-wecom
agentseek-langchain
agentseek-contextseek
agentseek-schedule-sqlalchemy
```

### 角色包目录建议

行业报告角色包：

```text
digital_employees/industry-report/
  profile.yaml
  skills/
    report-intake/
    source-and-evidence/
    industry-research/
    report-writing/
    report-review/
  playbooks/
    securities-industry-report/
  assets/
    report-template.docx
  policies/
  evals/
```

智能办公角色包：

```text
digital_employees/smart-office/
  profile.yaml
  skills/
    meeting-coordination/
    travel-request/
    schedule-management/
    office-document-writing/
    internal-knowledge/
  playbooks/
    multi-party-meeting/
    travel-application/
    document-approval/
  assets/
  policies/
  evals/
```

`smart-office` 在本文中是未来角色包的结构示例，不随 v0.1.0 发布。
后续优先作为 `deepagents/enterprise-wecom` cookiecutter 中的第一方可选 pack，
生成新项目时只复制选中的 pack。首版不拆独立仓库，也不把两个 pack 同时装入运行项目。

角色包可以由 template 复制进生成项目，也可以由生成项目自行维护。
它不改变 AgentSeek core，也不要求 `agentseek-work` 理解具体办公或报告术语。

角色包的所有权继续分层：

- `agentseek-work` 保存 Profile、pack id/version、引用和 digest；
- enterprise-wecom template 解析角色包 manifest，并只装载当前 Profile 的 Skills 和 Playbooks；
- `agentseek-files` 或可信资产目录保存 DOCX 等二进制 assets；
- 具体工具仍由 contrib 插件和 MCP 提供。

`agentseek-work` 不读取 Skill 正文，也不执行模板专属 Playbook 实现。

### 最小 Pack manifest

每个角色包使用 `pack.yaml` 作为唯一发现入口：

```yaml
schema_version: 1
pack_id: industry-report
pack_version: 1.0.0
profile: profile.yaml
skills:
  - id: report-writing
    version: 1.0.0
    path: skills/report-writing/SKILL.md
    sha256: <content-sha256>
playbooks:
  - id: securities-industry-report
    version: 1.0.0
    entrypoint: enterprise_wecom_digital_employee.reports.playbook:build_playbook
assets:
  - id: strategic-report-docx
    version: 1.0.0
    artifact_ref: trusted-asset://strategic-report-docx/1.0.0
    sha256: <content-sha256>
policies:
  - policies/report-policy.yaml
evals:
  manifest: evals/manifest.yaml
```

`profile.yaml` 只能引用 manifest 中声明的 skill、playbook 和 asset id。

enterprise-wecom template 的 `pack_loader.py` 负责：

- 从配置的单一 pack root 读取 `pack.yaml`；
- 校验 `schema_version`、必填字段和重复 id；
- 拒绝绝对路径、`..`、隐藏路径和 symlink 逃逸；
- 校验 Skill、policy 和 asset digest；
- 校验 playbook entrypoint 属于生成项目允许的 package；
- 只把当前 Profile 引用的 Skills 复制到虚拟 `/skills`；
- 生成不可变 `LoadedPackManifest` 供 agent 和 WorkItem 使用。

loader 不扫描并自动启用目录中的所有 pack，也不执行 manifest 外的任意 Python 路径。

### 可复用与可替换部分

智能办公数字员工直接复用：

- 企业微信 channel 和主动消息；
- 员工身份、组织上下文和隔离 scope；
- DigitalEmployeeProfile 和 channel binding；
- WorkItem、WorkEvent、审批、恢复、预算和 outbox；
- 文件接收、解析、分析和 artifact；
- MCP policy、audit 和 egress；
- 短期、显式长期和语义记忆；
- scheduler、TaskSandbox 和 Agent 运维；
- Langfuse 与本地事件。

智能办公角色包只替换：

- Profile 的岗位职责；
- `skill_refs`；
- `supported_playbooks`；
- `tool_grants` 和 `data_scopes`；
- 办公资产和模板；
- 场景测试与质量指标。

### Skill、Playbook、Tool、Policy 和 WorkItem 的边界

| 层 | 回答的问题 | 示例 |
| --- | --- | --- |
| Skill | 应该怎样完成这类工作？ | 报告结构、会议协调方法、引用规范。 |
| Playbook | 这项正式任务必须按什么阶段执行？ | 材料盘点、提纲评审、终稿批准。 |
| Tool | 实际执行什么读取、生成或业务动作？ | 查询数据、预订会议室、生成 DOCX。 |
| Policy | 当前主体是否允许执行？ | MCP allowlist、egress、数据范围。 |
| WorkItem | 任务进行到哪里，结果和责任是什么？ | 状态、attempt、审批和 artifact。 |

简化表达：

```text
Skill    = 方法
Playbook = 流程
Tool     = 动作
Policy   = 强制边界
WorkItem = 持久状态与证据
```

Skills 不能替代以下确定性能力：

- 身份和授权；
- 状态转换；
- 审批；
- 数据 egress；
- 数据库事务和幂等；
- 文件隔离；
- outbox 和通知防重；
- 预算执行；
- 审计和恢复。

### 报告编写适合使用 Skills

报告 Skills 适合承载：

- 需求澄清清单；
- 行业报告结构；
- 管理层摘要写法；
- 来源权威等级；
- Evidence 和 Claim 编写规范；
- 图表和表格表达；
- 公司语言风格；
- 质量检查清单；
- 何时调用分析、检索和文档工具。

报告 Playbook 应确定性指定每个 phase 的必需 Skill：

```text
需求受理       -> report-intake
资料与证据     -> source-and-evidence
行业研究       -> industry-research
初稿编写       -> report-writing
质量与修订     -> report-review
```

模型可以按 Skill 的说明继续读取 reference，但不能自行跳过 Playbook 要求的岗位规范。

### 智能办公适合使用 Skills

智能办公 Skills 可以承载：

- 会议协调所需字段与冲突处理方法；
- 出差申请材料清单；
- 日程和提醒表达规范；
- 内部知识查询方法；
- 邮件、通知、纪要和办公材料写作规范；
- MCP 工具选择和结果复述规则。

真正的会议预订、出差提交或流程修改仍由 MCP tool 执行，
并继续经过 tool grants、MCP policy 和确认流程。

Skill 被 Profile 引用不等于获得工具权限。

### Skill 的渐进式读取

DeepAgents 只把 Skill 名称和 description 放进初始上下文，完整内容按需读取。

`SKILL.md` 应保持简短，建议把详细规范拆到 `references/`：

```text
skills/report-writing/
  SKILL.md
  references/
    report-structure.md
    executive-summary.md
    citation-rules.md
    tables-and-charts.md
    company-style.md
    quality-checklist.md
```

当前文件工具默认读取行数有限。Skill 说明必须要求显式使用足够的 `limit`，
或通过短 `SKILL.md` 加按需 references 避免静默截断。

### Pack evals

每个角色包必须包含：

```text
evals/
  manifest.yaml
  cases/
    <case-id>.yaml
  fixtures/
```

`evals/manifest.yaml` 声明 eval schema version、case 列表和允许的 fixture root。

每个 case 至少包含：

```yaml
case_id: report-outline-basic
intent: 创建证券行业报告提纲
expected_route: WorkItem
required_skills: [report-intake, report-writing]
allowed_tools: [create_work, create_report_brief]
forbidden_tools: [deliver_report]
expected_states: [draft, waiting_review]
required_artifacts: [outline]
privacy_assertions: [no_secret, no_host_path, no_cross_employee_data]
```

测试分成两类：

- contract eval：manifest、路由、状态、工具、权限、artifact 和隐私，必须确定性通过；
- model eval：报告质量、引用、语言和修订效果，使用固定样本和评分标准。

fixtures 只能使用脱敏或合成材料，不能提交生产报告、员工数据或凭证。
industry-report pack 的核心 eval 在 M4 建立，在 M6 成为 RC/GA 验收的一部分。

### Skill 和角色包版本固定

DigitalEmployeeProfile 使用显式引用：

```text
skill_refs:
  - enterprise-employee@v1
  - workitem-interaction@v1
  - report-intake@v1
  - source-and-evidence@v1
  - report-writing@v1
  - report-review@v1
```

创建 WorkItem 时固定：

```text
pack_id
pack_version
skill_set_version
skill_digests
profile_version
playbook_version
runtime_release
```

每个模型 phase 的 WorkEvent 还应记录实际 `model_id` 和调用配置 digest。

进行中的任务不能因为部署更新而自动切换 Skill。新版本 Skill 应用于新任务；
旧任务迁移需要 Agent 运维执行显式、可审计操作。

为了让历史任务可复现，角色包版本必须保留不可变 tag、内容快照或可取回 artifact。
只保存 digest 而无法取回旧 Skill 内容，不足以完成复现。

启用角色包时创建内容寻址的 `PackSnapshot`：

```text
PackSnapshot
- pack_snapshot_id
- pack_id
- pack_version
- source_repository
- source_commit
- manifest_digest
- content_artifact_id
- asset_version_refs
- created_at
```

`content_artifact_id` 保存 manifest、Profile、Skills、policy、Playbook 配置和 eval manifest 的
不可变快照；二进制模板使用 immutable asset ref 和 hash。生成项目有 git 历史时同时保存 commit，
但 git commit 不是唯一取回机制。

WorkItem 增加 `pack_snapshot_id`。即使生成项目后来删除旧 pack，也能按受控 artifact 取回当时内容。

### 二进制模板不是 Skill

当前 `StaticAgentAssets` 只加载 UTF-8 文本。DOCX 等二进制模板不能放入 `/skills`。

正确关系是：

```text
report-writing Skill
-> 说明如何选择和使用模板

DigitalEmployeeProfile.asset_refs
-> 指向批准的模板 artifact

python-docx tool
-> 读取模板 artifact 并生成报告
```

模板资产必须记录 asset id、version 和 hash，并由只读可信资产目录或
`agentseek-files` 的受控 template/artifact storage 管理。

### DirectTurn 与 WorkItem

智能办公数字员工不应把每条消息都变成持久 WorkItem。

```text
DirectTurn
= 单轮、立即返回、没有异步等待、没有正式 artifact、无需跨 turn 恢复

WorkItem
= 多步骤、异步等待、人工评审、跨 turn 恢复或正式 artifact
```

DirectTurn 示例：

- 查询制度；
- 总结一个文件；
- 改写邮件；
- 翻译；
- 查询审批状态；
- 列出会议室。

WorkItem 示例：

- 完整行业报告；
- 多人会议协调；
- 跨天材料收集；
- 多文件合并分析；
- 需要审批的文档流程；
- 产生正式交付物的办公任务。

Skill 可以帮助理解意图，但是否创建 WorkItem 由 runtime 规则和 tool contract 决定，
不能完全交给模型自由选择。

满足任一条件必须创建 WorkItem：

- 产生或修改已登记的正式 artifact；
- 需要 `waiting_external`、`waiting_input`、`waiting_review` 或 `waiting_approval`；
- 跨多个 turn、多个系统或多个可恢复 phase；
- Playbook 或 tool contract 声明 `work_mode=required`；
- 委派人明确要求建立、跟踪或审计正式任务。

单次同步 MCP 写操作不必一律创建 WorkItem。只有 tool contract 声明
`work_mode=direct_allowed`，并且现有 confirmation、幂等和 MCP audit 全部生效时，
才允许在 DirectTurn 执行。其他写操作默认 `work_mode=required`。

工具合同至少声明：

```text
work_mode = required | optional | direct_allowed
side_effect = read | write | risky
supports_idempotency = true | false
```

### v0.1.0 的 Profile 装载范围

当前模板在 `agent.py` 中使用 `skills=["/skills"]`，而 StaticAgentAssets 会加载
项目 `skills/` 下所有文本文件。这适合一个项目只有一个岗位角色包。

如果把行业报告、智能办公和合同审核的全部 Skills 同时放入一个项目：

- 模型会看到不属于当前岗位的 Skill metadata；
- Skill 选择噪音增加；
- 岗位版本难以证明；
- prompt 不能成为隔离边界。

因此 v0.1.0 固定：

```text
一个生成项目
= 一个企微 Bot
= 一个 DigitalEmployeeProfile
= 一个启用的 DigitalEmployeePack
= 一组 profile-scoped Skills
```

以后根据同一模板生成智能办公数字员工时，创建独立项目实例和 Bot，
只携带 smart-office 角色包。

未来若需要一个 gateway 承载多个数字员工，必须增加：

- profile-scoped SkillResolver；
- 按 channel binding 选择的 agent/Runnable registry；
- 每次只暴露当前 Profile 的 `skill_refs`；
- Profile 独立的 tool grants、assets 和 evals；
- 多 Profile 隔离测试。

不能把所有岗位 Skills 统一暴露给同一个 agent 后，仅靠提示词要求它自行隔离。

## 报告任务合同

### 为什么需要任务合同

“帮我写一份证券行业报告”不足以启动正式任务。

数字员工需要将自然语言需求整理为可确认的报告合同。建议的数据结构是：

```text
ReportBrief
- title
- report_type
- decision_context
- target_audience
- scope
- key_questions
- time_range
- geographic_scope
- required_sources
- excluded_sources
- confidentiality_level
- expected_length
- output_formats
- due_at
- requester_id
- acceptance_criteria
- brief_version
```

其中 `decision_context` 很重要。相同资料面向董事会、战略发展部或技术团队，
结论结构和表达方式不同。

### 启动条件

建议只有满足以下条件后，任务才能从 `draft` 进入 `queued`：

- 报告主题明确；
- 目标受众明确；
- 研究范围和时间范围明确；
- 交付形式明确；
- 内部材料的数据权限明确；
- 委派人是已解析的战略发展部员工；
- 委派人确认报告合同。

## 企业任务运行模型

### WorkItem

v0.1.0 的中心实体应是持久化 `WorkItem`，而不是对话 session：

```text
WorkItem
- work_id
- tenant_id
- digital_employee_id
- pack_id
- pack_version
- pack_snapshot_id
- skill_set_version
- skill_digests
- runtime_release
- requester_id
- reviewer_id
- approver_id
- data_owner_id
- beneficiary_id
- playbook_id
- playbook_version
- brief
- status
- current_phase
- phase_attempt
- version
- priority
- input_file_ids
- source_ids
- artifact_ids
- approval_state
- budget_id
- external_task_id
- next_poll_at
- lease_owner
- lease_expires_at
- due_at
- idempotency_key
- created_at
- updated_at
```

对话用于创建、查询和推动任务。任务状态不依赖对话是否仍在上下文窗口中。

### 状态机

建议采用以下顶层状态：

```text
draft
-> queued
-> running
-> succeeded

running -> waiting_external -> queued
running -> waiting_input    -> queued
running -> waiting_review   -> queued
running -> waiting_approval -> queued

draft|queued|running|waiting_* -> cancelled
queued|running|waiting_external -> failed
```

状态含义：

| 状态 | 含义 |
| --- | --- |
| `draft` | 报告合同尚未确认。 |
| `queued` | 合同已确认，等待执行资源。 |
| `running` | 数字员工正在执行当前阶段。 |
| `waiting_external` | 已持久化外部任务标识，等待 MinerU、模型限流或远端服务完成；不占用 worker。 |
| `waiting_input` | 缺少资料、范围或业务判断。 |
| `waiting_review` | 提纲、初稿或修订稿等待业务评审。 |
| `waiting_approval` | 敏感数据、对外使用或高风险动作等待批准。 |
| `succeeded` | 最终产物通过验收并完成交付。 |
| `failed` | 系统或业务错误导致任务终止，允许人工处理。 |
| `cancelled` | 有权用户显式取消任务。 |

网关重启、模型超时和外部工具暂时不可用，都不应使 WorkItem 丢失。

### WorkEvent

每次状态变化都追加不可变事件：

```text
WorkEvent
- event_id
- work_id
- event_type
- actor_type
- actor_id
- phase
- payload_digest
- policy_decision
- occurred_at
```

`WorkItem` 保存当前状态，`WorkEvent` 保存发生过什么。

它们不能只存在于 Langfuse。Langfuse 服务模型与 agent 调试，业务任务事件服务审计和运营。

### 恢复真相源

`WorkItem` 当前状态和不可变 `WorkEvent` 是 phase 级唯一业务真相源。

LangGraph checkpoint 只保存同一 phase attempt 内的 step 级执行快照。
发生崩溃时按以下顺序恢复：

```text
读取 WorkItem.current_phase 和 version
-> 查找最后成功 WorkEvent
-> 校验 phase attempt、输出 digest 和幂等键
-> 只接续属于该 attempt 的 checkpoint
-> checkpoint 冲突、损坏或过期时丢弃并按业务账本恢复
```

checkpoint 不能推进 WorkItem 状态，不能覆盖批准版本，也不能作为 MCP 已完成的唯一证明。

### 模型与外部调用预算

每个 WorkItem 必须有默认预算，每个 phase 可以进一步收紧：

```text
WorkBudget
- max_model_calls
- max_input_tokens
- max_output_tokens
- max_external_queries
- max_phase_duration_seconds
- max_work_duration_seconds
- max_retry_count
```

每次调用前预留预算，调用结束后记录实际消耗。重试同样计入预算。

预算不足时停止启动新调用，转入：

```text
waiting_approval
reason=budget_extension_required
```

委派人可以增加预算、缩小 ReportBrief 或取消任务。模型不能自行扩大预算。

## 报告标准作业流程

### Playbook

首个 Playbook 建议命名为：

```text
securities_industry_report/v1
```

完整流程为：

```text
需求受理
-> 报告合同确认
-> 材料盘点
-> 研究计划
-> 资料检索与证据登记
-> 数据分析
-> 提纲评审
-> 初稿编写
-> 事实与数字校验
-> 合规和保密检查
-> 业务评审
-> 修订
-> 最终批准
-> 文件交付
-> 任务归档
```

### 阶段 1：需求受理

数字员工从企微消息、附件或正式任务入口接收需求。

它先判断：

- 请求是否属于岗位职责；
- 委派人是否有权使用相关内部资料；
- 信息是否足够形成 ReportBrief；
- 是否存在相同的在途任务。

不完整需求进入 `waiting_input`，而不是让模型自行补全关键业务条件。

### 阶段 2：材料盘点

数字员工登记每个输入材料：

- `file_id`；
- 来源；
- 所有者；
- 保密等级；
- 适用时间；
- 解析状态；
- 是否允许外发；
- 是否允许送入外部模型或外部解析服务。

v0.0.9 的 CurrentFiles 和完整文件分析能力继续作为输入基础。

### 阶段 3：研究计划

研究计划至少包含：

- 报告章节建议；
- 需要回答的关键问题；
- 每个问题的预期证据；
- 内部材料和外部材料的使用范围；
- 数据分析任务；
- 风险和未知项。

研究计划由数字员工生成，但进入正式研究前由委派人确认。

### 阶段 4：资料与证据

Research 不直接把搜索结果堆进报告。它先登记来源和证据。

```text
SourceRecord
- source_id
- work_id
- source_type
- title
- publisher
- published_at
- retrieved_at
- uri_digest
- file_id
- confidentiality_level
- authority_level
- allowed_uses
- content_hash
- snapshot_policy
- snapshot_status
- snapshot_artifact_id
- license_restriction
- retrieval_query
- retrieval_query_digest
- license_terms_ref
- excerpt_status
```

```text
EvidenceRecord
- evidence_id
- source_id
- locator
- excerpt
- structured_value
- unit
- period
- confidence
- extraction_method
```

来源优先级建议为：

```text
已批准的公司内部数据
-> 监管机构、交易所和行业协会正式资料
-> 上市公司正式披露
-> 公司授权行业数据库
-> 权威研究机构
-> 一般公开网页
```

低优先级来源不能在没有交叉验证时支撑关键结论。

#### 来源快照策略

v0.1.0 必须交付来源快照策略，但不能无条件复制所有来源全文。

| 来源类型 | 可复核记录 |
| --- | --- |
| 员工上传文件 | 原 `file_id` 作为快照。 |
| 监管机构、交易所和协会公开文件 | 保存原文件 artifact、发布时间和 hash。 |
| 许可归档的公开网页 | 保存 HTML 或 PDF 快照、retrieved_at 和 hash。 |
| 商业数据库 | 按许可保存 query、数据版本、时间、digest 和允许的结果片段。 |
| 企业 MCP | 保存请求摘要、数据日期、结果 digest 和 Evidence 片段。 |
| 禁止复制的来源 | 保存稳定 locator、hash、时间和许可说明，不保存全文。 |

商业数据库和其他受许可来源必须记录：

- 实际 retrieval query，敏感内容按权限加密保存，日志只写 digest；
- `retrieved_at` 和数据版本；
- `license_terms_ref`；
- result digest；
- 许可允许时保存 Evidence excerpt；
- 许可禁止摘录时写 `excerpt_status=prohibited`，不能为了必填字段复制受限内容。

快照前仍需执行保密和许可策略。`snapshot_status` 至少区分：

```text
stored | referenced | prohibited | failed
```

关键 Claim 的来源如果既无快照也无法稳定复核，必须在质量门中标为风险，不能静默通过。

### 阶段 5：论点与引用

报告中的关键主张应登记为 Claim：

```text
Claim
- claim_id
- work_id
- section_id
- statement
- claim_type
- evidence_ids
- verification_status
- reviewer_status
```

`verification_status` 至少包含：

```text
unverified | verified | conflicted | rejected
```

证据冲突单独记录：

```text
EvidenceConflict
- conflict_id
- work_id
- subject
- evidence_ids
- conflict_type
- status
- resolution
- resolved_by
- resolved_at
- selected_evidence_ids
```

未解决冲突的关键 Claim 不能进入最终批准版本。

建议至少对以下内容强制引用：

- 行业规模和增速；
- 市场份额和排名；
- 政策、法规和监管要求；
- 公司经营数字；
- 同业对比；
- 对未来趋势的关键判断。

事实、推断和建议必须在表达上区分。

### 阶段 6：提纲评审

提纲是 v0.1.0 的第一个强制人工评审点。

委派人以业务评审人身份可以：

- 通过；
- 退回修改；
- 调整章节；
- 增加或删除关键问题；
- 改变受众和篇幅；
- 终止任务。

提纲通过后形成版本，后续重大结构变化需要记录原因。

### 阶段 7：初稿编写

数字员工基于已登记证据生成初稿，而不是从无来源的模型记忆直接写作。

初稿至少包含：

- 标题和版本；
- 摘要；
- 正文章节；
- 图表或表格；
- 关键结论；
- 风险和不确定性；
- 来源和引用；
- 待确认问题。

### 阶段 8：质量检查

质量检查建议分成确定性检查和模型辅助检查。

确定性检查包括：

- 数字单位是否一致；
- 同一指标在不同章节是否冲突；
- 日期和报告期是否一致；
- 百分比和合计是否合理；
- 关键 Claim 是否有 Evidence；
- 引用是否能定位到来源；
- 内部材料是否违反输出范围；
- 是否包含宿主路径、token 或敏感配置。

模型辅助检查包括：

- 论证是否连贯；
- 是否遗漏反面证据；
- 推断是否超过证据；
- 摘要是否忠实于正文；
- 表达是否适合目标受众。

模型检查不能替代确定性规则和人工评审。

### 阶段 9：评审与修订

每条评审意见应结构化记录：

```text
ReviewComment
- comment_id
- work_id
- artifact_version
- section_id
- reviewer_id
- comment
- disposition
- resolution
- resolved_in_version
```

数字员工需要说明每条意见是“已采纳、部分采纳或未采纳”，并给出原因。

### 阶段 10：批准与交付

只有满足输出合同并获得所需批准，WorkItem 才能进入 `succeeded`。

建议 v0.1.0 交付：

- 最终 DOCX 报告；
- Markdown 中间稿；
- 来源清单；
- 关键 Claim-Evidence 对照表；
- 版本和审批记录；
- 可选 PDF 预览件。

交付文件必须登记为 `agentseek-files` outbound artifact，并关联 `work_id`。

## 权限、保密与外部服务

### 权限不能来自记忆

短期记忆、显式长期记忆和 pgvector 召回都不能证明权限。

权限判断必须来自：

- 企业身份；
- 数字员工岗位授权；
- 数据范围；
- Playbook 工具授权；
- 当前任务授权；
- 下游系统最终校验。

### 建议的保密等级

```text
public
internal
confidential
restricted
```

不同等级决定：

- 能否使用外部检索；
- 能否发送到外部 MinerU；
- 能否发送到外部大模型；
- 能否通过企微交付；
- 是否需要委派人以数据所有者身份确认；
- 产物保存和过期策略。

### 外部模型和解析器

v0.0.9 已验证 MinerU 文件解析，但 v0.1.0 需要增加任务级数据策略。

不能因为文件类型受支持，就默认允许内部材料离开公司边界。

建议每次外部调用都记录：

- `work_id`；
- 数据等级；
- provider；
- purpose；
- policy decision；
- 输入摘要或 digest；
- 输出 digest；
- 时间和执行结果。

### Egress 硬策略

记录外部调用不能代替事前阻断。任何数据离开本地边界前，必须调用确定性策略：

```text
check_data_egress(
  work_id,
  source_or_file_id,
  confidentiality_level,
  target_provider,
  purpose,
  requester_scope,
  digital_employee_data_scopes,
  provider_allowlist,
)
```

该检查适用于：

- 外部大模型；
- MinerU；
- Tavily 或其他外部检索；
- 外部 MCP；
- 主动消息；
- 文件交付。

策略拒绝时，数据不能序列化到请求体、日志或 trace。模型不能绕过或覆盖策略结果。

## 审批模型

当前 MCP 的同一员工确认适合即时工具调用。正式报告需要独立审批实体：

```text
ApprovalRequest
- approval_id
- work_id
- approval_type
- subject_version
- requested_by
- approver_id
- decision
- decision_reason
- expires_at
- decided_at
```

v0.1.0 设置三个审批或评审节点，均由委派人完成：

1. 报告合同确认；
2. 提纲评审；
3. 最终报告批准。

涉及 restricted 数据时，委派人需要以数据所有者身份再次确认具体数据和用途。
对外发布不进入 v0.1.0 的自动执行范围；数字员工只交付给委派人。

批准必须绑定具体版本。批准后内容发生实质变化，应重新批准。

### 实质变化规则

以下变化默认属于实质变化，必须重新批准：

- ReportBrief 范围、受众、时间范围或保密等级变化；
- 章节增加、删除或重排；
- 关键 Claim 增删或含义变化；
- 数据、比例、金额、排名或报告期变化；
- Evidence 被替换；
- 核心结论或建议变化。

错别字、标点、分页、样式和不改变含义的措辞属于非实质变化。
无法确定时按实质变化处理，并记录判定理由。

## 主动工作与企微交互

行业报告通常是长任务，不能依赖一次 WeCom stream 完成。

v0.1.0 需要支持：

- 创建任务后立即返回 `work_id`；
- 查询“我的报告任务”；
- 查询某个任务的进度和当前阻塞；
- 在等待输入时向委派人提问；
- 在等待评审时通知委派人；
- 任务失败时通知委派人和运维；
- 任务完成后发送结果或交付入口。

企业微信 AI Bot 不提供完整主动推送能力。建议 v0.1.0 接入自建应用主动消息，
并将通知抽象为 channel-independent `NotificationPort`。

如果主动消息无法在 v0.1.0 落地，任务状态仍必须持久化。员工可以通过查询命令恢复任务，
但这应视为降级模式，而不是目标体验。

自建应用主动消息是 M0 可行性门。M0 技术探针至少验证：

- 给委派人主动发送文本；
- 发送文件或安全下载入口；
- userid 和应用可见范围；
- access token 刷新；
- 防重复、失败重试和审计；
- 公司网络与公网出口。

如果探针失败，必须在 M0 明确选择推迟完整 GA，或把版本范围降级为“可创建、可查询、跨轮推进”。

### 企微评审意见 MVP

v0.1.0 为提纲和关键 Claim 分配稳定 `section_id`。显示顺序或章节号变化时，
`section_id` 保持不变。委派人使用可读稳定编号提交结构化意见：

```text
S03 核心能力：补充头部券商案例
C02 关键结论：重新核对数据来源
通过提纲
退回修改
批准最终版
```

系统将每条意见转换为 `ReviewComment`，绑定 artifact version、稳定 `section_id`
和当时的显示标题。不能只用会随修订重排的章节序号关联意见。

Word 批注导入涉及 OOXML comment 锚点和版本合并，不作为 v0.1.0 必须能力。

## 技术架构

### 遵循 AgentSeek 插件框架的原则

AgentSeek 是 template-first toolkit。运行时插件模型来自 Bub。

当前 contrib 包通过 Python entry point 注册到 `bub` 分组。例如：

```text
wecom      = agentseek_wecom.plugin:main
enterprise = agentseek_enterprise.plugin:main
files      = agentseek_files.plugin:main
langchain  = agentseek_langchain.plugin:main
contextseek = agentseek_contextseek.plugin:ContextSeekPlugin
schedule   = agentseek_schedule_sqlalchemy.plugin:ScheduleImpl
```

v0.1.0 继续遵守这个模型，不在 `src/agentseek` 增加行业报告业务逻辑。

设计遵守七条原则：

1. AgentSeek core 只负责项目生命周期和模板工具，不承载企业业务。
2. 通用横向能力进入独立 contrib 插件。
3. 证券行业报告等纵向业务留在 enterprise-wecom 模板。
4. Profile、Skills、Playbooks、assets 和 evals 组成角色包，不伪装成 runtime 插件。
5. 插件通过 Bub hook、state 和公开 Python protocol 协作。
6. 插件不读取其他插件的私有数据库、目录或内部对象。
7. 模板是 composition root，负责选择和连接插件与角色包。

`agentseek-enterprise` 当前已经证明这种边界可行。它通过 `load_state()` 注入员工身份、
短期记忆和 HMAC scope，不处理企微协议，也不实现业务 MCP。

`agentseek-files` 通过 `load_state()` 注入 CurrentFiles，不决定模型如何回答报告任务。

`agentseek-wecom` 通过 `provide_channels()` 提供企微 channel，不拥有员工记忆和报告状态。

v0.1.0 的 Work Runtime 应沿用同一模式。

### 新增一个通用 work 插件

建议 v0.1.0 新增一个 contrib 包，而不是继续膨胀 `agentseek-enterprise`：

```text
contrib/agentseek-work/
```

建议 entry point：

```toml
[project.entry-points."bub"]
work = "agentseek_work.plugin:main"
```

它承担所有企业任务都可能复用的能力：

- DigitalEmployeeProfile 和 channel binding；
- 岗位版本、启停状态、requester scope 和权限 digest；
- WorkItem 和 WorkEvent；
- 状态机和乐观并发控制；
- 幂等创建；
- lease、重试、超时和取消；
- waiting_input、waiting_review 和 waiting_approval；
- ApprovalRequest；
- artifact 关系；
- 持久 outbox；
- 当前任务 state 注入；
- 任务级授权校验；
- 任务事件和观测关联。

它不承担：

- 企微协议；
- 员工身份查询；
- 文件下载和 OCR；
- 证券行业研究方法；
- 报告章节和写作 prompt；
- 具体 MCP server 配置；
- DOCX 模板和公司品牌样式。

这样 `agentseek-work` 可以被未来的审计数字员工、客服工单数字员工或运维数字员工复用，
而不会带入证券行业报告专属概念。

### 为什么不把 WorkItem 直接放进 agent.py

`agent.py` 是模板应用的 LangChain composition root。它适合：

- 选择模型；
- 注册工具；
- 注入模型可见的上下文；
- 组合 DeepAgents state 和 runtime context；
- 加载行业报告 Playbook。

它不适合拥有 PostgreSQL schema、任务锁、重试和 outbox。

如果 WorkItem 只写在 `agent.py`：

- 换 channel 后无法复用；
- 异步 worker 必须依赖聊天进程；
- 数据迁移和事务边界会与 prompt 代码混合；
- 其他 enterprise 模板无法使用；
- 测试只能做大而慢的端到端测试。

因此任务运行能力进入 `agentseek-work`，报告业务继续留在模板。

### DigitalEmployeeProfile 在一轮消息中的位置

`employee_context` 和 `DigitalEmployeeProfile` 表示两个不同主体：

```text
employee_context
= 当前发消息的战略发展部员工
= requester / reviewer / approver / data_owner / beneficiary

DigitalEmployeeProfile
= 接收委派并执行工作的行业报告数字员工
= digital_worker
```

因此必须先解析人类员工，再解析数字员工，最后才能加载双方之间的 WorkItem：

```text
Human Employee Identity
-> Digital Employee Binding
-> DigitalEmployeeProfile
-> requester_scope authorization
-> Current WorkItem
```

#### 数字员工如何绑定到 channel

建议增加持久化绑定：

```text
DigitalEmployeeBinding
- tenant_id
- channel
- channel_binding_key
- digital_employee_id
- enabled
```

`channel_binding_key` 可以来自企微 bot/callback 的稳定标识，并使用 HMAC 或内部映射保存。

`agentseek-wecom` 只负责把稳定、非密钥的 binding 信息放入 Envelope context。
它不查询 DigitalEmployeeProfile，也不判断战略发展部权限。

v0.1.0 只有一个数字员工时，可以配置 default digital employee 作为兼容路径。
但 WorkItem 仍必须保存明确的 `digital_employee_id`，不能长期依赖“系统里只有一个”的假设。

#### Profile 的解析时机

`agentseek-work.build_prompt()` 看到完整聚合 state 后，按以下顺序执行：

```text
1. 读取 employee_context 和 enterprise runtime scope
2. 读取 Envelope 中的 channel binding
3. 解析 DigitalEmployeeBinding
4. 加载已启用的 DigitalEmployeeProfile
5. 检查 requester 是否满足 profile.requester_scope
6. 注入安全的 digital_employee_profile 摘要
7. 加载显式 work_id 或当前员工的 Current WorkItem
```

所以 DigitalEmployeeProfile 位于 `employee_context` 之后、`current_work` 之前。

#### Profile 的 state 形态

模型可见 state 只放岗位说明：

```text
digital_employee_profile
- digital_employee_id
- name
- owning_org
- job_role
- responsibilities
- pack_id
- pack_version
- supported_playbooks
- skill_refs
- asset_refs
- profile_version
```

私有状态记录解析结果：

```text
_digital_employee_status
- found | not_configured | disabled | requester_forbidden
- binding_digest
- permissions_digest
- skill_set_digest
```

完整 tool grants、data scopes 和策略规则不进入模型 prompt。
它们由 repository 和 tool adapter 在执行时读取并校验。

#### 没有 Profile 时的行为

如果没有绑定、岗位被停用或 requester 不在允许范围：

- 不创建或加载 WorkItem；
- 报告 tools 返回确定性的授权或配置错误；
- 不回退为一个拥有宽泛权限的通用 Agent；
- 写入脱敏诊断事件；
- 向员工返回可操作但不泄露内部配置的提示。

#### Profile 版本与任务复现

新任务使用当前启用的 Profile 版本，并在 WorkItem 保存：

```text
digital_employee_id
digital_employee_profile_version
digital_employee_permissions_digest
pack_id
pack_version
skill_set_version
skill_digests
```

岗位档案更新后，新任务使用新版本。进行中的任务继续使用创建时固定的版本，
除非 Agent 运维执行显式、可审计的迁移。

这样可以解释某份历史报告当时使用了哪套岗位职责、Playbook 和权限。

### Bub hook 链路

当前 AgentSeek/Bub 一轮消息的主要扩展点是：

```text
provide_channels
-> admit_message
-> load_state
-> build_prompt
-> run_model / run_model_stream
-> save_state
-> channel.send / stream_events
```

v0.1.0 不新增一套平行事件循环。它把任务能力放进这条 hook 链。

完整交互链路建议为：

```text
1. agentseek-wecom.provide_channels
   接收企微消息并构造统一 Envelope

2. agentseek-enterprise.admit_message
   保持同一员工 session 的 turn 顺序

3. 所有插件 load_state 聚合
   enterprise -> employee_context / short_term_memory
   files      -> current_files / current_files_context
   schedule   -> scheduler capability

4. agentseek-work.build_prompt
   在完整 employee_context 已可用后解析 DigitalEmployeeProfile
   校验 requester_scope
   再加载当前 WorkItem
   写入 digital_employee_profile / current_work / current_work_context
   不直接改写用户问题

5. agentseek-contextseek.build_prompt
   按企业员工 scope 召回语义历史

6. agentseek-langchain.run_model_stream
   把聚合后的 state 和 runtime context 交给 RunnableSpec

7. enterprise-wecom agent.py
   注入 EmployeeContext、DigitalEmployeeProfile、CurrentFiles、CurrentWork
   注册通用 work tools 和报告 Playbook tools

8. tools / playbook
   在 repository 事务中修改 WorkItem
   文件只通过 file_id 访问
   MCP 调用继续经过 policy/audit

9. save_state
   保存短期记忆、语义历史和 turn-work 关联

10. agentseek-wecom
    返回当前回复；长任务由 worker 继续执行
```

这里选择 `build_prompt` 加载 scoped WorkItem，而不是直接依赖 `load_state()` 的插件顺序。

原因是每个插件的 `load_state()` 独立运行，不能假设它已经看到另一个插件刚返回的 state。
当前 `agentseek-contextseek` 已采用相同策略：企业 scope 依赖完整身份 state，
所以在 `build_prompt()` 阶段完成 scoped enrichment。

`agentseek-work.build_prompt()` 同样只丰富 state，返回 `None`，不把业务文字硬拼到 prompt。
最终是否把 CurrentWork 暴露给模型，由 enterprise-wecom 模板决定。

该 hook 使用 `_work_enriched` turn guard，保证 Bub 或 LangChain 多次触发 prompt hook 时，
同一 turn 不重复查询、加锁或产生业务事件。

### State 是组合边界，不是业务数据库

插件之间通过有命名约定的 state key 组合：

```text
employee_context         # 员工身份，模型可见
digital_employee_profile # 数字员工安全岗位摘要，模型可见
current_files            # 当前文件记录，应用可见
current_files_context    # 有界文件上下文，模型可见
current_work             # 当前任务摘要，应用可见
current_work_context     # 有界任务上下文，模型可见
_langgraph_runtime_context
  enterprise             # HMAC tenant/user/session scope
  digital_employee       # 数字员工 id、岗位版本和授权 digest
  work                   # work_id、playbook 和任务权限摘要
```

State 中只放当前 turn 需要的摘要：

- `work_id`；
- 报告标题；
- 当前状态和阶段；
- 当前等待事项；
- 当前 artifact 版本；
- 允许的下一步操作；
- 绑定 file_id；
- 脱敏的审批摘要。

以下内容不能整体放进 state：

- 完整报告正文；
- 全部 WorkEvent；
- 全部 Evidence；
- 数据库连接或 repository 对象；
- 原始内部文件；
- 审批凭证和 secret。

完整数据始终从 PostgreSQL 和 `agentseek-files` 按授权读取。

### Runtime context 的组合

`agentseek-enterprise` 当前将非 PII 的 tenant、employee 和 session HMAC key 写入
`_langgraph_runtime_context["enterprise"]`。

`agentseek-work` 在 `build_prompt()` 阶段保留已有 mapping，先增加数字员工 context：

```text
_langgraph_runtime_context["digital_employee"] = {
  version,
  digital_employee_id,
  profile_version,
  permissions_digest
}
```

存在 Current WorkItem 时，再增加：

```text
_langgraph_runtime_context["work"] = {
  version,
  work_id,
  playbook_id,
  requester_key,
  permissions_digest
}
```

它不能覆盖 `enterprise`。

enterprise-wecom 模板把当前 `EnterpriseRuntimeContext` 扩展为组合 schema，
供 LangGraph tools 获取 enterprise、digital_employee 和可选 work 三个 scope。

创建任务前还没有 `work` context，但必须已经有 `digital_employee` context。
这样 `create_work` 才知道任务应归属于哪个数字员工。

这样工具不需要从模型参数接受 `requester_id` 或数据库 scope，避免模型伪造身份。

### 通用 work tools 与报告 tools 分离

`agentseek-work` 提供窄而通用的 runtime-aware tools：

```text
create_work
get_work
list_my_work
cancel_work
provide_work_input
approve_work_version
```

这些工具负责：

- 从 runtime 获取真实 tenant 和 requester；
- 执行授权；
- 校验状态转换；
- 使用 repository 事务；
- 追加 WorkEvent；
- 返回结构化结果。

工具不能相信模型传入的 `requester_id`、`tenant_id`、`reviewer_id` 或数据 scope。
这些值必须来自 enterprise/work runtime context，并由 repository 再次校验。

Agent 运维使用独立的 admin service/tool 集合：

```text
admin_view_work
admin_view_events
admin_retry_failed_phase
admin_requeue_work
admin_release_expired_lease
admin_mark_failed
admin_cancel_work
```

不提供任意 `force_transition(from_any_state, to_any_state)`。
所有运维动作必须符合有限修复转换、填写原因并追加 operator WorkEvent。
运维默认不能读取报告正文；内容级接管仍需委派人显式授权。

enterprise-wecom template 提供报告专属 tools：

```text
create_report_brief
confirm_report_brief
submit_report_outline
review_report_outline
request_report_revision
deliver_report
```

报告 tools 调用 `agentseek-work` 的 service API，不直接写数据库。

这种分层与当前文件分析一致：`agentseek-files` 提供通用 `analyze_file`，
enterprise-wecom 决定什么问题必须调用它。

### Playbook 通过模板注入

`agentseek-work` 不 import `enterprise_wecom_digital_employee.reports`。

它只定义协议：

```text
WorkPlaybook
- playbook_id
- version
- validate_brief()
- allowed_transitions()
- run_phase()
- validate_output()
```

enterprise-wecom 提供实现：

```text
securities_industry_report/v1
```

Work plugin 从模板配置的 registry import path 加载 Playbook。

这种模式与 `AGENTSEEK_LANGCHAIN_SPEC` 相同：通用插件定义加载合同，
生成项目提供实际 RunnableSpec 或 Playbook。

因此其他模板可以注册自己的 Playbook，而不修改通用 work 包。

### 交互 turn 与异步 worker 分离

企微 turn 只负责：

- 创建或查询任务；
- 收集缺失信息；
- 执行一次明确的评审或批准；
- 返回当前状态。

它不应在一个 stream 中持续运行完整行业研究。

`agentseek-work` 提供一个 lifecycle channel 或受管 worker：

```text
WorkRuntimeChannel.start()
-> claim queued WorkItem with lease
-> load registered Playbook
-> run one resumable phase
-> commit output and WorkEvent
-> transition or schedule next wakeup
-> write notification outbox
```

这沿用 `agentseek-schedule-sqlalchemy` 通过 `provide_channels()` 管理后台 scheduler 生命周期的做法。

worker 必须具备：

- PostgreSQL lease；
- lease 到期回收；
- 乐观版本号；
- phase 级 idempotency key；
- 有界重试；
- graceful shutdown；
- 单阶段提交；
- 从最后成功阶段恢复。

模型进程失败不能把 WorkItem 留在不可恢复的 `running`。

#### Mac mini 首版并发模型

首版默认一个 phase execution worker，优先验证事务和恢复正确性。

等待 MinerU、模型限流或远端异步任务时，worker 必须：

```text
保存 external_task_id 和 next_poll_at
-> WorkItem 转 waiting_external
-> 提交 WorkEvent
-> 释放 lease 和 worker slot
-> 由 scheduler 到期重新入队
```

因此一个慢文件不会让其他 queued WorkItem 饥饿。外部检索可以有限并发，
但并发数、速率和预算都由配置确定，不由模型决定。

### v0.0.9 文件能力承接

Work Runtime 显式承接以下已知行为：

- MinerU 慢任务进入 `waiting_external`，不在 worker 内持续等待；
- worker 主动轮询绑定 file_id，完成后自动继续材料盘点，不要求员工再次提问；
- Scheme C 后台结果变化后，重新计算依赖该文件的 Evidence 和 Claim；
- PPTX 图形化数值无法可靠提取时标为 `unverified`，要求委派人提供源数字；
- 单个文件失败不影响其他材料和其他 WorkItem；
- MinerU phase timeout 按异步任务设计，不等于企微 stream timeout。

### 调度插件只负责时间

`agentseek-schedule-sqlalchemy` 保持独立，不存储 WorkItem 内容。

它负责：

- 到期任务唤醒；
- retry_at；
- due_at 检查；
- 评审和输入等待提醒；
- outbox 重试。

实际任务状态仍在 PostgreSQL Work repository。

调度 job 只携带 `work_id` 和操作类型，不携带报告正文、员工姓名和文件路径。

### 文件插件只暴露 file_id 和 artifact

WorkItem 只保存：

```text
input_file_ids
artifact_ids
```

它不保存 `runtime/files/.../original` 的宿主路径。

报告 Playbook 通过 `agentseek-files` 的公开 service 读取：

- 文件元数据；
- 已提取文本；
- 完整分析结果；
- outbound artifact 登记。

`agentseek-files` 继续负责：

- 文件 scope；
- MIME 和扩展名；
- 解析状态；
- MinerU；
- 文件生命周期；
- artifact 物理位置。

`agentseek-work` 只负责“这个文件为什么属于这个任务”。

### MCP 仍是业务系统边界

报告 Playbook 查询行业数据时继续使用现有 MCP adapter。

调用链保持：

```text
Report Playbook
-> template MCP adapter
-> enterprise MCP policy
-> confirmation when required
-> remote MCP server
-> MCP audit
```

Work Runtime 不绕过 MCP policy，也不直接连接已有 MCP 背后的业务数据库。

每次调用额外关联：

- `work_id`；
- `phase`；
- `source_id`；
- Playbook version；
- WorkEvent id。

如果现有 MCP audit 暂时不能增加字段，v0.1.0 先在 WorkEvent 保存 MCP audit event id，
而不是复制或重写 policy 判定逻辑。

### Langfuse work_id 关联

`work_id` 使用脱敏 metadata 和可选 tag 贯穿 Langfuse，不假设 SDK 存在 `work_id` 顶层字段。

当前 SDK 的 `update_current_trace()` 支持 `version`、`metadata` 和 `tags`，
不支持 `release=` 或 `work_id=` 顶层参数。因此 v0.1.0 采用：

```text
metadata.work_id
metadata.phase
metadata.work_event_id
tags: ["work:<opaque-id>", "phase:<name>"]
```

Langfuse client 构造器可以携带 release，但当前 logfire/OTel runtime trace 路径
没有继承该 client 默认值，因而 runtime trace 顶层仍可能为 `release=None`。

M1 单独验证 `LANGFUSE_RELEASE`、OTel resource attributes、SDK `version`，
以及改为 client 创建 trace 的兼容性。不能使用 SDK 不接受的顶层参数。

`WorkItem.runtime_release` 是审计和复现的权威版本源。Langfuse release 只是辅助观测字段；
顶层缺失不能被解释为 WorkItem 没有固定运行版本。

### ContextSeek 不是报告证据库

`agentseek-contextseek` 继续负责员工历史对话的语义召回。

它可以帮助理解“继续上一份报告”之类的自然语言，但不能作为：

- WorkItem 状态源；
- 已批准报告版本；
- 权限证明；
- 行业数据来源；
- Claim 的正式 Evidence。

正式 Source、Evidence 和 Claim 进入 Work repository。

这保持了 v0.0.9 已验证的记忆分层原则。

### Channel 和主动通知解耦

`agentseek-work` 不 import `agentseek-wecom`。

Work Runtime 在同一事务中写入持久 notification outbox：

```text
WorkNotification
- notification_id
- work_id
- recipient_key
- event_type
- payload
- status
- attempts
- next_attempt_at
```

enterprise-wecom template 负责将 outbox dispatcher 连接到
`agentseek-wecom` 的自建应用主动消息 adapter。

如果未来增加飞书或 Web channel，只替换 notifier，不修改 WorkItem 和报告 Playbook。

发送成功后更新 outbox。重复发送使用稳定 notification id 防重。

建议依赖保持单向：

```text

  enterprise  <---------------- composition root
  work        <---------------- composition root
```

箭头表示模板依赖插件。`-X->` 表示禁止的依赖。

## 验收场景

### 验收 A：证券行业发展报告

输入：

- 一组公开行业 PDF；
- 一份行业数据 XLSX；
- 授权 MCP 数据；
- 明确的管理层报告需求。

期望：

- 创建唯一 `work_id`；
- 形成并确认 ReportBrief；
- 形成来源清单和研究计划；
- 提纲经人工评审；
- 报告中关键数字均可追溯；
- 断言、推断和建议表达清楚；
- 生成 DOCX 和证据清单；
- 最终批准后交付；
- 所有动作可按 `work_id` 审计。

### 验收 B：公司内部专题报告

输入：

- internal 或 confidential 文件；
- 公司经营数据；
- 内部报告模板；
- 已解析的战略发展部委派人；

期望：

- 非授权员工不能读取任务和文件；
- 外部工具调用遵守数据策略；
- restricted 数据不会发送到未批准 provider；
- 报告只交付给授权对象；
- 删除或过期策略按配置执行；
- Langfuse 和日志不出现报告正文或敏感数据。

### 验收 C：跨重启恢复

任务在研究、等待评审和文档生成阶段分别重启网关。

期望：

- WorkItem 状态不丢失；
- 已完成步骤不重复执行；
- MCP 写操作不重复；
- 已批准版本仍能准确识别；
- 任务从正确阶段恢复。

故障注入 harness 必须覆盖：

- phase 开始后 kill worker；
- MCP 已返回但 WorkEvent 尚未提交时 kill；
- artifact 已写入但状态尚未更新时 kill；
- lease 过期；
- checkpoint 损坏或属于旧 attempt；
- 通知已发送但 outbox 尚未确认；
- PostgreSQL 短暂断连；
- MinerU 长时间 pending。

断言业务动作、通知和最终 artifact 均不重复。

### 验收 D：证据冲突

两个来源对同一行业指标给出不同数字。

期望：

- 系统不静默选择任意一个数字；
- 记录来源、口径和报告期差异；
- 请求人工判断或在报告中解释差异；
- 最终 Claim 指向被采用的证据和选择理由。

### 验收 E：v0.0.9 GA 回滚

回滚目标是 `enterprise-wecom-v0.0.9-ga`。

回滚前停止 v0.1.0 worker 和 scheduler wakeup，防止旧网关与新 worker 并行。
新增 PostgreSQL 表保留但停用，不执行破坏性 schema downgrade。
v0.0.9 不注册 `agentseek-work`，也不读取新表。新 artifact 按保留策略清理。

回滚后重新执行 v0.0.9 的身份、记忆、pgvector、MCP、文件和健康检查。

## 风险与取舍

### 报告质量不能只靠更强模型

模型能力会影响表达质量，但企业报告的可靠性主要依赖：

- 清晰的任务合同；
- 有层级的来源；
- Claim-Evidence 绑定；
- 确定性数据检查；
- 版本化评审；
- 人工最终责任。

### 通用工作流会拖慢首个场景

v0.1.0 应先实现证券行业报告 Playbook，不先建设万能工作流平台。

模型、数据结构和执行接口应可扩展，但 UI 和配置器不必提前通用化。

### DOCX 是必要交付，不是附加功能

行业报告数字员工若只能在企微回复 Markdown，尚未形成完整岗位交付。

因此 v0.1.0 建议把受控 DOCX 生成和 outbound 登记列为必须交付。

v0.1.0 选择 `python-docx + 战略发展部批准的 Word 模板`：

- 无需开放通用 shell；
- 可复用模板样式、标题、表格、页眉和页脚；
- 便于在受控 Python 执行路径测试；
- 降低 Mac mini 对 LibreOffice 和 Pandoc 的运行依赖。

LibreOffice 或 Pandoc 只作为后续 PDF 转换、高保真渲染或复杂目录刷新的可选 adapter。

正式公司模板未就绪时，M0 必须取得战略发展部批准的临时中性模板，
不能由开发人员自行定义品牌和格式规范。

### v0.1.0 发布分段

接受按能力降低集成风险，但不把 v0.1.0 GA 降级为只有任务账本的技术版本：

```text
v0.1.0-alpha1  Profile、DigitalEmployeePack、WorkItem、WorkEvent、状态机和恢复
v0.1.0-alpha2  ReportBrief、材料、Source/Evidence/Claim 和研究
v0.1.0-beta1   提纲评审、初稿、质量门和 Markdown
v0.1.0-rc1     主动通知、DOCX、批准、交付和故障恢复
v0.1.0-ga      一个限定行业报告主题端到端通过
```

GA 只支持一个岗位、一个 Playbook、一个批准模板和当前简化角色模型。
管理 UI、多 Agent、Word 批注导入、多个模板和复杂图表后置。

### 自主性必须受责任边界约束

数字员工可以自主推进低风险研究步骤，但以下事项必须等待人：

- 改变报告范围；
- 使用超出任务授权的内部数据；
- 选择存在重大冲突的关键数字；
- 形成对公司有重大影响的战略结论；
- 对外发布；
- 覆盖已批准版本。

### 已确认的组织与审批决策

- 战略发展部员工可以作为报告任务委派人。
- 委派人同时是业务评审人、最终批准人、当前任务的数据所有者和交付对象。
- 行业报告数字员工负责执行，不拥有最终批准权。
- 信息技术部 Agent 运维负责运行保障，不默认读取报告正文和业务数据。
- v0.1.0 不自动对外发布报告，只向委派人交付。
