# v0.1.0 行业报告编写数字员工规划

> **简要结论：** v0.1.0 将 AgentSeek Enterprise WeCom 从“企业对话与工具调用助手”
> 升级为“行业报告编写数字员工”。它面向公司战略发展部，围绕持久任务、可信证据、
> 人工审批、报告交付和全程审计完成证券行业及公司专题报告。

## 规划状态

本文是 v0.1.0 的讨论稿，不代表已经冻结的实现合同。

标记规则：

- **已确定**：由 v0.0.9 GA 能力或当前产品方向直接支持。
- **建议**：本规划推荐的 v0.1.0 方案。
- **待确认**：需要产品负责人逐项决定。
- **后续版本**：不进入 v0.1.0 的范围。

## 产品定位

### 服务部门

首个数字员工服务于公司战略发展部。

它承担的核心职责是：

- 编写证券行业发展报告；
- 编写公司发展、经营或专项分析报告；
- 整理内部材料、业务数据和外部公开资料；
- 建立论点、证据、数据和来源之间的可追溯关系；
- 根据评审意见修改报告；
- 形成可审阅、可交付、可归档的报告产物。

### 不是个人研究助手

数字员工不以“帮助某个用户自由搜索和写作”为中心。

它以组织交付为中心：

```text
岗位职责
-> 接收正式任务
-> 明确报告合同
-> 按标准作业流程执行
-> 使用授权数据和工具
-> 记录来源和执行证据
-> 在关键节点等待评审
-> 交付正式报告
-> 留下可审计的任务档案
```

个人 Agent 可以在一次对话中尽力回答。行业报告数字员工必须证明：

- 谁委派了任务；
- 报告服务什么决策；
- 使用了哪些材料；
- 关键结论由哪些证据支持；
- 哪些内容由谁审核；
- 交付的是哪个版本；
- 任务是否满足验收条件。

## 报告场景

### 场景 A：证券行业发展报告

典型任务包括：

- 证券行业年度或季度发展综述；
- 行业政策与监管变化分析；
- 券商数字化转型趋势报告；
- 行业竞争格局与标杆机构分析；
- AI、数据治理、财富管理等专题研究；
- 面向管理层的行业趋势简报。

主要材料来自：

- 公司授权的证券行业数据 MCP；
- 监管机构和行业协会公开材料；
- 上市公司公告、年报和正式披露；
- 战略发展部提供的内部材料；
- 员工上传的 PDF、DOCX、XLSX 和 PPTX；
- 经允许使用的外部检索结果。

### 场景 B：公司专题报告

典型任务包括：

- 公司战略规划专题材料；
- 公司经营发展分析；
- 部门年度总结或专项汇报；
- 数字化建设、数据架构和 AI 应用专题报告；
- 内外部材料对比分析；
- 管理层会议所需的研究底稿。

公司报告可能包含内部数据。系统必须比公开行业报告采用更严格的数据边界。

## 组织角色

v0.1.0 采用简化的三主体模型：

| 主体 | 所属部门 | 责任 |
| --- | --- | --- |
| 业务负责人 `requester` | 战略发展部 | 委派任务，同时承担业务评审、最终批准、数据所有者和报告接收责任。 |
| 行业报告数字员工 `digital_worker` | 战略发展部数字岗位 | 执行研究、分析、写作、检查和版本整理。 |
| Agent 运维 `operator` | 信息技术部 | 管理运行状态、任务故障、策略、审计和人工恢复。 |

v0.1.0 固定以下角色映射：

```text
reviewer    = requester
approver    = requester
data_owner  = requester
beneficiary = requester
```

系统仍分别保存这些角色字段，确保评审、批准、数据授权和交付事件可审计。
它们在 v0.1.0 必须解析为同一个战略发展部员工，不能由模型自行改成其他人员。

信息技术部 Agent 运维默认只查看任务元数据、状态、错误和脱敏日志。
运维不因管理员身份自动获得报告正文和业务数据访问权。需要内容级排障时，
应由委派人显式授权，并记录一次有时效的人工接管事件。

v0.1.0 只覆盖战略发展部有权使用的数据。跨部门材料仍需原数据所属部门授权，
不把战略发展部委派人自动视为其他部门的数据所有者。

## 数字员工岗位档案

### DigitalEmployeeProfile

建议新增数字员工岗位档案：

```text
DigitalEmployeeProfile
- digital_employee_id
- tenant_id
- name
- owning_org
- job_role
- responsibilities
- supported_playbooks
- tool_grants
- data_scopes
- requester_scope
- escalation_policy
- service_status
- profile_version
```

首个岗位档案建议为：

```text
name: 行业报告编写数字员工
owning_org: 战略发展部
job_role: 证券行业研究与报告编写
responsibilities:
  - 行业资料收集和证据整理
  - 行业趋势及竞争格局分析
  - 公司专题材料编写
  - 报告版本修改和质量检查
  - 研究底稿与引用归档
```

岗位档案不是模型可自由修改的 prompt。它由管理员配置和版本化。

## 报告任务合同

### 为什么需要任务合同

“帮我写一份证券行业报告”不足以启动正式任务。

数字员工需要将自然语言需求整理为可确认的报告合同。建议的数据结构是：

```text
ReportBrief
- title
- report_type
- decision_context
- target_audience
- scope
- key_questions
- time_range
- geographic_scope
- required_sources
- excluded_sources
- confidentiality_level
- expected_length
- output_formats
- due_at
- requester_id
- acceptance_criteria
- brief_version
```

其中 `decision_context` 很重要。相同资料面向董事会、战略发展部或技术团队，
结论结构和表达方式不同。

### 启动条件

建议只有满足以下条件后，任务才能从 `draft` 进入 `queued`：

- 报告主题明确；
- 目标受众明确；
- 研究范围和时间范围明确；
- 交付形式明确；
- 内部材料的数据权限明确；
- 委派人是已解析的战略发展部员工；
- 委派人确认报告合同。

## 企业任务运行模型

### WorkItem

v0.1.0 的中心实体应是持久化 `WorkItem`，而不是对话 session：

```text
WorkItem
- work_id
- tenant_id
- digital_employee_id
- requester_id
- reviewer_id
- approver_id
- data_owner_id
- beneficiary_id
- playbook_id
- playbook_version
- brief
- status
- current_phase
- priority
- input_file_ids
- source_ids
- artifact_ids
- approval_state
- due_at
- idempotency_key
- created_at
- updated_at
```

对话用于创建、查询和推动任务。任务状态不依赖对话是否仍在上下文窗口中。

### 状态机

建议采用以下顶层状态：

```text
draft
-> queued
-> running
-> waiting_input
-> waiting_review
-> waiting_approval
-> succeeded
-> failed
-> cancelled
```

状态含义：

| 状态 | 含义 |
| --- | --- |
| `draft` | 报告合同尚未确认。 |
| `queued` | 合同已确认，等待执行资源。 |
| `running` | 数字员工正在执行当前阶段。 |
| `waiting_input` | 缺少资料、范围或业务判断。 |
| `waiting_review` | 提纲、初稿或修订稿等待业务评审。 |
| `waiting_approval` | 敏感数据、对外使用或高风险动作等待批准。 |
| `succeeded` | 最终产物通过验收并完成交付。 |
| `failed` | 系统或业务错误导致任务终止，允许人工处理。 |
| `cancelled` | 有权用户显式取消任务。 |

网关重启、模型超时和外部工具暂时不可用，都不应使 WorkItem 丢失。

### WorkEvent

每次状态变化都追加不可变事件：

```text
WorkEvent
- event_id
- work_id
- event_type
- actor_type
- actor_id
- phase
- payload_digest
- policy_decision
- occurred_at
```

`WorkItem` 保存当前状态，`WorkEvent` 保存发生过什么。

它们不能只存在于 Langfuse。Langfuse 服务模型与 agent 调试，业务任务事件服务审计和运营。

## 报告标准作业流程

### Playbook

首个 Playbook 建议命名为：

```text
securities_industry_report/v1
```

完整流程为：

```text
需求受理
-> 报告合同确认
-> 材料盘点
-> 研究计划
-> 资料检索与证据登记
-> 数据分析
-> 提纲评审
-> 初稿编写
-> 事实与数字校验
-> 合规和保密检查
-> 业务评审
-> 修订
-> 最终批准
-> 文件交付
-> 任务归档
```

### 阶段 1：需求受理

数字员工从企微消息、附件或正式任务入口接收需求。

它先判断：

- 请求是否属于岗位职责；
- 委派人是否有权使用相关内部资料；
- 信息是否足够形成 ReportBrief；
- 是否存在相同的在途任务。

不完整需求进入 `waiting_input`，而不是让模型自行补全关键业务条件。

### 阶段 2：材料盘点

数字员工登记每个输入材料：

- `file_id`；
- 来源；
- 所有者；
- 保密等级；
- 适用时间；
- 解析状态；
- 是否允许外发；
- 是否允许送入外部模型或外部解析服务。

v0.0.9 的 CurrentFiles 和完整文件分析能力继续作为输入基础。

### 阶段 3：研究计划

研究计划至少包含：

- 报告章节建议；
- 需要回答的关键问题；
- 每个问题的预期证据；
- 内部材料和外部材料的使用范围；
- 数据分析任务；
- 风险和未知项。

研究计划由数字员工生成，但进入正式研究前由委派人确认。

### 阶段 4：资料与证据

Research 不直接把搜索结果堆进报告。它先登记来源和证据。

```text
SourceRecord
- source_id
- work_id
- source_type
- title
- publisher
- published_at
- retrieved_at
- uri_digest
- file_id
- confidentiality_level
- authority_level
- allowed_uses
- content_hash
```

```text
EvidenceRecord
- evidence_id
- source_id
- locator
- excerpt
- structured_value
- unit
- period
- confidence
- extraction_method
```

来源优先级建议为：

```text
已批准的公司内部数据
-> 监管机构、交易所和行业协会正式资料
-> 上市公司正式披露
-> 公司授权行业数据库
-> 权威研究机构
-> 一般公开网页
```

低优先级来源不能在没有交叉验证时支撑关键结论。

### 阶段 5：论点与引用

报告中的关键主张应登记为 Claim：

```text
Claim
- claim_id
- work_id
- section_id
- statement
- claim_type
- evidence_ids
- verification_status
- reviewer_status
```

建议至少对以下内容强制引用：

- 行业规模和增速；
- 市场份额和排名；
- 政策、法规和监管要求；
- 公司经营数字；
- 同业对比；
- 对未来趋势的关键判断。

事实、推断和建议必须在表达上区分。

### 阶段 6：提纲评审

提纲是 v0.1.0 的第一个强制人工评审点。

委派人以业务评审人身份可以：

- 通过；
- 退回修改；
- 调整章节；
- 增加或删除关键问题；
- 改变受众和篇幅；
- 终止任务。

提纲通过后形成版本，后续重大结构变化需要记录原因。

### 阶段 7：初稿编写

数字员工基于已登记证据生成初稿，而不是从无来源的模型记忆直接写作。

初稿至少包含：

- 标题和版本；
- 摘要；
- 正文章节；
- 图表或表格；
- 关键结论；
- 风险和不确定性；
- 来源和引用；
- 待确认问题。

### 阶段 8：质量检查

质量检查建议分成确定性检查和模型辅助检查。

确定性检查包括：

- 数字单位是否一致；
- 同一指标在不同章节是否冲突；
- 日期和报告期是否一致；
- 百分比和合计是否合理；
- 关键 Claim 是否有 Evidence；
- 引用是否能定位到来源；
- 内部材料是否违反输出范围；
- 是否包含宿主路径、token 或敏感配置。

模型辅助检查包括：

- 论证是否连贯；
- 是否遗漏反面证据；
- 推断是否超过证据；
- 摘要是否忠实于正文；
- 表达是否适合目标受众。

模型检查不能替代确定性规则和人工评审。

### 阶段 9：评审与修订

每条评审意见应结构化记录：

```text
ReviewComment
- comment_id
- work_id
- artifact_version
- section_id
- reviewer_id
- comment
- disposition
- resolution
- resolved_in_version
```

数字员工需要说明每条意见是“已采纳、部分采纳或未采纳”，并给出原因。

### 阶段 10：批准与交付

只有满足输出合同并获得所需批准，WorkItem 才能进入 `succeeded`。

建议 v0.1.0 交付：

- 最终 DOCX 报告；
- Markdown 中间稿；
- 来源清单；
- 关键 Claim-Evidence 对照表；
- 版本和审批记录；
- 可选 PDF 预览件。

交付文件必须登记为 `agentseek-files` outbound artifact，并关联 `work_id`。

## 权限、保密与外部服务

### 权限不能来自记忆

短期记忆、显式长期记忆和 pgvector 召回都不能证明权限。

权限判断必须来自：

- 企业身份；
- 数字员工岗位授权；
- 数据范围；
- Playbook 工具授权；
- 当前任务授权；
- 下游系统最终校验。

### 建议的保密等级

```text
public
internal
confidential
restricted
```

不同等级决定：

- 能否使用外部检索；
- 能否发送到外部 MinerU；
- 能否发送到外部大模型；
- 能否通过企微交付；
- 是否需要委派人以数据所有者身份确认；
- 产物保存和过期策略。

### 外部模型和解析器

v0.0.9 已验证 MinerU 文件解析，但 v0.1.0 需要增加任务级数据策略。

不能因为文件类型受支持，就默认允许内部材料离开公司边界。

建议每次外部调用都记录：

- `work_id`；
- 数据等级；
- provider；
- purpose；
- policy decision；
- 输入摘要或 digest；
- 输出 digest；
- 时间和执行结果。

## 审批模型

当前 MCP 的同一员工确认适合即时工具调用。正式报告需要独立审批实体：

```text
ApprovalRequest
- approval_id
- work_id
- approval_type
- subject_version
- requested_by
- approver_id
- decision
- decision_reason
- expires_at
- decided_at
```

v0.1.0 设置三个审批或评审节点，均由委派人完成：

1. 报告合同确认；
2. 提纲评审；
3. 最终报告批准。

涉及 restricted 数据时，委派人需要以数据所有者身份再次确认具体数据和用途。
对外发布不进入 v0.1.0 的自动执行范围；数字员工只交付给委派人。

批准必须绑定具体版本。批准后内容发生实质变化，应重新批准。

## 主动工作与企微交互

行业报告通常是长任务，不能依赖一次 WeCom stream 完成。

v0.1.0 需要支持：

- 创建任务后立即返回 `work_id`；
- 查询“我的报告任务”；
- 查询某个任务的进度和当前阻塞；
- 在等待输入时向委派人提问；
- 在等待评审时通知委派人；
- 任务失败时通知委派人和运维；
- 任务完成后发送结果或交付入口。

企业微信 AI Bot 不提供完整主动推送能力。建议 v0.1.0 接入自建应用主动消息，
并将通知抽象为 channel-independent `NotificationPort`。

如果主动消息无法在 v0.1.0 落地，任务状态仍必须持久化。员工可以通过查询命令恢复任务，
但这应视为降级模式，而不是目标体验。

## 技术架构

### 遵循 AgentSeek 插件框架的原则

AgentSeek 是 template-first toolkit。运行时插件模型来自 Bub。

当前 contrib 包通过 Python entry point 注册到 `bub` 分组。例如：

```text
wecom      = agentseek_wecom.plugin:main
enterprise = agentseek_enterprise.plugin:main
files      = agentseek_files.plugin:main
langchain  = agentseek_langchain.plugin:main
contextseek = agentseek_contextseek.plugin:ContextSeekPlugin
schedule   = agentseek_schedule_sqlalchemy.plugin:ScheduleImpl
```

v0.1.0 继续遵守这个模型，不在 `src/agentseek` 增加行业报告业务逻辑。

设计遵守六条原则：

1. AgentSeek core 只负责项目生命周期和模板工具，不承载企业业务。
2. 通用横向能力进入独立 contrib 插件。
3. 证券行业报告等纵向业务留在 enterprise-wecom 模板。
4. 插件通过 Bub hook、state 和公开 Python protocol 协作。
5. 插件不读取其他插件的私有数据库、目录或内部对象。
6. 模板是 composition root，负责选择和连接所需插件。

`agentseek-enterprise` 当前已经证明这种边界可行。它通过 `load_state()` 注入员工身份、
短期记忆和 HMAC scope，不处理企微协议，也不实现业务 MCP。

`agentseek-files` 通过 `load_state()` 注入 CurrentFiles，不决定模型如何回答报告任务。

`agentseek-wecom` 通过 `provide_channels()` 提供企微 channel，不拥有员工记忆和报告状态。

v0.1.0 的 Work Runtime 应沿用同一模式。

### 新增一个通用 work 插件

建议 v0.1.0 新增一个 contrib 包，而不是继续膨胀 `agentseek-enterprise`：

```text
contrib/agentseek-work/
```

建议 entry point：

```toml
[project.entry-points."bub"]
work = "agentseek_work.plugin:main"
```

它承担所有企业任务都可能复用的能力：

- DigitalEmployeeProfile 和 channel binding；
- 岗位版本、启停状态、requester scope 和权限 digest；
- WorkItem 和 WorkEvent；
- 状态机和乐观并发控制；
- 幂等创建；
- lease、重试、超时和取消；
- waiting_input、waiting_review 和 waiting_approval；
- ApprovalRequest；
- artifact 关系；
- 持久 outbox；
- 当前任务 state 注入；
- 任务级授权校验；
- 任务事件和观测关联。

它不承担：

- 企微协议；
- 员工身份查询；
- 文件下载和 OCR；
- 证券行业研究方法；
- 报告章节和写作 prompt；
- 具体 MCP server 配置；
- DOCX 模板和公司品牌样式。

这样 `agentseek-work` 可以被未来的审计数字员工、客服工单数字员工或运维数字员工复用，
而不会带入证券行业报告专属概念。

### 为什么不把 WorkItem 直接放进 agent.py

`agent.py` 是模板应用的 LangChain composition root。它适合：

- 选择模型；
- 注册工具；
- 注入模型可见的上下文；
- 组合 DeepAgents state 和 runtime context；
- 加载行业报告 Playbook。

它不适合拥有 PostgreSQL schema、任务锁、重试和 outbox。

如果 WorkItem 只写在 `agent.py`：

- 换 channel 后无法复用；
- 异步 worker 必须依赖聊天进程；
- 数据迁移和事务边界会与 prompt 代码混合；
- 其他 enterprise 模板无法使用；
- 测试只能做大而慢的端到端测试。

因此任务运行能力进入 `agentseek-work`，报告业务继续留在模板。

### DigitalEmployeeProfile 在一轮消息中的位置

`employee_context` 和 `DigitalEmployeeProfile` 表示两个不同主体：

```text
employee_context
= 当前发消息的战略发展部员工
= requester / reviewer / approver / data_owner / beneficiary

DigitalEmployeeProfile
= 接收委派并执行工作的行业报告数字员工
= digital_worker
```

因此必须先解析人类员工，再解析数字员工，最后才能加载双方之间的 WorkItem：

```text
Human Employee Identity
-> Digital Employee Binding
-> DigitalEmployeeProfile
-> requester_scope authorization
-> Current WorkItem
```

#### 数字员工如何绑定到 channel

建议增加持久化绑定：

```text
DigitalEmployeeBinding
- tenant_id
- channel
- channel_binding_key
- digital_employee_id
- enabled
```

`channel_binding_key` 可以来自企微 bot/callback 的稳定标识，并使用 HMAC 或内部映射保存。

`agentseek-wecom` 只负责把稳定、非密钥的 binding 信息放入 Envelope context。
它不查询 DigitalEmployeeProfile，也不判断战略发展部权限。

v0.1.0 只有一个数字员工时，可以配置 default digital employee 作为兼容路径。
但 WorkItem 仍必须保存明确的 `digital_employee_id`，不能长期依赖“系统里只有一个”的假设。

#### Profile 的解析时机

`agentseek-work.build_prompt()` 看到完整聚合 state 后，按以下顺序执行：

```text
1. 读取 employee_context 和 enterprise runtime scope
2. 读取 Envelope 中的 channel binding
3. 解析 DigitalEmployeeBinding
4. 加载已启用的 DigitalEmployeeProfile
5. 检查 requester 是否满足 profile.requester_scope
6. 注入安全的 digital_employee_profile 摘要
7. 加载显式 work_id 或当前员工的 Current WorkItem
```

所以 DigitalEmployeeProfile 位于 `employee_context` 之后、`current_work` 之前。

#### Profile 的 state 形态

模型可见 state 只放岗位说明：

```text
digital_employee_profile
- digital_employee_id
- name
- owning_org
- job_role
- responsibilities
- supported_playbooks
- profile_version
```

私有状态记录解析结果：

```text
_digital_employee_status
- found | not_configured | disabled | requester_forbidden
- binding_digest
- permissions_digest
```

完整 tool grants、data scopes 和策略规则不进入模型 prompt。
它们由 repository 和 tool adapter 在执行时读取并校验。

#### 没有 Profile 时的行为

如果没有绑定、岗位被停用或 requester 不在允许范围：

- 不创建或加载 WorkItem；
- 报告 tools 返回确定性的授权或配置错误；
- 不回退为一个拥有宽泛权限的通用 Agent；
- 写入脱敏诊断事件；
- 向员工返回可操作但不泄露内部配置的提示。

#### Profile 版本与任务复现

新任务使用当前启用的 Profile 版本，并在 WorkItem 保存：

```text
digital_employee_id
digital_employee_profile_version
digital_employee_permissions_digest
```

岗位档案更新后，新任务使用新版本。进行中的任务继续使用创建时固定的版本，
除非 Agent 运维执行显式、可审计的迁移。

这样可以解释某份历史报告当时使用了哪套岗位职责、Playbook 和权限。

### Bub hook 链路

当前 AgentSeek/Bub 一轮消息的主要扩展点是：

```text
provide_channels
-> admit_message
-> load_state
-> build_prompt
-> run_model / run_model_stream
-> save_state
-> channel.send / stream_events
```

v0.1.0 不新增一套平行事件循环。它把任务能力放进这条 hook 链。

完整交互链路建议为：

```text
1. agentseek-wecom.provide_channels
   接收企微消息并构造统一 Envelope

2. agentseek-enterprise.admit_message
   保持同一员工 session 的 turn 顺序

3. 所有插件 load_state 聚合
   enterprise -> employee_context / short_term_memory
   files      -> current_files / current_files_context
   schedule   -> scheduler capability

4. agentseek-work.build_prompt
   在完整 employee_context 已可用后解析 DigitalEmployeeProfile
   校验 requester_scope
   再加载当前 WorkItem
   写入 digital_employee_profile / current_work / current_work_context
   不直接改写用户问题

5. agentseek-contextseek.build_prompt
   按企业员工 scope 召回语义历史

6. agentseek-langchain.run_model_stream
   把聚合后的 state 和 runtime context 交给 RunnableSpec

7. enterprise-wecom agent.py
   注入 EmployeeContext、DigitalEmployeeProfile、CurrentFiles、CurrentWork
   注册通用 work tools 和报告 Playbook tools

8. tools / playbook
   在 repository 事务中修改 WorkItem
   文件只通过 file_id 访问
   MCP 调用继续经过 policy/audit

9. save_state
   保存短期记忆、语义历史和 turn-work 关联

10. agentseek-wecom
    返回当前回复；长任务由 worker 继续执行
```

这里选择 `build_prompt` 加载 scoped WorkItem，而不是直接依赖 `load_state()` 的插件顺序。

原因是每个插件的 `load_state()` 独立运行，不能假设它已经看到另一个插件刚返回的 state。
当前 `agentseek-contextseek` 已采用相同策略：企业 scope 依赖完整身份 state，
所以在 `build_prompt()` 阶段完成 scoped enrichment。

`agentseek-work.build_prompt()` 同样只丰富 state，返回 `None`，不把业务文字硬拼到 prompt。
最终是否把 CurrentWork 暴露给模型，由 enterprise-wecom 模板决定。

该 hook 使用 `_work_enriched` turn guard，保证 Bub 或 LangChain 多次触发 prompt hook 时，
同一 turn 不重复查询、加锁或产生业务事件。

### State 是组合边界，不是业务数据库

插件之间通过有命名约定的 state key 组合：

```text
employee_context         # 员工身份，模型可见
digital_employee_profile # 数字员工安全岗位摘要，模型可见
current_files            # 当前文件记录，应用可见
current_files_context    # 有界文件上下文，模型可见
current_work             # 当前任务摘要，应用可见
current_work_context     # 有界任务上下文，模型可见
_langgraph_runtime_context
  enterprise             # HMAC tenant/user/session scope
  digital_employee       # 数字员工 id、岗位版本和授权 digest
  work                   # work_id、playbook 和任务权限摘要
```

State 中只放当前 turn 需要的摘要：

- `work_id`；
- 报告标题；
- 当前状态和阶段；
- 当前等待事项；
- 当前 artifact 版本；
- 允许的下一步操作；
- 绑定 file_id；
- 脱敏的审批摘要。

以下内容不能整体放进 state：

- 完整报告正文；
- 全部 WorkEvent；
- 全部 Evidence；
- 数据库连接或 repository 对象；
- 原始内部文件；
- 审批凭证和 secret。

完整数据始终从 PostgreSQL 和 `agentseek-files` 按授权读取。

### Runtime context 的组合

`agentseek-enterprise` 当前将非 PII 的 tenant、employee 和 session HMAC key 写入
`_langgraph_runtime_context["enterprise"]`。

`agentseek-work` 在 `build_prompt()` 阶段保留已有 mapping，先增加数字员工 context：

```text
_langgraph_runtime_context["digital_employee"] = {
  version,
  digital_employee_id,
  profile_version,
  permissions_digest
}
```

存在 Current WorkItem 时，再增加：

```text
_langgraph_runtime_context["work"] = {
  version,
  work_id,
  playbook_id,
  requester_key,
  permissions_digest
}
```

它不能覆盖 `enterprise`。

enterprise-wecom 模板把当前 `EnterpriseRuntimeContext` 扩展为组合 schema，
供 LangGraph tools 获取 enterprise、digital_employee 和可选 work 三个 scope。

创建任务前还没有 `work` context，但必须已经有 `digital_employee` context。
这样 `create_work` 才知道任务应归属于哪个数字员工。

这样工具不需要从模型参数接受 `requester_id` 或数据库 scope，避免模型伪造身份。

### 通用 work tools 与报告 tools 分离

`agentseek-work` 提供窄而通用的 runtime-aware tools：

```text
create_work
get_work
list_my_work
cancel_work
provide_work_input
approve_work_version
```

这些工具负责：

- 从 runtime 获取真实 tenant 和 requester；
- 执行授权；
- 校验状态转换；
- 使用 repository 事务；
- 追加 WorkEvent；
- 返回结构化结果。

工具不能相信模型传入的 `requester_id`、`tenant_id`、`reviewer_id` 或数据 scope。
这些值必须来自 enterprise/work runtime context，并由 repository 再次校验。

enterprise-wecom template 提供报告专属 tools：

```text
create_report_brief
confirm_report_brief
submit_report_outline
review_report_outline
request_report_revision
deliver_report
```

报告 tools 调用 `agentseek-work` 的 service API，不直接写数据库。

这种分层与当前文件分析一致：`agentseek-files` 提供通用 `analyze_file`，
enterprise-wecom 决定什么问题必须调用它。

### Playbook 通过模板注入

`agentseek-work` 不 import `enterprise_wecom_digital_employee.reports`。

它只定义协议：

```text
WorkPlaybook
- playbook_id
- version
- validate_brief()
- allowed_transitions()
- run_phase()
- validate_output()
```

enterprise-wecom 提供实现：

```text
securities_industry_report/v1
```

Work plugin 从模板配置的 registry import path 加载 Playbook。

这种模式与 `AGENTSEEK_LANGCHAIN_SPEC` 相同：通用插件定义加载合同，
生成项目提供实际 RunnableSpec 或 Playbook。

因此其他模板可以注册自己的 Playbook，而不修改通用 work 包。

### 交互 turn 与异步 worker 分离

企微 turn 只负责：

- 创建或查询任务；
- 收集缺失信息；
- 执行一次明确的评审或批准；
- 返回当前状态。

它不应在一个 stream 中持续运行完整行业研究。

`agentseek-work` 提供一个 lifecycle channel 或受管 worker：

```text
WorkRuntimeChannel.start()
-> claim queued WorkItem with lease
-> load registered Playbook
-> run one resumable phase
-> commit output and WorkEvent
-> transition or schedule next wakeup
-> write notification outbox
```

这沿用 `agentseek-schedule-sqlalchemy` 通过 `provide_channels()` 管理后台 scheduler 生命周期的做法。

worker 必须具备：

- PostgreSQL lease；
- lease 到期回收；
- 乐观版本号；
- phase 级 idempotency key；
- 有界重试；
- graceful shutdown；
- 单阶段提交；
- 从最后成功阶段恢复。

模型进程失败不能把 WorkItem 留在不可恢复的 `running`。

### 调度插件只负责时间

`agentseek-schedule-sqlalchemy` 保持独立，不存储 WorkItem 内容。

它负责：

- 到期任务唤醒；
- retry_at；
- due_at 检查；
- 评审和输入等待提醒；
- outbox 重试。

实际任务状态仍在 PostgreSQL Work repository。

调度 job 只携带 `work_id` 和操作类型，不携带报告正文、员工姓名和文件路径。

### 文件插件只暴露 file_id 和 artifact

WorkItem 只保存：

```text
input_file_ids
artifact_ids
```

它不保存 `runtime/files/.../original` 的宿主路径。

报告 Playbook 通过 `agentseek-files` 的公开 service 读取：

- 文件元数据；
- 已提取文本；
- 完整分析结果；
- outbound artifact 登记。

`agentseek-files` 继续负责：

- 文件 scope；
- MIME 和扩展名；
- 解析状态；
- MinerU；
- 文件生命周期；
- artifact 物理位置。

`agentseek-work` 只负责“这个文件为什么属于这个任务”。

### MCP 仍是业务系统边界

报告 Playbook 查询行业数据时继续使用现有 MCP adapter。

调用链保持：

```text
Report Playbook
-> template MCP adapter
-> enterprise MCP policy
-> confirmation when required
-> remote MCP server
-> MCP audit
```

Work Runtime 不绕过 MCP policy，也不直接连接已有 MCP 背后的业务数据库。

每次调用额外关联：

- `work_id`；
- `phase`；
- `source_id`；
- Playbook version；
- WorkEvent id。

如果现有 MCP audit 暂时不能增加字段，v0.1.0 先在 WorkEvent 保存 MCP audit event id，
而不是复制或重写 policy 判定逻辑。

### ContextSeek 不是报告证据库

`agentseek-contextseek` 继续负责员工历史对话的语义召回。

它可以帮助理解“继续上一份报告”之类的自然语言，但不能作为：

- WorkItem 状态源；
- 已批准报告版本；
- 权限证明；
- 行业数据来源；
- Claim 的正式 Evidence。

正式 Source、Evidence 和 Claim 进入 Work repository。

这保持了 v0.0.9 已验证的记忆分层原则。

### Channel 和主动通知解耦

`agentseek-work` 不 import `agentseek-wecom`。

Work Runtime 在同一事务中写入持久 notification outbox：

```text
WorkNotification
- notification_id
- work_id
- recipient_key
- event_type
- payload
- status
- attempts
- next_attempt_at
```

enterprise-wecom template 负责将 outbox dispatcher 连接到
`agentseek-wecom` 的自建应用主动消息 adapter。

如果未来增加飞书或 Web channel，只替换 notifier，不修改 WorkItem 和报告 Playbook。

发送成功后更新 outbox。重复发送使用稳定 notification id 防重。

### 插件依赖方向

建议依赖保持单向：

```text
agentseek core
    ^
    | Bub entry points
    |
contrib plugins                 enterprise-wecom template
  enterprise  <---------------- composition root
  work        <---------------- composition root
  files       <---------------- composition root
  wecom       <---------------- composition root
  langchain   <---------------- composition root
  contextseek <---------------- composition root
  schedule    <---------------- composition root

work      -X-> wecom
work      -X-> MinerU
files     -X-> report Playbook
wecom     -X-> Work repository
core      -X-> enterprise business packages
```

箭头表示模板依赖插件。`-X->` 表示禁止的依赖。

跨插件协作通过：

- state key；
- runtime context；
- file_id / work_id / event_id；
- 公共 protocol；
- 模板 composition；
- 持久 outbox。

不通过导入另一个插件的 `_private` 对象或读取其数据库表实现。

### Sandbox 的位置

原路线中的任务级 sandbox 仍然需要，但它不再是 v0.1.0 的产品中心。

v0.1.0 只实现报告任务需要的受控能力：

- 读取当前 WorkItem 明确授权的输入文件；
- 运行 allowlist 中的文档生成和转换命令；
- 禁止读取项目根目录、`.env` 和其他员工目录；
- 默认禁止网络，研究访问由受控工具完成；
- 限制 CPU、内存、执行时间和输出大小；
- 将生成文件登记为 outbound artifact；
- 清理临时目录并写入脱敏事件。

不向模型提供任意 shell。

### Agent 编排原则

v0.1.0 不以多个自治 subagent 为目标。

建议采用：

```text
确定性状态机
+ 受约束的模型节点
+ 受策略保护的 MCP 工具
+ 人工评审和批准
```

研究、写作和检查可以使用不同 prompt 或模型配置，但它们共享同一个 WorkItem 和证据库。

### 测试边界

插件化也体现在测试分层：

```text
agentseek-work unit tests
  Profile binding、requester scope、版本固定、状态机、repository、lease、幂等、审批、outbox

plugin hook tests
  Profile 先于 WorkItem 解析、禁用与越权、runtime context 合并、save_state 关联

report Playbook tests
  ReportBrief、来源、证据、提纲、质量门、产物合同

template composition tests
  所有 entry points、tools、state schema 和 env 接线

Mac mini live tests
  企微委派、异步恢复、评审、DOCX 交付、权限和故障恢复
```

每个 contrib 包可以独立测试。只有最终 composition 和活体链路需要完整环境。

## v0.1.0 MVP 范围

- 一个可配置的行业报告数字员工岗位档案；

## 验收场景

### 验收 A：证券行业发展报告

输入：

- 一组公开行业 PDF；
- 一份行业数据 XLSX；
- 授权 MCP 数据；
- 明确的管理层报告需求。

期望：

- 创建唯一 `work_id`；
- 形成并确认 ReportBrief；
- 形成来源清单和研究计划；
- 提纲经人工评审；
- 报告中关键数字均可追溯；
- 断言、推断和建议表达清楚；
- 生成 DOCX 和证据清单；
- 最终批准后交付；
- 所有动作可按 `work_id` 审计。

### 验收 B：公司内部专题报告

输入：

- internal 或 confidential 文件；
- 公司经营数据；
- 内部报告模板；
- 已解析的战略发展部委派人；

期望：

- 非授权员工不能读取任务和文件；
- 外部工具调用遵守数据策略；
- restricted 数据不会发送到未批准 provider；
- 报告只交付给授权对象；
- 删除或过期策略按配置执行；
- Langfuse 和日志不出现报告正文或敏感数据。

### 验收 C：跨重启恢复

任务在研究、等待评审和文档生成阶段分别重启网关。

期望：

- WorkItem 状态不丢失；
- 已完成步骤不重复执行；
- MCP 写操作不重复；
- 已批准版本仍能准确识别；
- 任务从正确阶段恢复。

### 验收 D：证据冲突

两个来源对同一行业指标给出不同数字。

期望：

- 系统不静默选择任意一个数字；
- 记录来源、口径和报告期差异；
- 请求人工判断或在报告中解释差异；
- 最终 Claim 指向被采用的证据和选择理由。

## 质量指标

v0.1.0 建议至少跟踪：

| 指标 | 含义 |
| --- | --- |
| 任务完成率 | 进入 `queued` 的任务中成功交付的比例。 |
| 首次评审通过率 | 提纲或报告首次提交后直接通过的比例。 |
| 平均修订轮次 | 最终批准前的人工修订次数。 |
| Claim 引用覆盖率 | 必须引用的关键 Claim 中已绑定证据的比例。 |
| 数字校验通过率 | 确定性数字检查一次通过的比例。 |
| 来源有效率 | 来源可访问、可定位且在适用时间内的比例。 |
| 人工接管率 | 需要运维或业务人员接管的任务比例。 |
| 重复执行率 | 因重试导致步骤或业务动作重复的比例。目标为零。 |
| 越权阻断率 | 权限策略正确阻断的访问或操作数量。 |
| 敏感数据泄露数 | 未授权外发、日志或 trace 泄露。目标为零。 |

这些指标用于改进流程，不直接用于评价自然人员工。

v0.1.0 不重写这些能力。它在上面增加工作任务层：

```text

v0.1.0: 企业可以把一项报告工作正式委派给数字员工，
        并对执行过程、审批、交付和责任进行管理
```

## 风险与取舍

### 报告质量不能只靠更强模型

模型能力会影响表达质量，但企业报告的可靠性主要依赖：

- 清晰的任务合同；
- 有层级的来源；
- Claim-Evidence 绑定；
- 确定性数据检查；
- 版本化评审；
- 人工最终责任。

### 通用工作流会拖慢首个场景

v0.1.0 应先实现证券行业报告 Playbook，不先建设万能工作流平台。

模型、数据结构和执行接口应可扩展，但 UI 和配置器不必提前通用化。

### DOCX 是必要交付，不是附加功能

行业报告数字员工若只能在企微回复 Markdown，尚未形成完整岗位交付。

因此 v0.1.0 建议把受控 DOCX 生成和 outbound 登记列为必须交付。

### 自主性必须受责任边界约束

数字员工可以自主推进低风险研究步骤，但以下事项必须等待人：

- 改变报告范围；
- 使用超出任务授权的内部数据；
- 选择存在重大冲突的关键数字；
- 形成对公司有重大影响的战略结论；
- 对外发布；
- 覆盖已批准版本。

## 待逐项确认

### 产品决策

1. 正式名称采用“行业报告编写数字员工”还是“证券行业研究数字员工”？
2. 数字员工行政归属是否固定为战略发展部？
3. v0.1.0 首个验收报告的具体主题是什么？
4. 公司报告是否与行业报告共用一个 Playbook，还是拆成两个？
5. 最终产物是否必须同时包含 DOCX 和 PDF？

### 数据与合规

6. 公司现有数据分级标准是什么？是否沿用 `public/internal/confidential/restricted`？
7. 哪些材料允许发送到外部 MinerU 和外部大模型？
8. 哪些来源属于战略发展部认可的权威来源？
9. 是否需要保存网页或公告原文快照，以保证后续复核？
10. 报告底稿和最终产物分别保存多久？

### 已确认的组织与审批决策

- 战略发展部员工可以作为报告任务委派人。
- 委派人同时是业务评审人、最终批准人、当前任务的数据所有者和交付对象。
- 行业报告数字员工负责执行，不拥有最终批准权。
- 信息技术部 Agent 运维负责运行保障，不默认读取报告正文和业务数据。
- v0.1.0 不自动对外发布报告，只向委派人交付。

### 渠道与交付

11. v0.1.0 是否接入企业微信自建应用主动消息？
12. 报告通过企微文件、链接还是公司文档系统交付？
13. 是否已有公司 Word 报告模板和固定章节规范？
14. 是否需要在企微之外提供任务管理页面？
15. 报告评审意见从企微输入，还是从 Word 批注导入？

组织角色已经收敛。下一步逐项确认本文剩余十五个问题，优先冻结以下五项：
