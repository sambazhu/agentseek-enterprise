# v0.1.0 首个行业报告验收 Oracle

## 验收对象

| 字段 | 冻结值 |
| --- | --- |
| 报告题目 | 2025年中国证券行业发展研究报告。 |
| 目标受众 | 证券公司总经理。 |
| 委派部门 | 战略发展部。 |
| 交付对象 | 发起任务的委派人。 |
| 任务性质 | 在 50 分钟执行预算内形成可评审初稿，不宣称自动形成无需人工批准的最终研究结论。 |
| Playbook | `securities_industry_report/v1`。 |
| 正式产物 | 版本化 Markdown、DOCX、来源清单和证据清单。 |

## 必须回答的问题

报告必须完整回答以下问题，不能只生成行业信息摘要：

1. 2025 年中国证券行业在市场、监管、经营、竞争格局和技术应用方面发生了什么变化；
2. 代表性证券公司的经营表现和业务结构存在哪些可比差异，差异的事实依据是什么；
3. 五矿证券的财富、投行、自营权益、自营固收、资管五条业务线分别有哪些可借鉴做法；
4. 每项借鉴点适用于什么条件，依赖什么能力，存在什么风险，用什么指标验证；
5. 哪些关键数字或判断存在来源冲突、口径差异或证据不足，需要委派人判断。

## 验收输入合同

每次正式验收必须先生成不可变 fixture manifest，至少包含：

| 输入类型 | 最低要求 | manifest 字段 |
| --- | --- | --- |
| 内部材料 | 至少一个由委派人授权的文件输入。 | `file_id`、文件 digest、data_owner、分级、用途。 |
| 企业数据 | Gildata MCP 的行业和公司经营数据。 | server id、query fixture、参数摘要、数据版本、result digest。 |
| 公开来源 | 覆盖行业、监管和公司披露的可复核来源。 | locator、retrieved_at、许可、snapshot status、digest。 |
| 报告合同 | 本文冻结的题目、受众、报告期和必须回答的问题。 | `report_brief_version`、`playbook_version`、`pack_snapshot_id`。 |

fixture manifest 在验收开始前固定；不得用执行完成后的数据反向修改 oracle。
材料内容可在 Mac mini 的受控运行环境登记，不要求把业务文件提交到 Git。

## 内容 Oracle

### 结构完整性

- 执行摘要明确列出行业判断、同业差异、五矿证券借鉴点和重大不确定性；
- 行业发展概况、证券公司经营差异、五条业务线对标、行动建议、风险与不确定性、来源与证据附录均存在；
- 五条业务线逐线呈现，不得把权益自营与固收自营合并成一个无法评审的笼统结论；
- 每项行动建议包含依据、适用前提、依赖或风险、验证指标。

### 数据与比较正确性

- 比较前明确报告期、币种、单位、合并范围和指标口径；
- 同一比较表不混用未经说明的母公司与合并口径、年度与时点口径；
- 可确定性复算的合计、同比、占比、排序和范围通过程序校验；
- 每个关键定量结论都能定位到 SourceRecord 和 Evidence；
- 来源冲突不能静默覆盖，必须展示冲突值、来源、口径和采用理由；
- 输入或来源不足时明确降级，不编造公司、数字、排名、政策或引用。

### 对标有效性

五条业务线各自至少形成一组“同业事实 → 能力机制 → 五矿证券适用条件 → 建议动作 → 验证指标”的闭环。
只列同业案例、只给通用建议或只改写内部材料，均不算通过。

## 可追溯与安全 Oracle

- 关键 Claim 的 Evidence 覆盖率为 100%；非关键背景描述也必须有来源定位；
- DOCX、Markdown、来源清单和证据清单绑定同一 `work_id` 与 artifact version；
- 报告不包含 token、签名 URL、response_url、宿主绝对路径或未经授权的原始业务附件；
- Gildata 调用继续经过 MCP policy/audit，两个受保护文件保持相对 `68d7b25` 零 diff；
- Langfuse 和本地日志不记录文件正文、完整商业查询结果或业务敏感标识。

## 工作流 Oracle

| 阶段 | 通过条件 |
| --- | --- |
| intake | ReportBrief、输入 manifest、数据分级和授权完整。 |
| research | SourceRecord、Evidence、Claim 和 EvidenceConflict 可追溯。 |
| outline review | 委派人通过稳定 `section_id` 评审提纲。 |
| draft | 在 50 分钟预算内形成可评审初稿，或交付明确的部分结果和未完成原因。 |
| quality gate | 结构、数字、引用、冲突、安全和格式检查通过。 |
| approval | 批准绑定明确 artifact version；数字员工不自我批准。 |
| delivery | 只向 requester 提供一次性延迟通知和受控 DOCX 下载入口。 |

## 判定规则

- 任一关键数字不可追溯、五条业务线有遗漏、出现事实性编造、越权外发或批准版本错配，结果为 `FAIL`；
- 外部服务在预算内未完成但系统按合同停止、保留状态并交付可验证的部分结果，可判为 `DEGRADED_PASS`，不得判为完整通过；
- 只有内容、证据、流程、安全和 DOCX 视觉验收全部通过，才判为 `PASS`。
