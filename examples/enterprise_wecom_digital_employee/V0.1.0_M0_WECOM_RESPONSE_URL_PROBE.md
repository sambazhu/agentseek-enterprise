# 验证企业微信短连接延迟回复

## 配置探针

在 Mac mini 未提交的 `.env` 中设置一次性测试口令：

```env
AGENTSEEK_WECOM_RESPONSE_URL_PROBE_TRIGGER=<随机测试口令，不提交>
AGENTSEEK_WECOM_RESPONSE_URL_PROBE_DELAY_SECONDS=10
```

探针默认关闭。`TRIGGER` 为空时，生产消息路径保持原行为。

## 运行自动化检查

```bash
make test-wecom
```

自动化检查覆盖：

- `response_url` 不进入 prompt-safe context；
- 只接受配置的企业微信 HTTPS endpoint；
- 测试口令不进入 agent；
- 每个回调 URL 只提交一次延迟 Markdown；
- URL 缺失时关闭失败，不调用外部地址。

## 运行活体探针

```bash title="not executed in this run"
examples/enterprise_wecom_digital_employee/scripts/run_gateway.sh
```

TODO（Mac mini）：按现有生产重启流程加载探针配置。不要并行启动第二个网关。

在企业微信中向当前 AI Bot 发送与 `TRIGGER` 完全一致的测试口令。

预期收到两条消息：

1. 当前 stream 返回“短连接延迟回复探针已启动”；
2. 约 10 秒后收到“短连接 response_url 延迟回复探针成功”。

第二条消息必须来自同一个 AI Bot 会话，不是自建应用通知。

## 检查证据

| 检查项 | 通过条件 |
| --- | --- |
| 当前回复 | stream 正常结束，不影响既有 callback。 |
| 延迟回复 | 新消息在配置延迟后到达。 |
| 一次性 | 延迟消息只出现一次。 |
| 日志 | 只有 `wecom_response_url_probe status=succeeded`，没有完整 URL。 |
| Langfuse | 没有 `response_code`、完整 URL、测试口令或消息正文。 |
| 回归 | 普通文本、文件、语音和 A–E 回归正常。 |

## 关闭探针

从 Mac mini `.env` 删除两个 probe 变量并按生产流程重启网关。

探针消息属于用户可见外部状态，脚本不能自动撤回。只使用测试员工会话。
