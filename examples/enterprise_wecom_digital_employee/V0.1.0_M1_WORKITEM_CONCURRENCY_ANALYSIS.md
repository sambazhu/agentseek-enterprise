# M1-05 并发 WorkItem 约束分析

## 观察

活体验证中发现：同一 tenant + requester + digital_employee 可以同时存在多个非终态 WorkItem。

当前 `create_report_work` 的幂等机制基于 `(tenant_id, idempotency_key)` UNIQUE，其中 `idempotency_key` 从 message content + HMAC msgid 派生。不同企微消息（不同 msgid）产生不同 idempotency_key，因此可以创建多个非终态 WorkItem。

`find_current_work(tenant_id, requester_id, digital_employee_id)` 返回一个非终态 WorkItem，但 DB 层无约束阻止创建第二个。

## 现状

```
用户发"创建报告任务 A" → WorkItem 1 (draft/intake)  ← 非终态
用户发"创建报告任务 B" → WorkItem 2 (draft/intake)  ← 非终态
用户发"创建报告任务 C" → WorkItem 3 (draft/intake)  ← 非终态
```

无 DB 约束或应用层检查阻止上述序列。

## 潜在影响

1. 用户无法确定"当前在做的报告"是哪一个。
2. 预算用量按 `work_id` 隔离，并不会互相扣减；但多个任务各自获得完整预算，会放大总体资源消耗。
3. worker claim 时多个 queued WorkItem 竞争执行资源。
4. `find_current_work` 返回多个非终态中的一个，选择逻辑不明确。

## 可选方案

### 方案 A：绝对一对一

同一 `(tenant_id, requester_id, digital_employee_id)` 最多一个非终态 WorkItem。

DB partial unique index：
```sql
CREATE UNIQUE INDEX uq_one_active_work_per_employee
ON enterprise_work_items (tenant_id, requester_id, digital_employee_id)
WHERE status NOT IN ('succeeded', 'failed', 'cancelled');
```

应用层：`create_report_work` 创建前 `find_current_work`，如有非终态任务 → 返回已有或拒绝。

### 方案 B：按 Playbook 类型限制

同一 `(tenant_id, requester_id, digital_employee_id, playbook_id)` 最多一个非终态 WorkItem。不同 playbook 可并行。

DB partial unique index：
```sql
CREATE UNIQUE INDEX uq_one_active_work_per_playbook
ON enterprise_work_items (tenant_id, requester_id, digital_employee_id, playbook_id)
WHERE status NOT IN ('succeeded', 'failed', 'cancelled');
```

应用层：`create_report_work` 创建前检查同 playbook 是否有非终态任务。

### 方案 C：不限制，显式队列

允许多个非终态 WorkItem，但 `find_current_work` 按优先级 + created_at 返回最新的一个。用户可显式切换当前任务。

## 待 Codex 决策

1. 选择 A / B / C 或提出其他方案。
2. 如选 A 或 B，`create_report_work` 遇到已有非终态任务时的行为：返回已有（`created=False`）还是拒绝。
3. `find_current_work` 在多个非终态存在时的选择策略（最新 / 最高优先级 / 报错）。
4. 是否在 schema revision 5 中加 partial unique index。

## 决策：方案 B（M1-06）

采用按 Playbook 限制的并发合同：同一
`(tenant_id, requester_id, digital_employee_id, playbook_id)` 最多存在一个非终态
WorkItem。不同 Playbook 可并行，`playbook_version` 不进入并发键，避免角色包升级时绕过约束。

### 创建语义

- 相同 `(tenant_id, idempotency_key)`：视为同一消息重放，返回原 WorkItem，`created=False`；
- 不同 idempotency key、但命中同一活跃 Playbook scope：抛出显式
  `ActiveWorkConflictError`，携带现有 WorkItem，工具告知员工现有 `work_id/status/phase`；
- 不把新请求伪装成幂等重放，也不静默新建第二个任务；
- 原 WorkItem 进入 `succeeded/failed/cancelled` 后，scope 自动释放。

### 数据库真相源

schema revision 5 建立 migration-only partial unique index：

```sql
CREATE UNIQUE INDEX uq_work_items_active_playbook
ON enterprise_work_items (
  tenant_id, requester_id, digital_employee_id, playbook_id
)
WHERE status NOT IN ('succeeded', 'failed', 'cancelled');
```

应用层预检查用于提供清晰反馈；数据库索引负责封闭并发竞态。迁移前扫描重复活跃
scope，发现存量冲突就失败关闭，不自动删除、合并或选择任务。索引不放入 SQLAlchemy
metadata，因为 `metadata.create_all()` 先于 revision 执行，必须保证先完成存量检查。

### 查询语义

- 新增 `find_active_work(..., playbook_id)`，供数字员工 composition 和状态工具精确查询；
- `find_current_work` 保留为跨 Playbook 的兼容/概览 API，并继续使用确定性排序；
- M2 在该合同上继续实现 ReportBrief 与 intake，不再依赖“最近一条可能是哪条”的隐式选择。
