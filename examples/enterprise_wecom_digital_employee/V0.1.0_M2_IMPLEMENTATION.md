## 决策冻结

### ReportBrief 采用渐进式澄清

首版 ReportBrief 不是一张长表。员工只需先说明报告主题。
系统从消息、岗位 Profile 和 Playbook 默认值补全其余字段。

首版合同字段：

| 字段 | 规则 |
| --- | --- |
| `title` | 必填；报告主题。 |
| `target_audience` | 确认前必填；可以从上下文推断，也可以向员工追问一次。 |
| `coverage_period` | 报告覆盖期；允许明确指定、系统推断或使用 Playbook 默认值。 |
| `coverage_period_source` | `explicit`、`inferred` 或 `playbook_default`。 |
| `output_formats` | 默认 `docx`；首版允许 `markdown`、`docx`、`pdf`。 |
| `delivery_sla_minutes` | 默认 50；来自岗位 Playbook，不要求员工逐次填写。 |
| `confidentiality_level` | 默认 `internal`。 |

`ReportBrief.missing_fields` 首版只返回缺失的 `target_audience`。
覆盖期缺失不会阻断 intake。系统使用“截至请求时间的最新可得数据”。

### 合同与研究的边界

```text
自然语言请求
-> provisional ReportBrief
-> 必要时澄清目标受众
-> 委派人确认具体版本
-> 正式研究
```

- provisional 合同可以随 WorkItem 在 `draft/intake` 中持久保存。
- 未确认合同不得启动正式知识检索、外部搜索或报告编写。
- 合同确认只允许 WorkItem requester 执行。
- 确认后发生实质变化时，旧版本进入 `superseded`，新版本重新从
  `provisional` 开始。
- `WorkItem.brief` 保留为 M1 兼容字段，不作为 M2 合同真相源。

### 部门知识库采用 MCP 边界

正式部门知识库由外部知识库平台管理，通过 MCP 接入。
本地 PostgreSQL + pgvector 仅用于开发和合同模拟，不成为第二套生产知识平台。

首版不增加逐员工授权表。行业报告数字员工的 Profile 已固定
`owning_org: 战略发展部`，知识库工具按当前数字员工 Profile 和部门 scope
执行服务端约束。

建议的检索顺序：

```text
list/glob 元数据
-> keyword/grep 候选
-> semantic 补充
-> hybrid 排序
-> read 选定片段
```

知识库平台应提供关键词检索。关键词检索适合精确术语、文件名、代码、指标和专有名词；
向量检索适合语义改写和概念问题。默认使用 hybrid，而不是把全部文档注入模型。

当部门知识库不能覆盖关键问题时，系统向员工展示缺口，再让员工选择：

- 允许使用 Gildata 或公开搜索；
- 上传补充材料；
- 保留缺口继续生成。

## Slice M2-01：Lightweight ReportBrief and versioned contract ledger

### 通用 work 合同

`agentseek-work` 新增通用 `WorkContractSnapshot`，不包含报告领域字段。
其他数字员工可以用同一机制保存差旅合同、会议合同或审批合同。

| 能力 | 合同 |
| --- | --- |
| 状态 | `provisional`、`confirmed`、`superseded`。 |
| 版本 | `(work_id, contract_type, contract_version)` 复合主键。 |
| 当前版本 | 同一 `work_id + contract_type` 最多一个非 superseded 版本。 |
| payload | JSON 文档，由具体岗位定义 schema。 |
| 确认 | requester-only，带 expected version。 |
| 修订 | 当前版本原子 supersede，并追加下一 provisional 版本。 |
| 幂等 | 相同版本和相同内容可以安全重放。 |
| 租户边界 | 所有读写同时校验 `tenant_id` 和 `work_id`。 |

schema revision 6 新增 `enterprise_work_contracts` 和
`uq_work_contracts_current_type` partial unique index。
迁移在建索引前检查重复 current contract；发现脏数据时 fail closed。

### 行业报告合同

行业报告字段位于 example/template 的 `report_brief.py`。
`ReportBrief.to_contract()` 将领域合同转换为通用 WorkContract payload；
`ReportBrief.from_contract()` 按 schema version fail closed 还原。

## Slice M2-02：Department knowledge MCP contract and local hybrid simulator

### 实现边界

- 行业报告数字员工 Profile 升级为 `1.1.0`，声明 `knowledge_refs`。
- 部门知识库归属战略发展部，MCP 服务名固定为 `department-knowledge`。
- 服务端环境固定 tenant、collection 和 owning organization；模型参数不能切换 scope。
- 本地模拟器使用独立的 PostgreSQL `pgvector + pg_trgm` 表，不复用员工 ContextSeek 表。
- 只提供 list、search、read 三个只读工具。Word 文档只允许管理员导入。
- 员工通过企微上传的文件仍是 request-scoped material，不自动成为部门共享知识。
- Tavily 和 Gildata 保留在现有 MCP 配置中；M2-02 不自动调用，知识缺口必须先向员工说明并请求许可。

### 本地检索

```text
document metadata
-> keyword candidate search (pg_trgm / exact substring)
-> bge-m3 semantic search (pgvector cosine)
-> reciprocal rank fusion
-> selected chunk read
```

完整 MCP 字段合同见 `DEPARTMENT_KNOWLEDGE_MCP.md`。正式知识平台只需实现相同的
contract version 1，部署时替换 MCP server 配置，不需要修改 Profile 或报告流程。

### 本切片不包含

- 报告模板驱动的自动检索计划与 SourceRecord；
- coverage/gap 计算；
- 自动 Gildata/Tavily fallback；
- 员工上传材料自动发布到部门知识库；
- 部门知识平台的生产实现。

## Slice M2-03：Template-driven internal research and source coverage

### 实现边界

- 正式检索必须绑定 requester-scoped WorkItem 和当前 `confirmed` ReportBrief。
- DOCX 模板对应的结构化检索 manifest 位于 report-intake Skill 的 `references/`，
  与 PackSnapshot 一起内容寻址固定；章节和问题使用稳定 ID。
- `run_internal_report_research` 只调用 `department-knowledge/knowledge_search`
  和 `knowledge_read_chunks`，每个问题最多读取两个入选片段。
- schema revision 7 新增 `enterprise_work_sources`。SourceRecord 是租户隔离、不可变、
  幂等的来源账本，保存 locator/query/content/result digest、许可、分级和快照状态；
  不复制部门知识正文。
- coverage/gap 由模板问题与实际登记 SourceRecord 确定性计算，不交给模型判断。
- 内部知识缺口只返回给员工；本切片不自动调用 Gildata/Tavily，也不生成报告正文。

### ReportBrief 工具链

`save_report_brief` 保存或原子修订 provisional 合同，并向员工展示精确版本；
`confirm_report_brief` 仅在员工最新消息明确确认该版本后调用。确认前调用内部研究会
fail closed。确认后的实质修订会产生下一 provisional 版本，旧版本 superseded，新的
检索必须等待再次确认。

### M2/M3 边界

M2-03 只登记 SourceRecord 和覆盖缺口。Evidence excerpt、Claim-Evidence 绑定、
EvidenceConflict、研究计划人工确认和报告写作仍属于 M3/M4，不在本切片提前实现。

### M2-03 验收要点

- 5 个稳定 section/question ID 的模板 manifest；
- 未确认 ReportBrief 拒绝研究；
- 模拟 MCP 仅调用 `department-knowledge`；
- 1/5 问题命中时 coverage=0.2、4 个 gap；
- 重放检索保持 1 条 SourceRecord，不重复写入；
- example、template、work ledger 的测试和静态检查由本提交最终验证登记。

### ⛔ 阻断项

**`knowledge_search` 工具参数命名不匹配**

工具定义参数：`mode: SearchMode` / `limit: int`
模型（glm-5.2）传入：`search_mode='hybrid'` / `top_k=6`

glm-5.2 持续使用更具描述性的参数名（`search_mode`、`top_k`），与工具定义的泛化名（`mode`、`limit`）不匹配。C 能通过是因为模型那次没传参数（用默认 hybrid），但 E/F 模型明确传参导致报错。

**修复建议**：把 `mcp_server.py` 的工具参数 `mode` → `search_mode`、`limit` → `top_k`。或添加 `pydantic.Field(alias=...)` 别名。

### 非阻断观察

1. **stream dedup 健壮性**：网关报错或重启后，in-memory stream 丢失，WeCom 重试的旧 stream_id 被新网关当作 duplicate_msgid，可能吞掉同一窗口内的新消息。这是 v0.0.9 in-memory stream 设计的已知限制，不是 M2-02 bug。建议后续 stream 超时自动清理或加 TTL 过期。
2. **MCP server 懒启动**：`department-knowledge` MCP server 在模型首次调用工具时启动（非网关 boot 时），首次搜索有额外延迟。非阻断。
3. **0 SIGBUS / 0 Traceback / 0 HTTP 非200** ✅（grep 中 SIGBUS=1 为假阳性，实际匹配的是错误信息中的 "Traceback" 文本）

## M2-03 blocker remediation: component-aware relevance gate

Codex 在上述 BLOCKED 报告后确认：hybrid `score` 是 `k=60` 的 reciprocal rank
fusion 排名分，理论最大值约为 `2 / 61 = 0.0328`，不是 0-1 相关性置信度。
因此用 `minimum_score=0.05` 直接过滤属于量纲错误。

修复保持 department-knowledge 的 RRF 排序合同不变，在研究模板中明确三类阈值：

- `minimum_fused_score=0.02`：关键词和语义排名形成双路佐证时准入；
- `minimum_keyword_score=0.08`：沿用部门知识库的关键词最低相似度；
- `minimum_semantic_score=0.70`：用 bge-m3 cosine similarity 判断纯语义命中。

hybrid 命中满足任一门槛即可进入候选；keyword/semantic 模式只检查各自对应的
component score。RRF 仍只负责排序，不再被误当成统一置信度。真实相关样本
`score=0.032258, semantic_score=0.843804` 可以通过，已验证的无关样本
`score=0.015, semantic_score=0.664` 会被拒绝。SourceRecord 的 `result_digest`
同时纳入三个 component score，保留判定依据但不复制知识正文。

回归 fixture 已改用上述真实分数分布，在一次研究中同时验证低 RRF/高语义命中与
低 RRF/低语义拒绝，防止再次产生 0 SourceRecord 假 gap。Mac mini 仍需重测
E、VI、VII 和 VIII 后才能关闭 M2-03。

## M2-04 阻断修复：主题直接证据缺口 + 报告正文交付守卫

### 设计决定

不通过删除知识库文档或注入合成 gap 来打通活体路径。报告主题本身是否获得直接证据，
是正式研究合同的一部分：通用行业方法论可以支持章节框架，但不能替代对命名机构、政策、
事件、时间和量化事实的直接支撑。

因此内部研究模板升级为 `neutral-industry-report-internal-research v1.1.0`，并在执行摘要
增加 `executive-summary.topic-specific-evidence`：

- `query_strategy=report_topic`，检索 query 仅为已确认 ReportBrief 的标题；
- 使用 keyword 模式和更严格的 `minimum_keyword_score=0.35`；
- 其余五个问题保持 `query_strategy=full_context`，继续使用标题、覆盖期和问题 prompt；
- 老模板未声明 `query_strategy` 时默认 `full_context`，保持向后兼容。

研究模板内容变化会改变 PackSnapshot digest。为遵守 immutable snapshot 合同，
`industry-report` Pack 从 `1.1.1` 升为 `1.2.0`，不覆盖或删除已有 1.1.0/1.1.1 快照。

### M2 报告正文守卫

提示词只作为第一层约束。`report_output_guard.py` 在 DeepAgent 完整运行结果解析后、
WeCom 投递前执行确定性守卫：

1. 仅对非终态、`current_phase=intake` 的 WorkItem 生效；
2. 光秃的“确认/同意/好/OK”等消息不授权任何 M2 行为；
3. 仅以强报告措辞或超过 1200 字符作为正文拦截信号；Markdown 标题/表格和章节标签
   只记录为诊断特征，不单独触发拦截；
4. 命中后不投递原始模型正文，替换为固定 fail-closed 操作提示；
5. 每个 M2 输出写入 `report_output_guard` 企业事件，包含 allowed/blocked、reason、
   work_id、phase、字符/行数、输出 SHA-256、结构特征和顶层工具调用顺序，
   不记录员工原话、模型正文或具体数据；内部 MCP server/tool 仍以 MCP audit 为准。

`get_report_research_gaps` 的无缺口响应同时增加
`report_generation_available=false`，且 `choices=[]` 时明确 M2 未启用写作，模型不得
即兴提供“编写报告”选项。M3/M4 才引入 Evidence、Claim、正文和 DOCX。

### 自动化覆盖

- 研究模板固定为 5 sections / 6 questions，主题问题 query 必须精确等于报告标题；
- 真实低 fused/high semantic 分数仍按既有 component-aware relevance gate 工作；
- 无缺口时 `choices=[]`、`report_generation_available=false`，且 next step 禁止正文；
- 光秃确认、强报告措辞和超长报告会被拦截并产生脱敏审计事件；
- 合法 coverage 表格、多章节标签与四选项会放行，同时留下安全诊断摘要；
- 精确 `确认 ReportBrief vN` 的简短操作结果不被误拦；
- terminal/non-intake WorkItem 不受 M2 守卫影响；
- example 与 cookiecutter 模板保持同构，渲染测试检查新模块存在。
