# v0.1.0 M3 Implementation Log

## M3-00A: WeCom session backpressure

Status: runtime hardening implemented; awaiting final Mac mini live verification.

M3 starts with a runtime admission slice before report outline and draft
generation. It keeps the existing per-session FIFO single-flight worker and
adds explicit backpressure around it.

### Runtime contract

- One active turn per `session_id`.
- At most `AGENTSEEK_WECOM_SESSION_QUEUE_MAXSIZE` pending messages; default 3.
- Different sessions retain coroutine-level concurrency.
- Accepted pending messages record their one-based queue position in structured
  events. Employees can query the current active/pending counts with the queue
  status command; the AI Bot callback protocol does not reliably render
  non-terminal stream updates.
- A message above the pending limit finishes immediately and never reaches the
  agent or model.
- A pending message expires after
  `AGENTSEEK_WECOM_QUEUE_WAIT_TIMEOUT_SECONDS`; default 240 seconds. Expired
  messages are skipped when the worker reaches them.
- `查看消息队列` and `查看排队状态` bypass the model and return active count,
  approximate active age, and pending count.

### Observability

The channel emits redacted structured events:

- `wecom_turn_queued`
- `wecom_turn_started`
- `wecom_turn_queue_rejected`
- `wecom_turn_queue_wait_timeout`
- `wecom_turn_queue_status`

Events contain hashed runtime scope through the enterprise observability layer,
counts, limits, and durations. They do not contain message text, OA account,
employee name, or model output.

### Boundaries

M3-00A does not implement `取消当前处理`, `清空等待消息`, hard preemption of a
blocking LLM call, or forced process exit under load. Those belong to M3-00B.
Long report generation remains a WorkItem concern and must not become a large
chat queue.

### Deterministic acceptance

Automated tests cover:

1. Eight distinct messages remain FIFO and single-flight when the configured
   pending limit permits them.
2. With the default policy, one active plus three pending messages are accepted
   and the next message is rejected.
3. Queue positions are 1, 2, and 3.
4. Queue status bypasses the agent in both busy and idle sessions.
5. A pending message expires without entering the agent and pending count
   returns to zero.
6. Different sessions remain concurrent.

Mac mini live verification should send one slow message followed by four rapid
distinct messages, verify three queued-position events and one user-visible
terminal rejection, query queue status while busy, and confirm that no rejected
or expired message produces a model turn.

### Single-stream product contract

Mac mini verification established that the WeCom AI Bot renders terminal
`finish=true` stream content reliably but does not reliably render intermediate
`finish=false` content. M3-00A therefore keeps the v0.0.9-style single-stream
delivery and does not reintroduce `response_url` for ordinary chat.

The user-facing acceptance contract is now:

1. A normal accepted message eventually receives one terminal answer or one
   terminal timeout/error response.
2. A message above the queue limit receives one terminal rejection, enters no
   Agent turn, and is not duplicated through another delivery channel.
3. `查看消息队列` / `查看排队状态` returns active and pending counts without
   entering the Agent.
4. A queued message that exceeds its TTL receives one terminal cancellation and
   enters no Agent turn.
5. Queue positions remain observable and deterministic, but are not promised as
   unsolicited visible messages. A pre-answer ACK is likewise best-effort only,
   not a release gate.

This is a deliberate protocol/product boundary. Making ACK and every queue
position independently visible would require a second terminal delivery channel
and would restore the ordering, duplication, retry, and exactly-once problems
that the single-stream simplification removed.

### User-facing delivery remediation

Status: delivery simplification implemented after confirming that the dual
callback-stream plus `response_url` lifecycle caused ordering, duplication, and
retry ambiguity; awaiting Mac mini live verification.

- Ordinary text, voice, and immediately processed media turns ignore the callback's
  `response_url`. Accepted messages return `stream.finish=false`, then ACK, queue
  position, processing progress, terminal answer, rejection, and queue TTL all
  remain on that one `stream_id`, matching the proven v0.0.9 interaction model.
- Queue status and capacity rejection finish synchronously on the same stream.
  Duplicate `msgid` callbacks reuse the stream's latest state and never create a
  second turn or consume a second delivery capability.
- `response_url` remains available only for explicitly asynchronous work. A file
  whose extractor returns `pending` completes the callback and reserves its
  one-shot URL for the later extraction/Agent result. The response URL probe is
  retained for deployment diagnostics.
- Response URLs and response codes never enter model context, logs, traces, or
  persistent runtime state.
- Text, voice, and text-only mixed callbacks perform queue admission before
  open-userid conversion. The worker resolves the plaintext userid and updates
  the runtime message immediately before enterprise processing, so the first
  callback no longer waits on the network identity conversion.
- Enterprise identity loading is now an async Bub hook. Blocking DM provider
  calls run outside the event loop with a 15-second outer deadline. Persistent
  DM sidecar requests have an 8-second inner deadline; a timeout force-kills the
  stale JVM (including a stopped process), and the next lookup starts a fresh
  sidecar. Lookup failure records identity status `error` and lets the turn and
  other sessions continue.
- `langchain_model_call` now emits `started` as soon as the LangChain model
  callback begins, followed by `succeeded` or `error`. This fixes the previous
  diagnostic ambiguity where an in-flight provider request looked like a stall
  before the model callback. Events expose timing and size counters without
  retaining prompt or completion text.
- `langchain_run_stage` events record spec resolution, prompt enrichment,
  context construction, and model invocation boundaries. They contain timing
  and size counters only, so pre-model setup stalls can be distinguished from
  runnable/provider stalls without recording prompts or replies.
- OpenAI-compatible model requests have a separate 60-second default deadline
  and zero automatic retries. Provider timeout exceptions become a terminal
  employee-facing timeout response, releasing the session worker before the
  broader 180/195-second turn deadlines.
- The same deadline is attached to the LangGraph `model` node, covering all
  model middleware and request preparation before provider callbacks begin.
  LangGraph `NodeTimeoutError` is normalized to the same terminal timeout
  response, so a pre-provider stall releases the session worker at the inner
  boundary instead of waiting for the 180/195-second outer turn limits.
- Short-term memory prompt injection keeps newest messages first and is bounded
  by `AGENTSEEK_ENTERPRISE_MEMORY_PROMPT_MAX_CHARS` (default 12000) and
  `AGENTSEEK_ENTERPRISE_MEMORY_PROMPT_MAX_MESSAGE_CHARS` (default 3000).
- Code review confirmed that `current_work_context` is already a small ledger
  summary; research questions, templates, and SourceRecord bodies are not
  injected there. Further prompt slimming should use the new model-call metrics
  rather than removing WorkItem capabilities speculatively.

### DeepAgents harness hardening

Mac mini stage timing repeatedly showed a long interval between
`model_invoke started` and `langchain_model_call started`. Local inspection and
benchmarking ruled out rebuilding the compiled runnable and per-turn tool
binding: the runnable is cached at spec load and binding the current tool set is
about 10-11 ms locally.

The enterprise template now registers an OpenAI-provider DeepAgents harness
profile that disables DeepAgents automatic `SummarizationMiddleware`; it can
issue a second summary-model request before the observable primary model
callback, while AgentSeek already supplies bounded, persisted short-term memory
and bounded runtime context.

The default `general-purpose` subagent and `task` tool remain available. They
are optional execution helpers and are not the router between ordinary chat and
formal work; the guarded `create_industry_report_work` path is the durable
WorkItem boundary. Future report compaction must be an explicit, observable
WorkItem operation rather than silently re-enabling conversational
auto-summarization. The model-node deadline also bounds any remaining
pre-provider middleware stall. Mac mini must verify that the previous 44-second
pre-model gap and burst hang disappear or terminate at the configured 60-second
boundary; if a gap remains, `langchain_run_stage` remains the oracle and the
change must not be misreported as a confirmed root-cause fix.

## M3-00A 后续 live 管线诊断（2026-07-16）— 投递/延迟问题，非队列逻辑缺陷

M3-00A 队列治理事件层验证 PASS，但测试期间 + 切快模型后，用户 live 体感"发消息后几十秒无任何反馈"。
深挖收消息→生成→投递全链路（`_dispatch_user_message` / `_wait_for_first_update` / `send` / `make_text_stream`），
发现 4 项与队列逻辑无关、但影响 live 可用性的问题。模型已切 `qwen-flash`（pid 16204，见下）。

### 模型选型（dashscope `AGENTSEEK_API_BASE` 不变）

探针实测（`/v1/chat/completions`，"你好" 简短回复）：

- `qwen-flash` 1.1s，非 reasoning，内容正确 ✅ → 已采用。
- `deepseek-v4-flash`（原配置）reasoning，agent 内单轮 23-34s ❌。
- `qwen3.7-flash` **不存在**（`Model.AccessDenied`）；`qwen3.6-flash`/`qwen3.5-flash`/`qwen3.7-plus` 全是 reasoning（含 `reasoning_content`），4.7-6.6s+ ❌。
- dashscope 上 qwen3.x 全线 reasoning，`qwen-flash` 是唯一快的非 reasoning 聊天模型。

### 发现 1：整 turn 57s，瓶颈是 LLM 单次调用 30s（非模型慢）

`你好`（qwen-flash）turn 拆解：接收建 stream 3s + 同步 DM 身份 5s + memory 3s + pgvector 4s + **LLM 30s** +
guard/save/finish 9s。LLM 30s 是 qwen-flash 单轮、`tool_sequence=[]`（无工具调用）的**一次**调用（探针同模型 1.1s）。
最可能：agent 每 turn 把当前 workitem（`8c669fb4`：v2 brief + 5/6 研究 Q&A + 缺口 + 11 SourceRecord + 研究模板）
全量塞进 system prompt，快模型也要 30s 消化；也可能是 dashscope 大请求排队。
**需 Codex**：(a) 上下文瘦身——聊天 turn 按需懒加载 workitem 研究/源/模板，预期 LLM 30s→3-5s；
(b) 加 LLM 调用耗时 + prompt/completion token 数结构化日志（现在日志完全不含 LLM timing，无法区分 prompt 大 vs endpoint 慢）。

### 发现 2：用户看不到"已收到，正在处理..."即时回执，但 ack 其实发了

`_wait_for_first_update`（`initial_wait_seconds=1.5` 默认）在 1.5s 后返回 `stream(content="已收到，正在处理...", finish=False)`，
`make_text_stream` 包成 stream envelope 返回 WeCom——**ack 机制本身没坏**。但 WeCom 客户端疑似只渲染 `finish=True` 的内容，
`finish=False` 的中间 ack 不显示。M2 期间用户看到的"已收到，正在处理..."其实是 LLM 慢回复正文，非系统 ack。
**需 Codex**：确认 WeCom 对 `finish=False` stream 的渲染行为；若确实不渲染，考虑把 ack 作为独立 `finish=True` 消息先投递、
再异步投递最终回复；或用 `response_url.py` 的 `WeComResponseUrlSender` 先发一条 ack。

### 发现 3：DM 身份解析同步阻塞 callback ~5s

`_dispatch_user_message` 开头 `await self._resolve_userid`（DM JDBC via JPype）阻塞 callback 约 5s，ack 要等身份解析完才返回。
**需 Codex**：身份解析移到 ack 之后异步做（先返 ack，再异步解析身份 + 跑 turn），或命中 `userid_cache_ttl_seconds` 缓存时跳过 DM。

### 发现 4：核实被拒/TTL 路径提示是否真正投递

昨晚 M3-00A 测试（glm-5.2）用户"没收到任何反馈"，原因复合：glm-5.2 单 turn 4-9min、queued 排空极慢、ack 不可见（发现 2）。
另外昨晚对被拒 stream（如 `a3140bd2`）WeCom 持续重传，疑似 rejection 提示未送达、或 WeCom 对未 finish 的 callback 一直重传。
切 qwen-flash + 重启 gateway 后正常 active 路径回复能送达（`你好`/`现在几点`/`你好` 均收到），投递链路本身通。
**需 Codex 核实**：被拒/TTL 路径的 `_finish_message_stream` 是否真的把 `finish=True` 提示送达 WeCom 并让其停止重传。

### 优先级与影响面

发现 1（上下文瘦身 + LLM 可观测）和发现 2（ack 可见性）对用户体感影响最大，优先；发现 3 次之；发现 4 核实即可。
**均不影响 M3-00A 队列治理本身的正确性**（事件层已验证 PASS），但影响 live 可用性。归入 M3-00B 或独立 live-UX 切片。

内部 GLM-5.2-W4A8（`10.99.100.129:30004`）Mac mini 仍网络不可达（traceroute 死在网关 `172.20.199.254`，需网络组打通 `172.20.199.x→10.99.0.0/8`）。

## M3-00A model-start watchdog implementation（2026-07-16）

Mac mini `8c81d21` 复验确认自动摘要关闭有效，但也澄清了三层截止线的覆盖关系：

- `AGENTSEEK_MODEL_REQUEST_TIMEOUT_SECONDS=60` 约束单次 provider 请求；
- LangGraph `model` node 的 `TimeoutPolicy(60)` 只约束该图节点；
- `agentseek-langchain` 插件在图外发出 `model_invoke started`，其整轮
  `AGENTSEEK_LANGCHAIN_RUN_TIMEOUT_SECONDS` 仍为 180 秒，而 WeCom turn 上限为
  195 秒。因此 burst 在首个 provider callback 前卡住时，60 秒配置无法触达，
  180 秒整轮截止线又晚于从 WeCom turn 起算的 195 秒外层截止线。

修复在插件真实执行边界增加独立的首模型回调 watchdog：

1. `AGENTSEEK_LANGCHAIN_MODEL_START_TIMEOUT_SECONDS` 默认 60 秒；未显式配置时兼容
   `AGENTSEEK_MODEL_REQUEST_TIMEOUT_SECONDS`，无需旧部署立即新增变量；
2. `run_model` 和 `run_model_stream` 把 runnable operation 与
   `_ModelCallObservability` 的首个 `on_chat_model_start`/`on_llm_start` 事件竞速；
3. 60 秒内 operation 已正常结束或首个模型调用已开始则继续；否则取消 operation，
   返回统一模型超时提示，并记录 `timeout_phase=model_start`；
4. watchdog 只约束 pre-model 启动阶段。首个模型回调出现后，180 秒整轮上限继续允许
   多工具 WorkItem 执行，provider request 和 graph-node deadline 仍作为内层防线；
5. 流式 pump 在超时或外层取消时一并取消，避免 session worker 残留后台 operation。

本地新增确定性测试覆盖：pre-model 永久挂起在 model-start deadline 结束；流式路径返回
`ok=false` 终态；首个 callback 已出现后不会被较短的 start deadline 误杀；专用环境变量
优先于 provider timeout，缺省时正确回退。`make check-langchain` 为 **26 passed**，ty/Ruff
全绿；Example **77 passed + 1 skipped**，模板渲染 **25 passed**。

## M3-00A callback control-plane isolation implementation（2026-07-16）

Mac mini `44663cb` 的时间线表明，两阶段投递在单聊正确，burst 失败是因为
gateway 事件循环在 ContextSeek 返回后被阻塞 263 秒。同时日志显示 Langfuse OTel
exporter 持续连接未启动的 `localhost:3000`，而当前 `emit_enterprise_event()` 会在调用
线程里直接执行 `client.flush()`。WeCom 重试又会产生更多事件，形成同步 flush 和
callback 重试相互放大的正反馈。

本轮在不修改 DeepAgent 或 MCP 行为的前提下分离控制面与观测输出：

1. 有 `response_url` 的 WeCom 消息在队列准入后立即同步固化 `finish=true` 首包；
   Agent worker 在当前 callback 协程返回前不能抢先执行。普通消息不再为了“快结果”
   等待 0.5 秒；始终先 ACK，最终结果经该消息的 `response_url` 投递一次。
2. 队列状态和拒绝仍 callback-only；排队成功的消息先回队列位置，后续终态使用
   各自 `response_url`。没有 `response_url` 的兼容回调才使用
   `AGENTSEEK_WECOM_INITIAL_WAIT_SECONDS` 和 stream polling。
3. Langfuse 网络调用、span 创建和 `flush()` 移到单一 daemon worker；业务线程只做
   `put_nowait`。队列由 `AGENTSEEK_LANGFUSE_QUEUE_MAXSIZE`（默认 1024）限制，满时丢观测事件
   而不阻塞 WeCom。本地 JSONL 仍同步写入，不受 Langfuse 可用性影响。
4. Langfuse probe 增加有界等待，使命令行验证仍能在退出前确认事件已发送；
   gateway 常驻流量不会等待它。

确定性回归覆盖：Langfuse `flush()` 挂起时业务 emit 在 100ms 内返回；有界队列满时
立即 drop；即时 handler 也只能在 ACK 固化后开始；并发重复 msgid 仍只启动一次
Agent/投递一次终态。Mac mini live oracle 是 burst 中 callback HTTP 不再被 Langfuse 故障拖住，
ACK/位置/拒绝先于 Agent pipeline 可见，且 Langfuse 不可达时不再产生重试风暴。
