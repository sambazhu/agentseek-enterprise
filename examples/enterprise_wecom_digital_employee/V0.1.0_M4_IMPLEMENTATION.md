# v0.1.0 M4 Implementation Record

## M4-00 WeCom outbound protocol freeze

M3 ends at an immutable, approved, content-addressed DOCX Artifact. M4 is the
first milestone allowed to expose that file outside the WorkItem runtime. The
transport contract is frozen before publication or delivery tables are added.

### Verified official protocol boundary

The deployment uses the WeCom AI Bot HTTP callback mode:

- [Receive messages](https://developer.work.weixin.qq.com/document/path/100719)
- [Active replies](https://developer.work.weixin.qq.com/document/path/101138)
- [Template cards](https://developer.work.weixin.qq.com/document/path/101032)
- [AI Bot long connection](https://developer.work.weixin.qq.com/document/path/101463)

The official active-reply documentation, last updated 2026-03-24, states that a
callback `response_url` is usable once and expires after one hour. Its documented
message types are `markdown` and `template_card`; `file` is not supported.

The official long-connection mode supports file replies, proactive messages and
chunked temporary-media upload. It uses BotID plus a dedicated Secret and is
mutually exclusive with callback mode for one AI Bot. The current plugin does not
implement that transport, so enabling it in configuration must fail closed.

The group-robot webhook API at
[message push configuration](https://developer.work.weixin.qq.com/document/path/91770)
does support file upload, but it requires a separate group webhook key and sends
only to that configured group. It is not the current AI Bot `response_url` and is
not an acceptable substitute for employee-scoped delivery.

### v0.1.0 decision

Keep the callback transport that already passed identity, memory, MCP, file
intake, queue and exactly-once response testing. Deliver an Artifact as a
`text_notice` template card whose action opens a short-lived signed HTTPS
download link.

The M4 ledger will distinguish:

1. publication of an immutable current Artifact;
2. exactly-once delivery of the template card to the requester;
3. download attempts and successful downloads, which may retry during the
   signed URL lifetime and are not the same as message delivery.

Tokens, response codes, media IDs, plaintext employee IDs and absolute storage
paths must never enter model context or structured events. The future download
endpoint will resolve only an immutable Artifact ID plus a hashed, expiring,
recipient-bound grant.

### Implemented controls

- `agentseek_wecom.outbound` publishes callback and long-connection capability
  records.
- callback supports only `markdown` and `template_card`; requesting `file`
  raises `UnsupportedWeComOutbound`.
- long connection is documented as file-capable but marked unimplemented.
- `WeComResponseUrlSender.send_template_card` emits the official payload shape
  and retains the existing trusted-host and response-code validation.
- an exact, default-disabled template-card probe consumes one callback
  `response_url` without entering the Agent, enabling a real WeCom UI oracle.
- `WeComSettings` accepts only `AGENTSEEK_WECOM_TRANSPORT_MODE=callback`.
- `scripts/probe_wecom_outbound.py` reports the effective capability without
  printing credentials.
- production preflight rejects `direct_file` in callback mode and validates a
  `signed_link` base URL as HTTPS with no credentials, query or fragment.
- example and cookiecutter configuration default Artifact delivery to
  `disabled`; M4-02 must explicitly enable it after the endpoint and ledger are
  present.
- the deterministic DOCX renderer strips Markdown blockquote markers and
  normalizes unordered and ordered list prefixes before writing Word text.

### M4-00 acceptance

1. callback capability reports only Markdown and template card, one-shot and
   3600-second response URL lifetime;
2. callback `file` request fails closed before network I/O;
3. long connection reports file capability but `implemented=false`;

## M4-01 ReportPublication ledger

M4-01 introduces publication as a durable business fact while leaving every
outbound delivery capability disabled. The checkpoint is:

```text
current confirmed ReportDraft
  + current approved ReportApproval
  + current immutable DOCX ReportArtifact
  + exact requester action: 发布 ReportArtifact vN
  -> immutable ReportPublication
  -> WorkItem.status=published
  -> delivery=not_delivered
```

Publication does not create a template card, signed URL, download grant, PDF or
direct-file message. Those remain M4-02 work.

### Schema revision 10

`enterprise_work_publications` stores one immutable publication record per
Artifact:

- `publication_id` and monotonically increasing `publication_version`;
- tenant/work/Artifact ownership binding;
- Artifact content SHA-256, Draft version, Approval contract version and
  trusted template digest;
- policy ID, authenticated publisher and timezone-aware publication time;
- metadata containing `delivery_status=not_delivered` and PackSnapshot ID.

The database enforces unique `(work_id, publication_version)` and
`(work_id, artifact_id)` bindings. Revision 10 also expands PostgreSQL WorkItem
and WorkEvent status constraints to admit `published`; existing rows and schema
history are retained.

### Atomic repository behavior

`put_publication_record` validates the registered Artifact binding and writes
the Publication, WorkItem transition and `publication_registered` WorkEvent in
one transaction. The first publication advances `draft -> published`. An exact
replay returns the existing publication without incrementing the publication or
WorkItem version and without adding an event. A later current Artifact may
create the next publication version while the WorkItem remains published.

### Server-side publication gate

`publish_report_artifact` accepts only the complete exact action
`发布 ReportArtifact vN`. Before touching the ledger it revalidates:

1. the exact current confirmed Draft version;
2. the current approved Approval and its Draft digest binding;
3. exactly one current DOCX Artifact with matching Draft, Approval and template
   digests;
4. the physical content-addressed file and its SHA-256;
5. the authenticated enterprise actor as the WorkItem requester.

Generic confirmation, request forms such as `请发布`, wrong versions,
negations, questions, stale approvals, missing files and tampered bytes all fail
closed before publication.

### Read model and output guard

The current-work summary exposes Artifact publication state and every
ReportPublication with a computed `current` flag. Any upstream Draft, Outline or
Brief revision makes an older Publication `current=false` without deleting its
history.

`get_current_work_status` and `get_current_report_publications` are the only
read paths for publication prose. The output guard treats publication and
delivery as separate claims:

- an unbacked current publication claim is replaced with
  `unverified_report_publication`;
- a stale publication may be described only as stale;
- any claim that a file/card/link was delivered remains blocked by the Artifact
  delivery guard;
- guard events retain only output digests, never the blocked prose.

### Pack and template

The example and cookiecutter Pack/Profile/report-writing versions advance to
`1.8.0` / `1.7.0` / `1.4.0`. The immutable Skill requires a later exact
publication request, a ledger tool call, and an immediate stop with an explicit
`not_delivered` statement.

### M4-01 acceptance

1. schema revision 10 installs idempotently and preserves revision 9 data;
2. the new publication table, constraints and PostgreSQL published-status
   checks are present;
3. no publication is possible before the exact current Approval and Artifact
   gates pass;
4. exact publication creates publication v1, advances the WorkItem and records
   one event atomically;
5. exact replay returns v1 with no new row, event or WorkItem version;
6. upstream revision makes the old publication non-current without deleting it;
7. forged current/stale publication claims fail closed and remain digest-only;
8. `artifact_ids` remain unchanged and delivery mode remains disabled;
9. no template card, signed link, download endpoint, file send, PDF, delivery
   row or delivery event is created;
10. example/template, static tests, MCP protected files and M3/M3-00A behavior
    remain unchanged.

### M4-01 WeCom publication-command correction

The first Mac mini live pass verified the revision-10 schema, publication
ledger, state transition, idempotency and guard design, but found that the
exact publication action was unreachable from WeCom. The runtime HumanMessage

standard `---Date:...---` separator, then applies the unchanged exact-action
and exact-version `fullmatch` to the remaining employee text. Messages without
that recognized envelope are never stripped. Wrong versions, extra delivery
instructions and user-authored date separators remain fail-closed.

historical or stale Artifact is still the current formal publication version.
Legitimate `current=false` history remains reportable. Focused publication and
guard tests pass (`58 passed`), as do the complete example suite
