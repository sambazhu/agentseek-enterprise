# v0.1.0 规划评审

> 本文评审对象是 `V0.1.0_INDUSTRY_REPORT_DIGITAL_EMPLOYEE_PLAN.md`（commit 88bf45a）。
> 评审基于 v0.0.9 GA（`8128aac4`）的全链路复测结论与本会话在 Mac mini 上积累的活体证据。
> 文末保留 Codex 逐项处置表，记录接受、部分接受和对应修正。

## 总体结论：**合理，架构判断高质量**

这份规划把 `enterprise-wecom` 从"对话+工具调用助手"升级为"组织任务完成型数字员工"，
核心判断都对：

- **以 `WorkItem` 而非对话 session 为中心实体** —— 长任务、跨重启、可审计的基础。正确。
- **`WorkEvent` 不可变事件账本，明确"不能只存在于 Langfuse"** —— 业务审计与模型观测分层。正确。
- **新增 `contrib/agentseek-work` 通用插件，报告业务留模板** —— 复用边界清晰；
  "为什么不放进 agent.py"（channel 可移植、异步 worker、迁移、测试）的理由站得住，
  与 v0.0.9 的 files/enterprise/wecom 分层一脉相承。
- **权限不来自记忆、工具不信模型传入的 requester_id**（来自 runtime context + repository 二次校验）。安全正确。
- **Profile 先于 WorkItem 解析、版本固定、无 Profile 不回退为宽权限 Agent** —— 可复现 + 不越权。正确。
- **确定性检查 vs 模型辅助检查分离，模型检查不替代人工评审** —— 报告可靠性的关键。正确。
- **交互 turn 与异步 worker 分离（lease / 幂等 / 单阶段提交 / 从最后成功阶段恢复）** —— 正确的异步模型。
- **Agent 编排用"确定性状态机 + 受约束模型节点 + 策略保护 MCP + 人工评审"，而非多自治 subagent** —— 对企业报告场景是正确取舍。

M0–M6 里程碑按依赖排序、验收 A–D 覆盖（行业报告 / 内部安全 / 跨重启恢复 / 证据冲突）都到位。
这是一份可以拿去冻结的产品+工程合同级文档。问题不在"设计错"，而在
**几项前置依赖被放到"待确认"而非"M0 阻断"**，且 **MVP 范围偏大、若干恢复/成本/egress 工程细节没画死**。

## 突出优点（保持，不要改坏）

1. 报告合同 `ReportBrief` + 启动条件（模型不能自行补全业务条件）。
2. `Source / Evidence / Claim` 三层可追溯 + 来源优先级 + 低优先级不能独立支撑关键结论。
3. 三审批节点绑定版本（合同 / 提纲 / 终稿），"实质变化需重新批准"。
4. `agentseek-work` vs 报告 Playbook 的协议分离（`WorkPlaybook` 协议由模板实现）。
5. State 是组合边界、非业务库；完整数据始终从 PostgreSQL + `agentseek-files` 按授权读。
6. 质量指标含"重复执行率=0""敏感数据泄露数=0""越权阻断率"——把不可妥协项写成了目标。

## 关键遗漏与风险（按严重度）

### 🔴 M0 必须先解（否则 v0.1.0 无法定验收）

**G1. 企微"自建应用主动消息"是硬依赖，却被列为"建议/待确认 #11"。**
报告任务的核心 UX（waiting_input/review/approval 通知、完成交付）全靠它。规划自己说
降级查询模式"不是目标体验"。但自建应用要企微管理后台配置、callback URL、可能要公网入口 —— 
这是最容易卡壳的一项。应升为 **M0 阻断项**：先确认能否拉通主动消息通道，再谈 Playbook。
拉不通，v0.1.0 只做"任务可创建+查询+跨轮推进"，不做"自动通知+审批流"。

**G2. 公司 Word 报告模板（待确认 #13）是 DOCX 交付的前置条件。**
规划说"DOCX 是必要交付"，但模板没定 → 要么发无品牌通用 DOCX（对战略发展部不算"交付"），
要么用 python-docx 套公司样式（需模板+章节规范+logo+字体）。必须 M0 拿到，否则 M5 交付做不出
真正可用的报告。同时关联 DOCX 生成选型（见 G14）。

**G3. 来源快照（待确认 #9）应从"待确认"升为"必须交付"。**
报告数字员工的全部价值是可追溯。`SourceRecord` 只有 `uri_digest`/`content_hash`，没有
"已存原文快照"。公告/网页 URL 会失效/改版，半年后无法复核 = Claim 失效。对"行业报告"岗位，
**来源原文快照是必须的**。建议 `SourceRecord` 加 `snapshot_artifact_id`（指向 `agentseek-files`
存的原文副本），受限来源一律快照。

### 🟠 设计阶段要补（写代码前定清楚）

**G4. LangGraph checkpoint 与 WorkItem 状态机的"恢复真相源"未定。**
规划说"checkpoint 保存图执行状态，但不能替代企业任务账本"——那崩溃恢复时听谁的？
两个都可能说"phase 4 跑到一半"。必须明确：**`WorkItem` 状态机是唯一真相源**，
checkpoint 只做 phase 内部的 step 级续跑；恢复时先按 `WorkItem.current_phase` + 最后成功
`WorkEvent` 定位，再让 checkpoint 接续 step。否则"从最后成功阶段恢复"会歧义，且可能与
"已批准版本仍能准确识别"（验收 C）冲突。

**G5. `work_id` 贯穿 Langfuse 依赖一个未修的 v0.0.9 缺口。**
v0.0.9 已确认：runtime trace 顶层 `release=None`（`_LangfuseEmitter` 运行时路径没调
`update_current_trace`，见 `observability.py`）。规划说 work_id 要贯穿 Langfuse —— 但同一
emitter 缺口会让 runtime trace 顶层也拿不到 `work_id`（只进 metadata）。要么 v0.1.0 先修
emitter（运行时路径补 `update_current_trace(release=…, work_id=…)`），要么明确"work_id 在
Langfuse 只在 metadata"。建议合并到一处修，并把这条加进 M0/M1 的 emitter 修复项。

**G6. 模型/Token 成本边界完全没提。**
一个 WorkItem 跑 10 阶段，每阶段可能多次模型调用 + pgvector 召回（v0.0.9 实测单次语义召回
~27–53s）。没有：每阶段/每 WorkItem 的最大调用数、token 上限、超时、成本帽。既影响 worker
lease 大小，也影响"报告卡住烧钱"。至少给每阶段一个 `max_model_calls` + `max_tokens` +
`phase_timeout`，触发即转 `waiting_input` 或 `failed`。

**G7. 单实例 Mac mini 的并发模型未定。**
lease/optimistic version 都是标准件，但没说：几个 worker？Mac mini 单实例是 1 worker 串行？
若某 WorkItem 的 phase 在等 MinerU（v0.0.9 实测可几分钟到 ~15min），其他 queued 任务是否饿死？
需明确单实例下：phase 级让出（等 MinerU 时释放 lease、让其他任务插队）还是任务级串行。直接影响
"任务完成率"指标和用户体验。

**G8. 保密数据外发缺少确定性卡点（enforcement point）。**
规划列了"能否发送到外部大模型/MinerU"分级 + "每次外部调用记录"，但记录是事后。要达到
"敏感数据泄露数=0"这个**已声明指标**，必须在报告 Playbook 的工具层、调外部 provider 之前有一个
**硬 egress 策略检查**（按 file 的 `confidentiality_level` + 目标 provider 白名单），不通过直接拒绝，
不靠模型自觉。这条线没画出来，"零泄露"就是个愿望。

### 🟡 范围风险

**G9. v0.1.0 MVP 偏大，建议拆分发布。**
"必须交付"16 项：WorkItem/WorkEvent/PG schema/状态机/幂等恢复取消/ReportBrief/完整 10 阶段
Playbook/Source-Evidence-Claim/提纲评审+最终批准/跨重启恢复/Markdown+DOCX/outbound/企微查询/
主动通知或降级/work_id 贯穿/管理员运维查询。M1→M6 串行，现实里 3–6 个月。建议拆成两到三个 GA：
- **v0.1.0**：M1+M2+M5 轻量版 —— 任务账本 + ReportBrief + 材料绑定 + 跨重启恢复 + Markdown 交付 +
  企微查询（"可委派、可追踪、可恢复"的最小闭环）。
- **v0.1.1**：M3+M4 —— 研究/证据/Claim/提纲评审/初稿/质量门。
- **v0.1.2**：完整 DOCX + 主动通知 + 最终批准 + 审计闭环。

否则 v0.1.0 GA 太远，期间 v0.0.9 在生产跑着没有任何任务治理层。

### 🟢 细节遗漏（不阻塞，建议补）

**G10. 运维（operator）工具缺位。** 工具列表（create/get/list/cancel/provide_input/approve）
都是委派人视角。运维的"人工接管"动作（force_fail / requeue / force_transition / 查看 WorkEvent）
没进 tools，但"人工接管率"是声明指标。补一组 admin tools。

**G11. 证据冲突（验收 D）没有数据结构。** `Claim.verification_status` 没有 `conflicted` 态 +
冲突记录实体。验收 D 要"不静默选择" → 需要一个 `EvidenceConflict` 或 Claim 上的冲突标记 + 解决记录，
否则验收 D 落不了地。

**G12. "实质变化需重新批准"无阈值。** 每次修订都新版本；什么算"实质变化"（结构改 vs 错别字）？
不定规则 → 要么每版都重新批准（慢），要么都不批（险）。给个判定：如章节/关键 Claim 变化→重批；
措辞→不批。

**G13. v0.0.9 已知项的承接没写明。** 规划说"不重写 v0.0.9 能力"，但几个 v0.0.9 遗留应在 v0.1.0
显式承接/修复：
- MinerU 慢/不稳定 → worker 的 `phase_timeout` 要按 MinerU 变速设计（已知会卡 ~15min）。
- pptx 图形化数值 OCR 不出 → 报告里图表数字会过不了确定性校验，要有"标记为不可校验、要求人工
  提供源数字"的兜底。
- CurrentFiles 异步刷新 → WorkItem 绑定 file_id 后，材料盘点要能"等文件解析完再取证据"
  （worker 主动等，而不是让用户 ask again —— 这正好把 v0.0.9 的 ask-again UX 升级掉，值得在
  规划里点一句）。

**G14. DOCX 生成技术没选型。** python-docx（库、无 shell、好做）vs LibreOffice headless/pandoc
（要装、要 sandbox allowlist）—— 影响 sandbox 设计和公司模板能否套。M5 前要定，且与 G2 联动。

**G15. v0.1.0 自身的回滚没写。** v0.0.9 有 v0.0.8-ga 回滚 tag。v0.1.0 是加表+加插件+改 agent.py，
回滚 = production 退回 v0.0.9-ga（新表留着不用、新插件不注册）—— 建议在 `PRODUCTION_FREEZE.md`
写明 v0.1.0 回滚路径，延续 GA-readiness 纪律。

**G16. 跨重启恢复的"故障注入"测试 harness 没写。** M6 列了"故障恢复演练"但没说怎么做。v0.0.9
没有持久任务、不需要这个；v0.1.0 必须有：worker 跑到 phase 中途被 kill → 重启 → 断言不重复执行、
MCP 写不重复、从正确 phase 恢复。加进测试分层。

**G17. 评审意见的企微录入 UX（待确认 #15）可能阻塞修订流。** 在企微对话里"指到某章节、写一条评审
意见"很别扭。`ReviewComment` 数据结构有了，但录入路径（企微文本 vs Word 批注导入）不定，提纲评审+
修订就做不顺。M0 一起定。与 G1 联动（都依赖企微通道能力）。

## 建议（优先级排序）

1. **M0 先冻结**：自建应用主动消息可行性（G1）、公司 Word 模板（G2）、来源快照升级为必须（G3）、
   评审意见录入 UX（G17）。四项不定，后面都悬。
2. **M1 前补设计**：checkpoint vs WorkItem 真相源（G4）、模型/token 边界（G6）、并发模型（G7）、
   egress 硬卡点（G8）、emitter 修 release+work_id（G5）。
3. **考虑拆 v0.1.0 为两到三个 GA**（G9），让"任务账本+可恢复+Markdown 交付"先上线，避免大爆炸。
4. **把 v0.0.9 已知项（MinerU 延迟/图表数值/异步刷新）显式写进 v0.1.0 承接清单**（G13）——
   尤其是"worker 等文件解析完再取证据"，顺手干掉 ask-again UX。
5. 补运维工具（G10）、冲突数据结构（G11）、重批阈值（G12）、DOCX 选型（G14）、回滚路径（G15）、
   chaos harness（G16）。

## 一句话结论

**架构判断对、分层干净、可审计性是真正的设计目标，不是口号。** 主要问题不在"设计错"，而在
**几项前置依赖（自建应用主动消息 / Word 模板 / 来源快照）被放到"待确认"而非"M0 阻断"**，
且 **MVP 范围偏大、若干恢复/成本/egress 的工程细节没画死**。把这五项前置和工程细节在 M0/M1 钉死，
这份规划就能落地。
