# v0.1.1 部门数字员工与 Multi-Playbook 方案

> **概要：** v0.1.1 将已经验证的证券行业报告 Bot 演进为一名部门数字员工。
> 它具备版本化岗位说明、可发现的服务目录和多个受治理 Playbook，同时保留
> v0.1.0 全部账本合同。本版本不建设多数字员工统一路由网关。

## 一、背景

v0.1.0 已经跑通一条完整的企业任务链路：

```text
企微员工
-> 证券报告 WorkItem
-> ReportBrief
-> 内部研究与缺口决策
-> ReportOutline
-> Evidence 支撑的 ReportDraft
-> ReportApproval
-> DOCX ReportArtifact
-> ReportPublication
-> signed-link ReportDelivery
```

这条链路具备持久化、版本化、审计、fail-closed 和企微活体验证能力。
但当前产品边界仍是一个企微 Bot、一个 DigitalEmployeeProfile、一个启用 Playbook。

部门员工下一步需要的不只是更多报告工具。他们需要清楚知道：

- 这名数字员工是谁；
- 它属于哪个部门；
- 它能提供哪些服务；
- 一项请求会进入哪个正式流程；
- 哪些行为受权限、审批和合规边界约束。

因此，v0.1.1 采用以下产品模型：

```text
一个独立企微 Bot
-> 一名部门数字员工
   -> 一份 Job Charter
   -> 一个部门知识边界
   -> 多个可复用 Skill
   -> 多个受治理 Playbook
```

这比“一个 Gateway 隐藏多名数字员工”更简单。未来可以增加统一服务台，在多个
独立 Bot 之间做能力发现，但这不是 v0.1.1 的前置条件。

## 二、核心决策

### 2.1 一个 Bot 代表一名部门数字员工

Bot 对员工呈现一个稳定身份。Playbook 是这名数字员工执行的正式工作流程，
不是隐藏在同一 Bot 后面的另一名数字员工。

首个部门身份如下：

| 字段 | 值 |
| --- | --- |
| 归属部门 | 战略发展部 |
| 展示名称 | 战略发展部数字员工 |
| 数字员工编号 | `DE-SD-001` |
| 使命 | 基于授权知识、可审计证据和人工检查点完成战略研究与正式材料工作 |

数字员工编号用于展示、组织治理和审计，不是人类 OA 账号、身份凭据或授权依据。

### 2.2 v0.1.0 技术身份保持不变

v0.1.1 保留：

```yaml
digital_employee_id: industry-report
```

该 ID 已写入 WorkItem、PackSnapshot、事件和并发隔离键。如果直接改成
`strategic-development`，现有活动任务将无法被当前查询路径发现，除非同时引入
覆盖全部账本读取路径的身份迁移和别名机制。

v0.1.1 只新增面向员工的身份字段：

```yaml
digital_employee_id: industry-report
employee_code: DE-SD-001
display_name: 战略发展部数字员工
identity_scope: department
```

历史技术 ID 语义偏窄，但在本版本中视为不可变内部标识。未来只有在具备正式账本
兼容合同后，才允许迁移新的部门级技术 ID。

### 2.3 Skill 与 Playbook 保持分离

**Skill** 是可复用的方法或有边界的原子能力，例如文件分析、知识检索、证据整理、
需求受理和文档渲染。
文件、知识和 MCP 数据工具也归属数字员工的 Profile 级共享能力池。它们不再人为分为
“普通对话专用”或“Playbook 专用”：普通协助和正式服务都可以使用。

**Playbook** 是有状态、版本化、可审计的正式业务流程。它拥有 WorkItem 生命周期、
业务合同、人工检查点、Policy 和交付物。

一个 Playbook 可以组合多个 Skill 和共享能力。它不是另一套能力系统，而是在同一能力池上
增加 WorkItem、合同、状态机、人工检查点、审批和审计。Skill 和 MCP 能力本身不能伪造
这些正式业务事实，也不能替代审批门。

现有证券报告继续作为第一个生产 Playbook：

```text
securities-industry-report@1
```

v0.1.1 使用测试型第二 Playbook 验证 Registry 和隔离能力。在业务负责人、Policy、
输入、输出和验收口径冻结前，不对外宣称第二个正式部门流程已经上线。

### 2.4 路由选择 Playbook，不选择另一名数字员工

Bot 内路由按以下优先级执行：

1. 精确的当前 WorkItem 或合同命令，回到其绑定 Playbook；
2. 员工显式选择的服务或 Playbook；
3. 新请求唯一命中的确定性触发规则；
4. 没有候选或存在多个候选时，向员工澄清。

v0.1.1 不把 LLM 分类器作为默认路由器。模型不能发明 Playbook ID、静默选择
歧义流程，也不能把分类置信度当成授权。

首版路由结果合同：

```yaml
route_status: selected | clarification_required | out_of_scope | forbidden
digital_employee_id: industry-report
playbook_ref: securities-industry-report@1
reason_code: active_work | exact_action | explicit_service | deterministic_match
candidate_playbook_refs: []
profile_version: 1.10.0
pack_snapshot_id: pack_snapshot_sha256_...
```

路由事件只记录标识和摘要，不记录员工原文、OA 账号、姓名、凭据或完整 Prompt。

### 2.5 Profile 是统一能力与权限边界

部门 Profile 声明数字员工共享的 Skills、文件、知识库、MCP 工具、数据范围和出站模式。
这些声明同时是运行时能力上限：

```text
有效能力
= Profile 权限
   ∩ 当前部署中已配置的能力
   ∩ 员工授权
   ∩ 当前 Policy 决策
```

Playbook Manifest 中保留的 Skill、tool grant 和 data scope 字段用于依赖声明、兼容性校验和
治理文档，不再用来建立第二套能力池。当 Playbook 引用了 Profile 未声明的 Skill、Asset、
KnowledgeRef、tool grant 或 data scope 时，Loader 仍必须 fail-closed。

### 2.6 关键用户引导由服务端确定性生成

以下响应从版本化 Profile 和服务目录生成，不由模型临场发挥：

- `你是谁`
- `你能做什么`
- `怎么使用你`
- `有哪些服务`
- 歧义 Playbook 的选择提示
- 进入某个 Playbook 时的第一步指引

`我是谁` 继续查询经过认证的人类员工身份；`你是谁` 介绍数字员工。两者不能共用
同一响应路径。

默认自我介绍保持简洁：

```text
我是战略发展部数字员工，编号 DE-SD-001。
我可以协助完成证券行业研究与正式报告，并按需求确认、内部研究、
提纲、初稿、审批、渲染、发布和交付的可审计流程推进。
关键版本需要你明确确认，外部检索不会自动启用。
你可以从“请帮我编写一份关于……的证券行业报告”开始。
```

只有在员工请求帮助或启动正式任务时，才展示完整工作过程。普通回答不重复岗位介绍。

## 三、Profile v2 草案

Loader 同时接受 Profile v1 和 v2。旧 Profile 缺少新字段时使用兼容默认值。

```yaml
profile_schema_version: 2
digital_employee_id: industry-report
employee_code: DE-SD-001
name: 行业报告编写数字员工
display_name: 战略发展部数字员工
identity_scope: department
tenant_id: strategic-development
owning_org: 战略发展部
job_role: 战略研究与正式材料编制
mission: 基于授权知识、可审计证据和人工检查点完成战略研究与正式材料工作

responsibilities:
  - 行业资料收集和证据整理
  - 行业趋势及竞争格局分析
  - 公司专题材料编写
  - 报告版本修改和质量检查
  - 研究底稿与引用归档

service_catalog:
  - service_id: securities-report
    title: 证券行业正式报告
    summary: 形成可研究、评审、批准、发布和交付的正式 DOCX 报告
    playbook_ref: securities-industry-report@1
    workflow_steps:
      - 需求澄清与 ReportBrief 确认
      - 内部研究与缺口决策
      - 提纲、初稿与内容审批
      - DOCX 渲染、发布与交付
    example_requests:
      - 请帮我编写一份证券行业数字化转型报告
      - 研究利率变化对证券行业的影响并形成正式报告

behavior_policy_refs:
  - industry-report-v1
```

约束：

- `digital_employee_id` 是持久技术主键；
- `employee_code` 在租户数字员工目录中唯一；
- 员工界面优先展示 `display_name`；
- `service_catalog.playbook_ref` 必须属于 `supported_playbooks`；
- example requests 是路由测试样例，不是模型指令；
- 行为 Policy 必须指向 Pack 已声明的 Policy；
- Profile 内容变化必须升级版本并生成新的不可变 PackSnapshot。

## 四、Playbook Manifest 草案

现有 Pack schema v1 已支持 Playbook 列表。M2 在每个 Playbook 条目增加权限子集声明；
M3 再冻结并实现确定性路由元数据。无需仅为 Registry 改变 Pack schema 版本：

```yaml
playbooks:
  - id: securities-industry-report
    version: "1"
    entrypoint: enterprise_wecom_digital_employee.reports.playbook:build_playbook
    skill_refs:
      - report-intake@1.1.0
      - report-writing@1.5.3
    policy_refs:
      - industry-report-v1
    tool_grants:
      - analyze_file
      - department-knowledge-read
      - gildata-read
    data_scopes:
      - requester-authorized-files
      - strategic-development-department-knowledge
      - gildata-licensed-data
      - authorized-public-sources
    routing:
      explicit_aliases:
        - 证券行业正式报告
        - 证券报告
      intent_terms:
        - 证券行业报告
        - 对证券行业的影响
      owned_command_terms:
        - reportbrief
        - reportartifact
        - 报告任务状态
      priority: 100
```

实现修改不可变内容时再确定 Pack/Profile 的实际版本号。禁止修改内容却复用已发布版本。

## 五、运行时架构

### 5.1 当前限制

当前 Profile 数据类型已经使用 Skill 和 Playbook 列表，Pack Loader 也能读取多个
PlaybookSpec。但是运行时调用 `_single_playbook_ref()`，明确拒绝
`supported_playbooks` 数量不等于一的 Profile。

当前 `IndustryReportWorkComposition` 还直接拥有报告专用方法、工具、Prompt、Output
Guard、Asset 和 Delivery 初始化。因此增加第二个正式 Playbook 不是只修改 YAML。

### 5.2 目标组合结构

v0.1.1 在现有 Playbook Binding 外增加部门级组合层：

```text
DepartmentDigitalEmployeeComposition
  |- DigitalEmployeeJobCharter
  |- ServiceCatalog
  |- PlaybookRegistry
  |    |- securities-industry-report@1 -> 现有报告 Composition Adapter
  |    `- test-only second Playbook      -> 兼容性测试夹具
  |- PlaybookRouter
  `- CurrentWorkResolver
```

现有报告生命周期继续保留在当前模块，只适配一个小型公共协议，不进行重写。

```python
class PlaybookBinding(Protocol):
    playbook_id: str
    playbook_version: str

    def enrich_state(self, message, session_id, state) -> None: ...
    def tools(self) -> Sequence[object]: ...
    def current_work(self, state, runtime_context=None) -> WorkItem | None: ...
    def introduction(self) -> str: ...
```

公共协议保持最小。ReportBrief、Evidence、Draft、Artifact 和 Delivery 继续属于报告
Composition 的内部能力。

### 5.3 工具可见性

运行时建立一个 Profile 级 `CapabilityRegistry`，普通 DirectTurn 和所有 Playbook 共用同一份
文件、知识与 MCP 能力快照。未配置或未被 Profile 授权的能力不会暴露给模型。

请求尚未绑定时，数字员工可以在普通对话中使用这些共享能力。完成路由后，选中的
Playbook 仍使用同一底层能力提供者，但通过其版本化工作流工具调用，以登记证据、员工授权和审批事实。
各 Playbook 的 WorkItem、合同、状态变更、审批和交付工具仍彼此隔离，不向模型暴露全部 Playbook
专属工具的并集。

工具可见性不能代替服务端授权。每个动作工具仍需验证 Profile、Playbook、员工、
WorkItem、版本和 Policy。

### 5.4 Work 与会话边界

企微 Callback 队列继续按员工 Chat 隔离，保持突发消息背压和串行处理。

业务上下文进一步分层：

```text
对话记忆：tenant + human employee + digital employee
正式任务：tenant + human employee + digital employee + playbook
合同状态：tenant + work_id + contract type + version
```

M1-06 已经限制每个 tenant/requester/digital-employee/playbook 最多一个非终态
WorkItem。多 Playbook 后，同一员工可以在不同 Playbook 中各有一个活动任务。

活动任务路由规则：

- 精确合同或 Artifact 命令解析到其所属 WorkItem；
- 只有一个明确活动任务时，可接收普通继续请求；
- 多个活动任务遇到歧义的“继续”时必须澄清；
- 运行时不能把所有活动 WorkItem 同时注入一个模型 Prompt。

## 六、行为与 Policy

行为约束分四层：

1. **Job Charter**：使命、职责、服务和边界；
2. **Policy**：授权、审批、数据和出站规则；
3. **Tool 与状态机**：版本、确认、幂等和状态迁移；
4. **Output Guard**：阻止无账本依据的保存、批准、发布和交付声明。

Prompt 只承担行为引导，不是唯一 Policy。内部知识优先、外部检索显式选择、审批后
渲染、发布后交付等规则继续由服务和账本执行。

| 层级 | 规则示例 |
| --- | --- |
| 部门数字员工 | 身份处理、保密、禁止暴露凭据 |
| Playbook | 研究范围、确认门、审批和交付条件 |
| Tool | 参数校验、权限、幂等和审计 |

## 七、兼容合同

v0.1.1 必须保留以下 v0.1.0 事实：

- schema revision 11 和全部历史数据可读取；
- 不增加直接 DELETE 或手工 status UPDATE；
- `digital_employee_id=industry-report` 继续可解析；
- `securities-industry-report@1` 保持 WorkItem 身份不变；
- 旧 PackSnapshot 不可变且可访问；
- 活动和已交付报告可以继续查询、修订和交付；
- ReportBrief 到 ReportDelivery 的 payload 语义不变；
- M1-06 活动任务行为不变；
- MCP 受保护 Policy 和确认回退不变；
- Callback 队列、response_url、signed-link 和 exactly-once 行为不变。

Profile v1 兼容规则：

- 缺少 `profile_schema_version` 视为 v1；
- 缺少展示身份时回退到 `name` 和 `digital_employee_id`；
- 一个 Playbook 的 v1 Profile 保持 v0.1.0 行为；
- 多 Playbook 必须使用 Profile v2，并为每个 Playbook 显式声明权限和路由元数据。

Playbook Registry 本身不要求数据库迁移，因为 WorkItem 已保存 Playbook ID 和版本。
只有实现新增了现有事件元数据无法表达的持久路由或目录记录，才允许升级 schema。

## 八、里程碑

### M0：合同冻结

- 冻结本方案和术语；
- 定义 Profile v2 与 Pack Playbook 权限声明合同；Pack schema 仍保持 v1；
- 冻结技术 ID 兼容策略；
- 定义路由结果和事件元数据；
- 在运行时修改前建立验收 Oracle。

退出条件：团队确认字段归属、路由优先级、权限求交和 GA 兼容边界。

### M1：Job Charter 与确定性服务发现

- 同时加载 v1 和 v2 Profile；
- 确定性渲染“你是谁”“你能做什么”“怎么使用你”和服务目录；
- 区分人类员工“我是谁”和数字员工“你是谁”；
- 加入部门级行为 Policy 引用；
- 生产环境仍只启用一个 Playbook。

退出条件：自我介绍不调用模型，内容版本化、简洁且不显示未授权服务。

### M2：Playbook Registry 基础

- 用 Registry 替换 `_single_playbook_ref()`；
- 将现有报告 Composition 适配为 `PlaybookBinding`；
- 尽量保持单 Playbook 行为不变；
- 校验 Playbook 权限是 Profile 权限子集；
- 报告工具和 Output Guard 只属于报告 Binding。

退出条件：现有报告 Playbook 经过 Registry 后通过 v0.1.0 全量回归，账本和协议无变化。

### M3：确定性内部路由

- 把活动 WorkItem 命令路由到所属 Playbook；
- 支持显式服务别名和唯一确定性 Intent；
- 对正式流程请求的零候选或多候选返回澄清，普通无候选消息保留 DirectTurn；
- 增加测试型第二 Playbook；
- 验证工具、上下文和活动任务不跨 Playbook。

退出条件：双 Playbook 测试夹具在没有 LLM 分类器的情况下通过路由、隔离、授权和歧义测试。

### M4：发布加固

- 建立 Profile 级统一 Capability Registry，供 DirectTurn 和 Playbook 共享；
- 确保 Playbook 只增加 WorkItem、合同、状态机、审批和审计，不复制 Skills/MCP 能力池；
- 在干净数据库和现有账本上执行兼容测试；
- 执行证券报告完整生命周期；
- 验证队列、身份、记忆、文件、MCP、观测和下载边界；
- 完成 Mac mini 企微活体验证；
- 确认 v0.1.0 零回归后发布 v0.1.1。

## 九、验收 Oracle

### 9.1 身份与服务发现

- `你是谁` 返回部门展示名、数字员工编号、使命和边界；
- `你能做什么` 只列出已授权服务；
- `怎么使用你` 为每个服务给出一个简短入口示例；
- `我是谁` 继续走认证人类员工身份；
- 身份响应不包含明文 OA、凭据、宿主路径或隐藏工具名。

### 9.2 Registry 与路由

- 旧单 Playbook Profile 加载行为不变；
- v2 多 Playbook Profile 加载全部声明 Binding；
- 未声明或重复引用 fail-closed；
- 精确当前任务命令始终选择绑定 Playbook；
- 显式服务别名唯一选择一个 Playbook；
- 歧义请求返回候选列表且不创建 WorkItem；
- 路由不扩大工具或数据权限；
- 路由事件只含哈希和 ID，不含员工原文。

### 9.3 隔离

- Playbook A 不能调用 Playbook B 的工具；
- Playbook A 不能读取 Playbook B 的当前任务上下文；
- 每个 Playbook 的一个活动 WorkItem 约束继续生效；
- 多个活动 Playbook 遇到普通“继续”时不能静默选择；
- 部门对话记忆不能证明 Playbook 动作或授权已经完成。

### 9.4 v0.1.0 回归

- 报告完整生命周期继续可用；
- 精确版本门、幂等重放、stale 和 Guard 保持不变；
- 不产生 PackSnapshot immutable conflict；
- 不产生 Callback 重试风暴、重复 response_url 投递或下载回归；
- MCP 受保护文件保持既有基线零差异；
- 0 SIGBUS、Traceback、IntegrityError、真实 HTTP non-200、PII、密钥和宿主路径泄漏。

## 十、不在 v0.1.1 范围内

- 一个 Gateway 路由多名数字员工；
- LLM-first 意图分类器；
- 部门 Bot 之间自动委派；
- 未经单独业务设计评审的第二个生产 Playbook；
- Artifact 下载浏览器 SSO；
- PDF、PPTX、XLSX 或企微 direct-file；
- 修改 v0.1.0 报告账本或绕过已有检查点；
- 重命名或删除历史 `industry-report` 技术身份；
- 放宽 M1-06 delivered Work 占用 Scope 的既有行为。

## 十一、设计结果

部门数字员工获得稳定身份和清晰服务面，同时不会变成无边界的通用 Agent。新增流程可以
复用企业身份、文件、知识、记忆、WorkItem、审计和交付底座，并保持自己的 Policy 和合同。

这套设计同时建立一条明确边界：增加 Skill 可以较轻量，增加 Playbook 必须经过业务设计和
治理评审。这样一个部门 Bot 可以持续扩展，但不会把 Prompt 和工具 Schema 堆成无法审计的
能力集合。
