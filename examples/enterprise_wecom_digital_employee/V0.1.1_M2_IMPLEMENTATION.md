# v0.1.1 M2 Playbook Registry 实现与验收

## 一、切片目标

M2 在不改变 v0.1.0 报告账本和企微协议的前提下，把原来直接绑定在 Agent 上的
证券报告流程适配为一个版本化 `PlaybookBinding`，并由部门级 `PlaybookRegistry`
统一加载和委派。

本切片只启用一个生产 Playbook：

```text
securities-industry-report@1
```

多 Playbook 的确定性路由和第二个测试 Playbook 属于 M3。M2 允许 Registry 保存多个
Binding，但没有选择结果时禁止调用任何一个 Binding，避免隐式选择第一个流程。

## 二、实现合同

### 2.1 Registry

`PlaybookRegistry` 负责：

- 按版本化 `playbook_ref` 登记 Binding；
- 校验 Binding 集合与 Profile `supported_playbooks` 完全一致；
- 拒绝重复、缺失和额外 Binding；
- 委派消息状态、状态增强、工具、输出守卫、当前任务和服务介绍；
- 单 Playbook 阶段返回唯一活动 Binding；
- 多 Playbook 阶段在 M3 路由选择前 fail-closed。

动态入口只允许从模板自身 Python package 加载，Pack 不能导入任意外部模块。

### 2.2 权限边界

Pack 中每个 Playbook 显式声明：

- `skill_refs`；
- `policy_refs`；
- `tool_grants`；
- `data_scopes`。

每组声明必须是 Profile 对应权限的子集，并且 Skill 和 Policy 还必须由 Pack 声明。
Profile v2 缺少任一 Playbook 权限字段时加载失败。Profile v1 可以缺少这些字段，
Loader 会继承原 Profile/Pack 上限，保持 v0.1.0 单 Playbook 兼容。
显式空 `policy_refs`、`tool_grants` 或 `data_scopes` 是合法的最小权限子集。

研究模板是报告 Playbook 的可选扩展元数据，不是通用 `PlaybookSpec` 的必填字段。
证券报告 Binding 会单独要求它存在，并校验模板所属 Skill 已被该 Playbook 声明。

有效权限仍由运行时继续求交：

```text
Profile 上限 ∩ Playbook 声明 ∩ 员工授权 ∩ 当前 Policy
```

M2 没有修改 MCP Policy、确认回退或服务端动作工具的既有授权校验。

### 2.3 报告 Binding

`IndustryReportPlaybookBinding` 封装现有 `IndustryReportWorkComposition`，拥有：

- 报告消息状态和 WorkItem 上下文；
- 报告专用工具集合；
- 报告账本真实性 Output Guard；
- 当前报告任务查询；
- 服务目录介绍。

Agent 不再直接导入报告工具和报告 Guard，而是只从 Registry 的活动 Binding 获取。
原 `get_work_composition()` 保留为兼容 API，报告生命周期实现没有重写。

### 2.4 WorkItem 绑定

创建 WorkItem 时使用已选择 Playbook 的：

- `playbook_id` 和 `playbook_version`；
- Skill digest 子集；
- Profile 与 Playbook 权限摘要。

`digital_employee_id=industry-report`、Playbook `securities-industry-report@1`、活动任务
并发键和历史 WorkItem 查询语义均不变。

## 三、版本与迁移

| 项目 | M2 值 |
| --- | --- |
| Pack | `1.11.0` |
| Profile | `1.10.0` |
| Pack schema | `1` |
| Profile schema | `2`，兼容 `1` |
| Work schema | revision `11`，无迁移 |
| 生产 Playbook | `securities-industry-report@1` |

Pack/Profile 升版是因为不可变 Pack 内容和权限摘要发生变化。旧 PackSnapshot 必须保留。

## 四、M2 不做

- 不增加第二个生产 Playbook；
- 不做 LLM-first 意图分类；
- 不实现活动 WorkItem、显式服务和确定性规则路由；
- 不改变 ReportBrief 到 ReportDelivery 的合同；
- 不改变 schema revision 11；
- 不改变 MCP 受保护文件；
- 不释放 delivered Work 对 M1-06 scope 的既有占用。

## 五、Mac mini 验收 Oracle

### 5.1 静态与 Pack

- example、Work、Enterprise、WeCom、Files、LangChain、模板、ty、ruff、docs 全绿；
- Pack `1.11.0` / Profile `1.10.0` 注册新 PackSnapshot；
- 旧 `1.10.0` PackSnapshot 保留，零 immutable conflict；
- schema 仍为 revision 11；
- MCP protected files 相对 GA 与 `68d7b25` 均 zero-diff。

### 5.2 Registry 与权限

- Profile v2 的单生产 Playbook 成功注册；
- Binding 提供现有报告工具、Guard、当前任务和服务介绍；
- Profile v1 继承兼容探针通过；
- skill、policy、tool、data scope 任一越界都 fail-closed；
- 构造多 Binding Registry 可以登记和查询，但未选择时执行必须失败。

### 5.3 企微活体

1. `你是谁`、`你能做什么`、`怎么使用你` 继续走 M1 确定性路径，零模型调用；
2. `我是谁` 继续返回认证人类员工身份；
3. `查看当前报告任务状态` 命中原 `work_ed04971`，不创建新 WorkItem；
4. 走一次现有报告动作或精确状态命令，确认报告工具经 Registry 可达；
5. 确认 ReportBrief、Outline、Draft、Approval、Artifact、Publication、Delivery 历史仍可读；
6. 不发生工具全集泄漏、跨 Playbook 上下文或新路由事件。

### 5.4 健康与安全

- 零 SIGBUS、Traceback、IntegrityError、PackSnapshot conflict 和真实 HTTP non-200；
- 队列、去重、response_url 和 signed-link 下载不回归；
- 事件与 MCP audit 分离；
- 不记录员工原文、明文 OA、姓名、凭据、Prompt 或宿主路径。

## 六、退出条件

M2 只有在 Mac mini 确认现有证券报告 Playbook 经 Registry 后保持完整兼容，且新
PackSnapshot、权限子集和 Profile v1 兼容均通过后关闭。关闭后进入 M3：确定性内部
路由和测试型第二 Playbook。
