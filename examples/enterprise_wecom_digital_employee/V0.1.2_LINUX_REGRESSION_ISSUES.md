## P1 应修复

### 1. 大表分析超时链（C5-10 FAIL）
- 现象：5000 行 xlsx（135KB）→ MinerU 抽取物 **610KB**；用户问"总金额/失败笔数"→
  analyze_file 调用数 **0**（模型直吞注入内容）→ agent 循环反复序列化大 context
  （Pydantic 序列化警告刷屏）→ **LangChain 流超时 300s** 终态（08:04:43 问、08:09:44 超时）。
- 三个子问题：
  a) CurrentFiles 注入的每文件截断上限未兜住 610KB（或上限过大），违背 v0.0.9
     "bounded model context" 设计意图；
  b) 大表场景未强制走 analyze_file 工具（v0.0.9 设计的大文件通道），模型（deepseek-v4-flash）
     未选择工具——与 v0.1.0 已记录的"deepseek 不调动作工具"同族；
  c) 超时层级不一致：M3（ecc5158）设 model-node 60s 硬超时（NodeTimeoutError 归一化），
     实际生效的是 LangChain stream timeout=300s——60s 硬超时在该路径未触发。
- 修复建议：① 注入截断真正生效并调优上限；② 大文件内容惰性加载（工具按需取，不注入）；
  ③ 行数/字数超阈值时确定性路由 analyze_file；④ 超时层级统一并回归测试锁定。
- 附：SummarizationMiddleware 被显式排除（agent.py:98，V0.1.0_M3 文档：隐藏的第二摘要模型
  调用不可观测 + 已自有界记忆）——但即使启用也救不了本场景：610KB 是 CurrentFiles 每轮
  重新注入块（EnterpriseAgentState.current_files），不是对话历史，历史压缩不缩小它。

### 2. turn 级错误原文直回用户（含内部 URL）
- 现象：Gildata 工具 422 时用户收到
  `An error occurred at stage 'turn': 调用后端接口失败: [422 Unprocessable Content] during [POST] to [http://nlpdataagent/master_agent_chat_mcp] ...`
  ——英文原文+上游内部后端 URL+堆栈语义直接暴露给最终用户。
- 建议：turn 异常出口统一转友好中文（"该功能暂时不可用，请稍后再试或换个问法"），内部错误
  细节（URL/状态码/异常链）只进日志/事件；与 M0.1 日志泄漏家族同级的出口脱敏关注点。

### 3. 文件消息送达丢失（C5-05，两次未达）
- 现象：05-数字版-REGR-PDF.pdf 用户确认发送两次，网关侧**零事件**（无 msgtype=file、
  无 inbound 落盘、无 MinerU 提交）；同日其余 11 个文件（含同格式 PDF 06）全部正常到达。
- 影响：无法区分 WeCom 侧丢投 vs 本侧 LC 消息处理丢包；当前无对账手段。
- 建议：① file/媒体消息入口加接收审计计数（按 msgid 留痕，对账用）；② 文档化
  "发送失败/未送达"的用户侧自查路径；③ 如有条件用回调模式对照复测（该文件在
  callback 通道是否可达）。

### 6. Pydantic 序列化警告刷屏

- 建议：修 schema 注解或显式排除字段；顺带评估序列化热路径成本。

  可能性大。建议记录基线，PoC 可接受。

## P3 文档-实现一致性/增强建议

### 8. 知识检索文档与实现不符（非 BM25、无 tsvector）
- DEPARTMENT_KNOWLEDGE_MCP.md 称 hybrid 融合 "tsvector+BgeM3"——实现（repository.py）
  为 `position()` 精确连续子串 + pg_trgm `similarity()`≥0.08 + bge-m3 向量 + RRF(K=60)，
  **grep 零处 tsvector/bm25**。文档需修正。
- pg_trgm 对中文 similarity 实测 0.006–0.013（远低 0.08）→ keyword 腿对中文退化为
  精确短语命中，模糊检索实际全靠 semantic/hybrid。若需真 BM25/中文分词检索：
  zhparser/pg_jieba+ts_rank、ParadeDB pg_search、或应用层 jieba+rank_bm25（214 chunks
  毫秒级）三选一，属增强非缺陷。

### 9. import/probe 脚本易用性
- import_department_knowledge.py 只收一层目录（iterdir 不递归），文档却称"或目录递归"；
- probe 输出 document_count=20 实为列表默认 limit，显示误导。

### 10. 模型工具选择（deepseek-v4-flash）
- 本次再证：analyze_file 0 调用。与 v0.1.0 已知问题同族；建议在模型配置文档中给出
  工具调用强模型的推荐位（v0.1.0 曾建议 glm-5.2），或关键路径工具确定性路由。

### 11.【P0】群回合语义检索作用域泄漏（B5 FAIL，证据链完整）
- 现象：单聊告知私人代号 DIRECT-8841 → 两个群各自提问"我的私人代号是什么"→ **两个群都答出
  DIRECT-8841**（08:34:27/36，用户手机确认）。
- 已排除项（全部实证）：
  - 短期记忆：PG enterprise_short_term_messages 单聊行 sid=wecom:zhuchunlin、群行 sid=各自群 key，
    存储隔离正确；
  - 语义存储：pgvector 群消息入群桶（conversation/hmac-d37cee…、…ff06df…）、单聊入员工桶，
    存储正确；
  - 检索 SQL：pgvector.retrieve WHERE scope=%(scope)s 精确等值，无前缀/模糊；
  - deepagents 历史：StateBackend 每会话；
  - 群检测函数：envelope chat_type + session_id ':group:' 双兜底。
- 定罪证据：
  a) 复刻 client SQL 于员工作用域查"我的私人代号是什么"→ 第一命中即 DIRECT-8841（score 0.814）
     ——群回合只要以员工 scope 检索必泄漏；
  b) 事件日志实锤钩子 session 标识分裂：08:34:16 同一单聊回合
     wecom_turn_started sk=hmac-e5395a47… 而 short_term_memory_load sk=hmac-9a89468a…——
     插件钩子间传递的 session 标识不一致。
- 机制推断：检索钩子（contextseek build_prompt）侧群检测判 False（非 fail-closed——检索确实
  发生且命中员工桶）→ 回落员工作用域；存储钩子（save_state）拿到群 session 正常 → 群桶。
  存取作用域分裂。
- 边界事实：M0.5 修复 fb6e851 当年在 canary（CTX_STORAGE_BACKEND=seekdb）验证通过；
  **主实例 pgvector 后端路径首次活体即漏**——修复可能只在 seekdb 路径生效或钩子 session
  传递在两后端间行为不同。
- 修复建议：统一插件钩子的 session 标识传递（一回合一标识）；群检测在检索侧与存储侧走同一
  判定；补 pgvector 路径的群隔离离线测试（现有测试可能只覆盖 seekdb）；检索侧群检测失败时
  应 fail-closed（返回 None 不检索）而非回落员工作用域。
