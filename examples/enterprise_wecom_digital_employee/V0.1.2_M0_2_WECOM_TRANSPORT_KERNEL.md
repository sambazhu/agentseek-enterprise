# 为什么企微渠道需要 Transport Kernel

> **简要结论：** M0.2 将 Callback 的网络接入职责从 `WeComChannel` 拆出，
> 并建立三种企微 Transport 共用的会话地址。它不实现长连接或自建应用。

## 背景

M0.1 修复了群聊隔离和引用消息语义，但 Callback HTTP、消息加解密、
Uvicorn 生命周期、消息编排和队列仍集中在同一个 `WeComChannel` 中。
如果直接加入 WebSocket 或自建应用回调，每种协议的重连、回复期限、凭据
和主动发送资格都会继续进入这个类。

M0.2 先建立稳定边界。现有 Callback 行为保持不变，后续 Transport 只需
实现同一生命周期、入站绑定和地址解析合同。

## 工作方式

```text
WeComChannel
├── 消息语义、队列、Agent 编排和出站关联
├── ConversationAddress
│   ├── tenant / bot-or-agent / transport
│   ├── chat type / chat id / sender identity
│   └── last interaction / reply deadline
└── WeComTransport
    ├── AiBotCallbackTransport          已实现
    ├── AiBotLongConnectionTransport    未实现
    └── WeComAppTransport               未实现
```

`WeComTransport` 在
`contrib/agentseek-wecom/src/agentseek_wecom/transport.py` 定义三项职责：
绑定入站处理器、解析统一会话地址、管理 Transport 生命周期。

`AiBotCallbackTransport` 在
`contrib/agentseek-wecom/src/agentseek_wecom/transports/callback.py` 接管：

- Callback GET 验证和 POST 消息入口；
- 回调消息解密和回复加密；
- FastAPI 健康接口；
- Uvicorn 启动、优雅停止和超时取消。

`WeComChannel` 不再创建 Callback HTTP 路由，也不持有加解密器或 Uvicorn
实例。它绑定 Transport 的入站处理器，然后继续执行已有消息分发、队列、
流式回复和 `response_url` 出站关联。

## 统一会话地址

`ConversationAddress` 位于
`contrib/agentseek-wecom/src/agentseek_wecom/addressing.py`。字段含义如下。

| 字段 | 含义 |
| --- | --- |
| `tenant_id` | AgentSeek 部署租户，不使用展示名称做权限判断 |
| `bot_or_agent_id` | AI Bot ID 或未来自建应用 Agent ID |
| `transport` | `aibot_callback`、未来长连接或自建应用 |
| `chat_type` | `single` 或 `group` |
| `chat_id` | 单聊成员地址或企微群 `chatid` |
| `sender_userid` | 回调携带的发送人标识，可能仍是密文 |
| `plaintext_userid` | 身份 Provider 成功解析后的企微成员 ID |
| `last_interacted_at` | 本次交互的带时区时间 |
| `reply_deadline` | 当前 Transport 对本次交互可回复的截止时间 |

单聊继续使用 `wecom:{userid}`。明文身份解析成功后，session 和 chat ID
更新为明文成员 ID，保持已有记忆兼容。群聊继续使用
`wecom:{aibotid}:group:{chatid}`，成员身份解析不会改变群聊边界。

Callback 消息带 `response_url` 时，地址记录一小时回复期限；没有时记录
六分钟回调流式期限。安全上下文只包含截止时间，不包含 URL、响应码或
签名媒体地址。

## 这样拆分的原因

Transport 决定网络协议、连接生命周期、回复类型和时效。Channel 决定消息
如何进入 Agent、如何串行化同一会话，以及如何把结果关联回当前请求。
这两类变化速度不同，放在同一个类中会让任何新渠道都影响现有 Callback。

统一地址不把 `transport` 写入既有 session key。Callback 与长连接对同一
AI Bot 是互斥配置；未来切换 Transport 时可以继承原有单聊和群聊记忆。
Transport 类型仍作为独立字段保存，供出站能力和审计判断使用。

## 对使用方的影响

- 当前 `.env` 仍只接受 `transport_mode=callback`。
- Callback URL、端口、加密配置和 `/health` 响应保持不变。
- 长连接和自建应用仍会 fail closed，不能通过配置提前打开。
- inbox、outbox 和 msgid 去重仍是进程内状态；重启恢复不属于 M0.2。
- 下游可以从安全的 `context["wecom"]["address"]` 读取统一地址字段。

## 后续关系

M0.3 在 Transport Kernel 之下增加持久化 inbox、msgid 去重和 outbox。
后续切片再处理 Callback 耗时 I/O、卡片交互、AI Bot 长连接和自建应用。
任何新 Transport 在生产启用前，都必须复用统一地址和持久化消息合同。
