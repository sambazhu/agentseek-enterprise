# 为什么企微 Callback 需要持久化消息基座

> **简要结论：** M0.3 在 Transport Kernel 下增加加密 inbox、持久化
> `msgid` 去重和 outbox。默认仍为内存模式，只有显式启用 SQLite 才改变部署状态。

## 背景

M0.2 已把 Callback 网络接入从 `WeComChannel` 拆开，但消息流仍依赖进程内
字典。进程重启后，网关会忘记已接收的 `msgid`，也无法判断一条
`response_url` 回复是否已生成或已投递。

长连接和自建应用也需要相同的消息所有权。M0.3 先固定存储接口和恢复顺序，
避免 M0.5、M0.6 各自实现一套去重和重试逻辑。

## 工作方式

```text
WeComChannel
├── DurableMessageStore
│   ├── inbox：入站原文、处理状态、租约、回复期限
│   ├── msgid：tenant + bot/agent + transport 范围内稳定去重
│   └── outbox：终态回复、投递状态、租约、回复期限
└── WeComTransport
    ├── AiBotCallbackTransport          当前接入持久化基座
    ├── AiBotLongConnectionTransport    M0.5
    └── WeComAppTransport               M0.6
```

存储合同定义在
`contrib/agentseek-wecom/src/agentseek_wecom/durable.py:67`。当前适配器是
`SqliteDurableMessageStore`，位于同一文件 `:139`。它面向单机单实例部署，
不创建或迁移共享 PostgreSQL schema。

入站消息在进入 Agent 前写入 inbox，再通过带期限的 owner lease 取得处理权。
相关入口位于 `durable.py:152`、`durable.py:256` 和
`channel.py:732`。同一 `msgid` 的重复回调返回既有记录，不再次调用 Agent。
去重范围包含 tenant、Bot/Agent 和 transport，不会把不同机器人或租户合并。

终态 `response_url` 回复先写入 outbox，再取得投递 lease，最后调用企微接口。
入口位于 `durable.py:290` 和 `channel.py:1281`。网关启动时先恢复 outbox，
再恢复仍有回复能力的 inbox，见 `channel.py:904`。这样可以避免一条已经生成
但尚未投递的回复先被重新执行 Agent。

优雅停止会释放当前进程持有的 lease，见 `durable.py:424`。新进程可以立即
恢复。进程被强制终止时，lease 到期后才能由新实例接管，以降低双实例并发执行。

## 数据安全

SQLite 只保存 HMAC 派生的 inbox/outbox ID，不保存明文 `msgid`。回调正文、
`response_url` 和出站内容使用 AES-GCM 加密，并把记录 ID 作为附加认证数据。
数据库文件会收紧为 `0600`，符号链接和不匹配的 schema revision 会拒绝启动。

`AGENTSEEK_WECOM_DURABLE_SECRET` 使用 `SecretStr`，异常和配置 repr 不显示明文。
该值必须独立生成并在重启间保持稳定。丢失或改变它会使既有记录无法认证；
M0.3 不提供在线密钥轮换。

## 取舍和边界

默认 `AGENTSEEK_WECOM_DURABLE_MODE=memory` 保持 M0.2 行为。Linux 活体复验时
显式切换为 `sqlite`，通过后再决定生产默认值。

SQLite 适配器适合当前单机唯一网关。多主机部署需要实现相同
`DurableMessageStore` 合同的共享数据库适配器，并配套跨节点锁和迁移流程。
本切片不自动迁移当前共享 `ai_memory` 数据库。

自动重启补发只支持普通 Markdown。模板卡片包含进程内业务成功/失败回调，
不能安全序列化；重启发现这类 outbox 时会标记 `blocked`，由 M0.4 建立完整的
可恢复卡片状态机。没有 `response_url` 的 Callback 在进程退出后已经失去原
HTTP 响应通道，也会标记 `blocked`，不会重新执行 Agent 后丢弃结果。

本实现提供持久化去重和租约，但不声称跨远端网络绝对 exactly-once。进程若在
企微已接收消息、但本地尚未标记 delivered 的瞬间崩溃，恢复过程可能再次调用
一次性 URL；企微会拒绝已经消费的能力。涉及外部业务副作用的 Agent 工具仍需
使用自己的幂等键。

## 对使用方的影响

- 不设置 M0.3 配置时，不创建 SQLite 文件，不改变 Callback 行为。
- SQLite 模式不读取或修改 Work、Memory、ContextSeek 的数据库。
- 重启恢复受原消息 `reply_deadline` 限制，过期能力不会发送。
- 优雅重启可立即接管；异常崩溃需等待旧 lease 失效。
- M0.5 长连接和 M0.6 自建应用继续在本次路线中，并复用此存储合同。
