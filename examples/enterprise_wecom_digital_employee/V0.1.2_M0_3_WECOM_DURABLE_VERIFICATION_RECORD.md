`test_graceful_owner_release_makes_inbox_immediately_recoverable`、

### 根因分析（供 Codex 复核，未改代码）

两例失败同根因指向：**response_url 投递成功后 inbox 记录未提交终态**。

- 投递路径 `channel.py::_deliver_response_url_once` 中
  `mark_inbox(completed)`（约 :1353-1354）在 `send_markdown` 之后经
  `asyncio.to_thread` 异步提交；
- 测试的 `_wait_until` 仅观察 `RecordingSender.calls`（同步 append），在
  sender 被调用后、终态提交完成前即可继续执行 `channel.stop()`，关闭/
  取消尚未提交的 `mark_inbox`；
- `c9f395b` 的优雅停止释放 lease 不改变该窗口；
- 结果：记录停留非终态 → 重放回复走「正在恢复处理」分支、恢复后仍可被
  `claim_recoverable_inbox` 认领。

属于「投递可观察点早于终态提交」的实现/测试契约缺口：要么投递与终态
提交需在可观察副作用之前原子化，要么测试等待条件需观察终态而非 sender
调用。

### 优雅重启恢复活体 Oracle：发现新集成缺陷

时间线（UTC，消息为单聊慢任务「写约 1000 字散文」）：

| 时间 | 事件 |
| --- | --- |
| 07:22:38 | 消息入站，inbox=processing（lease 600s），原回合开始 |
| 07:22:59 | SIGTERM 优雅停止（1s 退出）。**lease 未释放**：记录 lease_owner 仍指向已死进程（PID 1354127），日志中 uvicorn 打印 "Application shutdown complete"，但 **无任何 bub channel manager 停机日志**（无 "cancelled N in-flight tasks"/"channel.manager stopped"）→ 真实关停路径未执行 `WeComChannel.stop()`，`release_owner` 未运行 |
| 07:23:09 | 重启：startup 恢复因 lease 未过期跳过；恢复仅在 startup 执行、无周期重试 → 消息持续卡住 |
| 07:32:38 | lease 自然过期 |
| 07:33:47 | 再次重启：恢复认领 → 重新调度 → **07:34:22 经原 response_url 投递最终 Markdown（998 字符）恰好 1 次**（事件唯一 + 员工目视确认"只收到 1 次"），inbox 全部 completed、outbox 全部 delivered |

结论：
- 「最终 Markdown 只投递一次」「不重复调度已完成消息」边界成立 ✓；
- lease 过期恢复路径（对应"强制终止后需等待 lease"）完整工作 ✓；
- **但文档边界「优雅停止会立即释放 lease」在真实网关关停链路被违反**：
  单测直接调用 `channel.stop()` 所以通过；真实 SIGTERM → uvicorn 关停
  未触达 bub channel manager 的 shutdown（`channel.stop()`），lease
  残留一个完整周期（默认 600s），且恢复无周期重试，需再次重启才能
  恢复。疑似修复点：gateway/uvicorn lifespan 关停序列应 await channel
  manager shutdown（或增加周期性恢复重试作为缓解）。
