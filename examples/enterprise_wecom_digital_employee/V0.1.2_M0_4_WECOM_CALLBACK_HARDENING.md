# 为什么企微 Callback 需要首包隔离和可恢复卡片状态

> **简要结论：** M0.4 保留 AI Bot Callback Transport，但把媒体耗时 I/O
> 移到首包之后，并让文件完成、卡片事件和卡片业务提交进入可恢复状态机。

## 背景

企微卡片事件只回调一次。服务器五秒内没有收到响应时会断开连接并丢弃事件。
媒体下载、解密、文件落盘、OCR 和 open userid 转换都可能访问网络或磁盘，
不能作为首包生成的前置条件。协议来源见企微官方的
[接收事件](https://developer.work.weixin.qq.com/document/path/101027)和
[模板卡片类型](https://developer.work.weixin.qq.com/document/path/101032)。

M0.3 已提供加密 inbox、outbox、租约和跨重启 `msgid` 去重，但模板卡片仍绑定
进程内成功回调。进程退出后无法证明卡片是否已经发送，也无法重新构造业务提交。

## 工作方式

```text
Callback 到达
├── 持久化 inbox 与 msgid 去重
├── 立即形成首包
└── 保留同一会话队列位置
    ├── 身份解析
    ├── 媒体下载、解密、文件解析
    ├── 文件完成后构造 Agent 消息
    └── Agent 回合与 response_url 终态投递
```

媒体入口位于 `contrib/agentseek-wecom/src/agentseek_wecom/channel.py:544`。
它先创建 stream 和安全上下文，再提交首包，最后同步地把预处理函数放入队列。
事件循环在处理函数返回前不会启动该队列任务。因此媒体网络 I/O 不会早于首包。

队列记录支持一个异步预处理阶段，见 `channel.py:129` 和 `channel.py:1329`。
文件解析为 pending 时，轮询也在这个队列位置内完成。后续同会话消息不能越过
文件消息，解析完成后也不再直接调用 Agent。不同群聊和单聊仍使用各自地址键，
不会互相阻塞。

模板卡片事件在 `channel.py:726` 接入。实现接受官方的
`button_interaction`、`vote_interaction`、`multiple_interaction`，以及卡片菜单
可能返回的 `text_notice`、`news_notice`。`event_key`、`task_id` 和选择项会做
类型、长度和控制字符归一化，再写入安全上下文。事件沿用普通消息的 inbox、
`msgid` 去重、身份解析和会话队列。

## 卡片投递状态

```text
pending ──claim──> sending ──企微接受──> sent ──幂等业务提交──> delivered
                         │                    │
                         └─结果不明→ blocked  └─失败→ 保持 sent，稍后只重试提交
```

M0.4 在原 outbox 状态中增加 `sent`，见
`contrib/agentseek-wecom/src/agentseek_wecom/durable.py:20`。这不改变 SQLite
表结构，也不迁移共享 PostgreSQL。卡片、`response_url` 和业务动作仍在加密
envelope 中。

可持久化业务动作由 `TemplateCardAction` 描述，见
`contrib/agentseek-wecom/src/agentseek_wecom/outbound.py:48`。动作只有类型和
JSON payload，不保存闭包。应用在启动时登记幂等 handler。报告交付把固定的
`DeliveryRecord` 写入动作 payload，重试时提交同一记录，不重新生成时间或授权。

恢复逻辑位于 `channel.py:1025`：

- `pending` 卡片可以发送，成功后进入 `sent` 并提交业务状态。
- `sent` 卡片不再发送，只执行幂等业务提交。
- 旧式闭包卡片、未知 handler 或无效 envelope 标记为 `blocked`。
- 进程死在网络调用中的 `sending` 结果无法判定，标记为 `blocked`，不猜测重发。

这个边界提供了“已知状态不重复发送”，但不声称跨企微网络绝对 exactly-once。
发送结果不明需要人工核对，这是一次性 `response_url` 的固有限制。

## 为什么这样设计

媒体任务在完成后重新入队会造成顺序反转：较晚的文本可能先进入 Agent。
M0.4 改为到达时保留队列位置，让耗时预处理成为回合的一部分。代价是同一会话
的后续消息会等待文件解析；队列超时和容量限制继续提供有界背压。

卡片先提交业务账本再发送会产生“账本已交付、员工未收到卡片”。先发送再仅用
`delivered` 标志又无法恢复崩溃后的业务提交。中间态 `sent` 把远端投递和本地
业务提交分开，使已发送卡片可以安全收尾。

## 对使用方的影响

- M0.4 不新增生产必填配置，不改变现有 SQLite schema revision。
- 媒体首包会稳定显示接收确认；最终结果仍使用原 stream 或 `response_url`。
- 同一会话中的文件和文本严格按到达顺序进入 Agent。
- 卡片交互事件具备持久化去重；重复 `msgid` 不再次调用 Agent。
- 报告交付卡片可在重启后恢复业务提交，旧式不可序列化卡片继续失败关闭。
- M0.5 长连接和 M0.6 自建应用不在本切片启用，但继续复用 M0.2/M0.3 内核。
