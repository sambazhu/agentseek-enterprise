# 如何复验企微 M0.4 Callback 加固

用于确认媒体首包隔离、文件会话顺序、模板卡片事件和可恢复卡片业务提交，
同时保持 M0.3 的单聊、群聊、引用、身份和持久化行为。

## 前置条件

- 使用分支 `enterprise/v0.1.2-wecom-callback-hardening`。
- 父生产基线是 `05e8086ec2bf47329ffea6362c7757abe83b000e`。
- Linux 保留 M0.3 的五项 durable 配置，不生成或替换加密材料。
- 停止其他机器上的同一机器人实例。
- 不迁移共享数据库，不启用长连接或自建应用 Transport。
- 模型 API Key 轮换不属于本轮复验项。

6. 核对健康、单实例和存储基线。

   - `:12000` 只有一个监听 PID。
   - `/health` 返回 `{"ok":true,"channel":"wecom","enabled":true}`。
   - durable SQLite 权限为 `600`。
   - 启动窗口没有 Traceback 或 ERROR。
   - 共享 PostgreSQL schema revision 没有变化。

7. 验证媒体首包和会话顺序。

   从同一单聊发送一个需要解析的 PDF。在文件最终回复出现前，立即再发送：

   ```text
   M0.4 文件后续消息：请只回复“顺序正常”
   ```

   文件回调必须先显示接收确认，不能等待下载或 OCR 才返回。第二条消息必须排队，
   Agent 事件顺序必须是文件消息在前、文本消息在后。不得出现旧路径中的独立
   `file-poll` 直接调度。确定性 Oracle 是
   `test_media_io_starts_only_after_first_callback_and_reserves_session_order`。

8. 验证模板卡片事件。

   临时在 Linux `.env` 设置以下验证值并重启。该值不是密钥。

   ```env
   AGENTSEEK_WECOM_TEMPLATE_CARD_EVENT_PROBE_TRIGGER=M0.4卡片交互探针
   ```

   测试员工精确发送 `M0.4卡片交互探针`。机器人应先确认，再发送恰好一张
   `button_interaction` 卡片。点击 `确认交互` 后，应出现恰好一个
   `template_card_event` 回合；事件的 `event_key=M04_CONFIRM`，群聊和单聊地址
   仍保持隔离。企微不会重试超时卡片事件，因此回调必须在五秒内返回首包。

   验证后清空该配置并重启。探针不发布或交付 Artifact。

9. 验证卡片重启状态机。

   以下三项由确定性 Oracle 覆盖，不制造真实员工重复卡片：

   - pending 卡片在重启后发送一次并完成业务提交；
   - sent 卡片在重启后不再发送，只补业务提交；
   - sending 结果不明时标记 blocked，不重发、不提交。

   对应测试是 `test_pending_template_card_is_sent_and_finalized_after_restart`、
   `test_sent_template_card_recovers_business_action_without_resending` 和
   `test_ambiguous_sending_template_card_is_blocked_without_resending`。

   如果 Linux 已启用 signed-link 且 Work schema 可用，可以额外验证一次报告
   交付卡片；当前 Linux `WORK_ENABLED=false` 时不得为此迁移共享库或改为 true。

10. 回归 M0.3 活体行为。

    - 单聊恰好一条终态回复。
    - 两个群聊双向隔离，内容零交叉。
    - 引用内容可见，但 raw URL、response code 不进入 Agent。
    - open userid 转明文不改写群会话边界。
    - 一次优雅 SIGTERM 仍释放 lease，新实例立即恢复。

11. 执行脱敏检查。

    只报告命中数，不输出原文。日志、事件和 durable SQLite 中以下内容必须零
    明文命中：模型 Key、企微 Token、EncodingAESKey、AppSecret、PG/DM 密码、
    namespace secret、`response_code`、媒体签名 URL、下载授权和卡片 action payload。

## 故障处理

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 文件下载开始早于回调首包 | 媒体 I/O 仍在 HTTP handler | 判为 BLOCKED，保留脱敏时间线 |
| 文件后的文本先进入 Agent | 文件完成绕过或重新插入队列 | 判为 BLOCKED，记录 session 事件顺序 |
| 点击卡片没有回调 | Bot 回调配置或卡片字段不匹配 | 核对 `template_card_event` 和探针 success 事件 |
| 同一卡片事件执行两次 | `msgid` 去重未覆盖 event | 判为 BLOCKED，不重复人工点击掩盖问题 |
| sent 卡片重启后再次发送 | 恢复逻辑忽略 `sent` | 判为 BLOCKED，停止卡片活体 |
| sending 结果不明仍自动重发 | 失败关闭边界失效 | 判为 BLOCKED，人工核对企微与台账 |
| action handler unavailable | 应用未在 Channel 恢复前初始化 | 判为 BLOCKED，不手工改 durable 状态 |

失败时保留原 durable SQLite 和 `.env`，切回生产基线并用现有脚本重启。以下命令
未在本机执行。

```bash title="not executed in this run"
git switch production
git merge --ff-only company-gitlab/production
```

不要删除或手工编辑 SQLite；其中可能包含已发送但尚未完成业务提交的卡片。
