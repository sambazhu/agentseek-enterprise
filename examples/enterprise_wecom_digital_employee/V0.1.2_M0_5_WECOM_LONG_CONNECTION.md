# M0.5 AI Bot long-connection transport

> **In short:** M0.5 adds an authenticated WebSocket transport without changing
> Callback behavior. Long connection actively refreshes streams, persists reply
> intent and proactive eligibility, and fails closed when ownership or credentials
> are invalid.

## Context

M0.1 through M0.4 established protocol safety, a shared transport boundary,
encrypted durable messaging, and a hardened Callback implementation. Callback
remains useful for compatibility. Its one-hour, one-shot `response_url` is not a
good primary path for long tasks or scheduled status notifications.

The official AI Bot API permits either Callback or long connection for one robot.
It does not run both modes at once. Each robot also permits one effective WebSocket
subscription. A new subscription disconnects the old one.

M0.5 therefore treats the mode choice as a deployment binding, not an automatic
fallback. One AI Bot selects one transport. Different bots can use different modes.
The Linux live Oracle uses a new long-connection bot as an isolated canary, so the
existing Callback bot does not change mode.

An AI Bot is a channel endpoint. A digital employee is the business identity defined
by a Profile and `digital_employee_id`. M0.5 keeps their relationship implicit:
one deployment loads one Profile and binds one bot to it. The current example still
loads the `industry-report` Pack directly; it does not yet route several bot IDs to
several digital employees inside one gateway.

## How it works

```text
WeCom AI Bot (one selected mode)
    │ WebSocket callback: req_id + body
    ▼
AiBotLongConnectionTransport
    ├── local single-owner lock
    ├── aibot_subscribe(BotID, Secret)
    ├── ping every 30 seconds
    ├── bounded reconnect with jitter
    └── authenticated callback dispatch
             │
             ▼
WeComChannel
    ├── ConversationAddress, 24-hour reply deadline
    ├── encrypted inbox + msgid dedup
    ├── first aibot_respond_msg stream before Agent work
    ├── coalesced stream refreshes
    └── encrypted terminal/proactive outbox
             │
             ▼
    aibot_respond_msg or aibot_send_msg
```

The deployment supplies the missing business binding:

```text
BotID -> deployment -> digital_employee_id -> Profile
```

M0.5's canary maps the new long-connection BotID to the existing
`digital_employee_id=industry-report`. It validates another channel entry for the
same digital employee. A robot display name alone does not create a new departmental
digital employee.

### Connection lifecycle

`AiBotLongConnectionTransport` owns the WebSocket lifecycle in
`contrib/agentseek-wecom/src/agentseek_wecom/transports/long_connection.py:68`.
Startup acquires a `0600` POSIX lock, starts the local health listener, connects to
the fixed official WSS endpoint, and waits for successful `aibot_subscribe`.
Authentication rejection stops startup. Network interruption clears readiness and
reconnects with bounded exponential delay.

The transport disables the WebSocket library's protocol-level automatic ping.
It sends the documented JSON `ping` command instead. A subscribed health response
contains `transport=long_connection` and `subscribed=true`.

SIGTERM is bridged to the outer Bub channel manager. Shutdown closes the socket,
cancels callback tasks, stops the health listener, releases durable leases, and
releases the process lock.

### Reply ordering

Long connection does not return a Callback HTTP body. `WeComChannel` sends the
first `stream` command before scheduling the Agent turn. Media download, userid
resolution, model calls, and file extraction therefore cannot run before the first
visible acknowledgement.

Every refresh reuses the inbound `req_id` and one `stream.id`. Incremental text is
coalesced to one refresh per configured interval. The default is three seconds,
below the per-conversation rate ceiling. The Agent turn timeout is also below the
official ten-minute stream completion limit.

The terminal refresh is written to the encrypted outbox before network delivery.
It is safe to recover because the same `req_id` and `stream.id` update the same
stream message. The reply deadline is 24 hours from the inbound callback.

### Addressing and isolation

`long_connection_conversation_address()` uses the existing direct-message session
contract and the existing Bot-plus-chat group contract. Plaintext userid resolution
may change a direct session from encrypted userid to plaintext userid. It never
changes a group session boundary.

The durable inbox scope includes tenant, Bot, transport, and `msgid`. A Callback
message and a long-connection message cannot suppress each other accidentally.

The direct-message session remains `wecom:<userid>` for compatibility. This is
correct while one runtime and one short-term-memory keyspace serve one digital
employee: employee A and employee B receive different keys. Transport and BotID do
not belong in the business conversation key because replacing a bot or moving the
same digital employee from Callback to long connection should not redefine that
employee's identity.

A future multi-digital-employee gateway needs one more logical scope. Its short-term
memory key must include `tenant_id + digital_employee_id + conversation_id`, either
as a composite database key or a namespaced session identifier. Several digital
employees may share one physical database, but they must not share a keyspace that
is indexed only by `wecom:<userid>`. M0.5 deliberately does not change this schema;
the canary uses isolated local stores to avoid polluting production test data.

### Proactive messages

The transport exposes `aibot_send_msg` for Markdown and template cards. It refuses
addresses that were not observed on an authenticated inbound interaction.

The channel adds a second guard. SQLite schema revision 2 stores an encrypted
conversation qualification record. The deterministic row key is HMAC-derived;
userid, chatid, and address data remain encrypted. A restart can therefore restore
qualification without trusting caller-supplied address data alone.

Callers provide an idempotency key. The channel hashes its tenant/Bot/chat scope,
then uses that digest as the durable outbox stream key. Repeating the same business
delivery returns `skipped` after the first delivered record. A proactive outcome
that is ambiguous after process loss enters `blocked` instead of being resent.

Long-connection template-card clicks still enter the normal session queue and Agent
turn. They do not use `aibot_respond_msg`, because that command belongs to message
callbacks. M0.5 delivers the terminal result as an idempotent proactive Markdown
message to the same qualified conversation. It does not attempt
`aibot_respond_update_msg`, because a valid update must reconstruct the complete
original card and finish within the card-event response window.

### Local durable migration

M0.5 migrates only the dedicated local WeCom SQLite file from revision 1 to 2. The
migration creates `wecom_conversations` and preserves inbox/outbox rows. Unknown
or newer revisions still fail closed.

The migration does not read, write, or migrate shared PostgreSQL. Long-connection
production preflight requires SQLite durable mode because memory mode cannot meet
restart recovery or persistent proactive qualification contracts.

Revision 2 is intentionally not readable by M0.4 code. Operators take a consistent
revision-1 backup while the gateway is stopped, before starting M0.5. Rolling back
to Callback restores that backup while no gateway is running. The M0.5 revision-2
file is moved to restricted storage for reconciliation instead of being deleted.

That migration rule applies when an existing bot changes mode. The selected Linux
Oracle creates a new canary bot with a new SQLite file, so it initializes revision 2
directly and never opens or migrates the Callback bot's revision-1 file.

### Multiple digital employees and the common application

The target enterprise topology permits several bots. Each bot independently chooses
Callback or long connection and binds to one departmental digital employee. A
department may later operate several digital employees, each with its own
`digital_employee_id`, Profile, authorization scope, and conversation namespace.

One self-built WeCom application may serve as a common outbound channel for those
digital employees. That application must carry the originating
`digital_employee_id`, enforce application visibility, and durably deduplicate each
target member, department, or tag delivery. This is the planned M0.6
`WeComAppTransport`. The current `CORP_ID` and `APP_SECRET` only support auxiliary
API operations such as userid conversion; they do not implement that outbound
application transport.

## Why it is like this

The upstream 0.1.3 core release is intentionally not merged into M0.5. It is
orthogonal to WeCom, but it overlaps current production in lifecycle, dotenv,
documentation, and lock files and produces merge conflicts. Core synchronization
needs its own branch and regression boundary.

The transport uses raw documented WebSocket commands instead of hiding lifecycle
inside the Agent runtime. This keeps authentication, heartbeat, request
correlation, and reconnect deterministic and independently testable.

Callback is not an automatic runtime fallback. The WeCom console disables one mode
when enabling the other, so an in-process fallback would report availability that
does not exist.

## Consequences for users

- You keep the existing Callback bot and gateway running during the canary test.
- You create a separate long-connection bot and obtain its dedicated Secret.
- You run only one long-connection gateway for that new BotID.
- You map the canary to the existing `industry-report` digital employee explicitly.
- You isolate canary writable stores to prevent test-data pollution; this is an operational test boundary.
- Existing direct and group session keys remain stable.
- Long tasks can recover terminal stream delivery within 24 hours.
- Scheduled Markdown/Card notifications can target previously observed sessions.
- Card-click Agent results arrive as proactive Markdown, not as an invalid stream update.
- Arbitrary employee, department, or tag delivery still waits for M0.6 application transport.
- Direct file upload remains disabled until chunked media upload is implemented.
- A default-off live probe can send proactive Markdown plus a button card; clear its trigger after verification.
- M0.5 does not claim a multi-Profile gateway or a completed common application transport.
