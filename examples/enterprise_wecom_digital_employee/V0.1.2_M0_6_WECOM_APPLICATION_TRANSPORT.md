# M0.6 WeCom self-built application transport

> **In short:** M0.6 adds one common self-built application as a supplementary
> channel for explicit member, department, and tag notification. It coexists with
> the selected AI Bot transport, carries an explicit digital-employee source, and
> fails closed on visibility, partial delivery, or ambiguous recovery.

## Deployment model

The WeCom administrator still selects exactly one mode for each AI Bot:

```text
department digital employee A ── AI Bot A ── Callback OR long connection
department digital employee B ── AI Bot B ── Callback OR long connection
             │                              │
             └──────── common self-built application ────────┘
                         explicit proactive notification
```

The application is not a third AI Bot mode and does not replace streaming. It adds
capabilities that an AI Bot does not provide reliably: selecting a member,
department, or tag before that recipient starts a robot conversation, and sending
temporary-media file messages.

The application `AgentID` identifies the WeCom credential and callback endpoint.
`digital_employee_id` identifies the business actor. They are deliberately separate.
One common application may be allowlisted for several digital employees, but every
outbox record still contains exactly one source `digital_employee_id`.

The current enterprise example loads one Profile (`industry-report`) per gateway.
M0.6 makes the transport source-aware but does not claim that this example already
routes several Profiles inside one process. That routing remains a later milestone.
Inbound callbacks therefore bind to the configured default digital employee. They
cannot infer a business source from AgentID when one common application is shared.

## Runtime flow

### Proactive delivery

1. A business workflow supplies an allowlisted `digital_employee_id`, an explicit
   `WeComAppTarget`, message type, payload, and stable business idempotency key.
2. The transport refreshes the application's `agent/get` snapshot when its cache
   expires.
3. It rejects targets outside the explicit member, department, or tag sets. `@all`
   and malformed or over-limit target lists are rejected before an API call.
4. The channel persists an encrypted outbox record. Its stable scope contains the
   tenant, digital employee, AgentID, normalized target, and business key.
5. The sender obtains and caches the application access token, then calls the
   official message API with duplicate checking enabled.
6. A complete success becomes `delivered`. Any returned invalid recipient makes the
   record `blocked`; the system does not silently call a partial send successful.

The access token belongs to the application Secret and is normally valid for 7200
seconds. The cache refreshes early and retries once for an explicitly invalid or
expired token. The application Secret is distinct from the older helper Secret used
for AI Bot `open_userid` conversion.

### Inbound callback

The independent application callback uses its own fixed path, Token, and 43-character
EncodingAESKey. It must never share the AI Bot callback path or credentials.

The transport verifies the signature, decrypts the bounded XML envelope, verifies
the AgentID when present, and normalizes text, media, and event callbacks. The HTTP
request receives an immediate `success`; Agent work continues in the existing
per-session queue. Because self-built applications do not stream, terminal output is
sent as a new application message to the originating user.

Application direct messages keep `wecom:<userid>` within the current one-Profile
deployment. This preserves the established short-term-memory contract for the same
digital employee. When several Profiles later share a physical memory store, the
logical namespace must add `tenant_id + digital_employee_id + conversation_id`.

### Media

Outbound image, voice, video, and file messages first upload bytes to the official
temporary-media API. The returned `media_id` is valid for three days. M0.6 enforces
the documented limits: image 10 MB, AMR voice 2 MB, MP4 video 10 MB, and file 20 MB;
all uploads must exceed five bytes.

Inbound application media uses the application Secret to download its `media_id`.
It does not reuse the AI Bot identity-conversion helper Secret. The resulting bytes
then enter the existing scoped file service and session queue.

## Durable recovery contract

Application outbox recovery follows these rules:

- an unsent or determinate failed outbox may retry before its 24-hour operational
  deadline;
- a `sending` record whose process died after more than one claim is ambiguous and
  becomes `blocked` instead of risking a duplicate notification;
- partial recipient acceptance becomes `blocked` and requires reconciliation;
- missing target, source, payload, or transport becomes `blocked`;
- application inbox recovery does not require an AI Bot `response_url` or WebSocket
  `req_id`; its terminal result uses the application outbox;
- payloads and target IDs remain encrypted at rest, while events log only source ID,
  message type, and target counts.

## Supported boundary

M0.6 implements the official `text`, `image`, `voice`, `video`, `file`, `textcard`,
`news`, `mpnews`, `markdown`, and `template_card` send types. A caller remains
responsible for a valid message-type payload.

The application visibility snapshot is intentionally strict. A direct user target
must appear in `allow_userinfos`; a department target must appear in `allow_partys`;
a tag target must appear in `allow_tags`. A user who is only indirectly visible via
a department is not accepted as an explicit user target in M0.6. The caller can send
to that visible department or ask an administrator to add the member explicitly.

`AGENTSEEK_WORK_ARTIFACT_DELIVERY_MODE=direct_file` remains unsupported. M0.6 can
upload and send a file through its API and live probe, but Work composition has not
yet been changed to choose an application target. It must not silently route an
artifact to a recipient inferred from unrelated conversation state.

## Security decisions

- There is no `@all` broadcast path.
- Callback XML is size-bounded and rejects DTD/entity declarations.
- Secrets use non-representable settings fields and are never added to events.
- Routing IDs remain internal and are not added to model-visible prompt context.
- A common application uses an explicit digital-employee allowlist.
- Visibility is checked locally before each cached-window send and server-side
  invalid-recipient results are still treated as failures.
- `.env`, logs, temporary media, durable SQLite, and runtime files are never committed.

## What the administrator creates

Do not create the application during code development. Create it only after the
Linux static gates pass and immediately before live verification. The administrator
creates one limited-scope application, records CorpID, AgentID, and its dedicated
Secret, configures an independent receive-message callback URL, Token, and
EncodingAESKey, and exposes it only to the test member, department, and tag.

The exact procedure and PASS/BLOCKED Oracles are in
`V0.1.2_M0_6_WECOM_APPLICATION_VERIFICATION.md`.
