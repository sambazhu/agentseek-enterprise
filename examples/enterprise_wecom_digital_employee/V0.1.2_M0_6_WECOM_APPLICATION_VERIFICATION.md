# 如何在 Linux 复验 M0.6 企微自建应用 Transport

本手册使用一个限定可见范围的新自建应用，验证指定成员、部门、标签、
文件和独立回调。现有 Callback `:12000` 不停机。M0.5 长连接 canary
可在隔离 worktree 中快进到 M0.6 分支并作为 `:12001` 验证宿主。

## 前置条件

- 功能分支为 `enterprise/v0.1.2-wecom-app-transport`。
- M0.6 代码提交为 `12a6bbc`，复验 HEAD 必须包含该提交。
- 父生产基线为 `2cff5c0e609695349286cea9e10ceeca17f93792`。
- GitHub 和 GitLab 同名功能分支指向同一提交。
- Callback `:12000` 保持原 PID 和原文件。
- 验证人可以修改 `:12001` canary 的 `.env` 并优雅重启该实例。
- 可以为 `:12001` 增加一条独立的公网 HTTPS 回调路由。
- 模型 Key 轮换不属于本轮门禁。

## 第一阶段：不创建应用，先跑静态门禁

1. 拉取功能分支，只读核对祖先、双端引用和 diff。

   ```bash title="not executed in this run"
   git fetch github enterprise/v0.1.2-wecom-app-transport
   git fetch company-gitlab enterprise/v0.1.2-wecom-app-transport
   git merge-base --is-ancestor 2cff5c0e609695349286cea9e10ceeca17f93792 github/enterprise/v0.1.2-wecom-app-transport
   git diff --check 2cff5c0e609695349286cea9e10ceeca17f93792..github/enterprise/v0.1.2-wecom-app-transport
   git ls-remote github refs/heads/enterprise/v0.1.2-wecom-app-transport
   git ls-remote company-gitlab refs/heads/enterprise/v0.1.2-wecom-app-transport
   ```

2. 运行确定性门禁。验证机 `:12000` 已占用时，企微组件测试显式用
   `12100` 避免环境端口冲突。

   ```bash
   uv lock --check
   AGENTSEEK_WECOM_PORT=12100 uv run --project contrib/agentseek-wecom pytest -q contrib/agentseek-wecom/tests
   PYTHONPATH=examples/enterprise_wecom_digital_employee/src uv run pytest -q examples/enterprise_wecom_digital_employee/tests
   uv run ruff check contrib/agentseek-wecom examples/enterprise_wecom_digital_employee
   PYTHONPATH=examples/enterprise_wecom_digital_employee/src uv run ty check contrib/agentseek-wecom/src examples/enterprise_wecom_digital_employee/src
   PYTHONPATH=. uv run pytest -q tests/cli_commands/test_templates_render.py -k "enterprise and wecom"
   uv run pytest -q tests/test_wecom_integration.py
   make docs-test
   bash -n examples/enterprise_wecom_digital_employee/scripts/run_gateway.sh
   ```

3. 显式复跑 M0.6 关键 Oracle。

   ```bash
   AGENTSEEK_WECOM_PORT=12100 uv run --project contrib/agentseek-wecom pytest -q \
     contrib/agentseek-wecom/tests/test_application_transport.py \
     contrib/agentseek-wecom/tests/test_outbound.py
   PYTHONPATH=examples/enterprise_wecom_digital_employee/src uv run pytest -q \
     examples/enterprise_wecom_digital_employee/tests/test_prod_check.py
   ```

任一静态门禁失败时不创建企微应用，不部署活体。

## 第二阶段：由管理员创建公共自建应用

只有第一阶段全部通过后才执行本阶段。

1. 在企微管理后台创建一个新自建应用，建议名称“数字员工通知中心
   M0.6”。不要改造现有 userid 转换辅助应用。
2. 可见范围只加入：

   - 一名测试成员；
   - 一个测试部门；
   - 一个测试标签。

   不选全企业，不使用 `@all`。记录测试用 userid、department ID 和
   tag ID，不在验证报告中展示成员明文身份。
3. 记录 CorpID、AgentID 和该应用的专用 Secret。Secret 不得复用 AI Bot
   长连接 Secret、Callback Token/AESKey 或旧 `AGENTSEEK_WECOM_APP_SECRET`。
4. 启用接收消息，配置独立回调：

   ```text
   URL: https://<public-host>/<dedicated-m06-route>
   Token: 1–32 位字母数字
   EncodingAESKey: 后台生成的 43 位值
   ```

   公网路由必须精确反代到 canary
   `AGENTSEEK_WECOM_APP_CALLBACK_PATH`，不得指向 AI Bot callback path。
   企微 URL 验证必须在 1 秒内成功。

## 第三阶段：隔离配置与部署

1. 在 M0.6 canary `.env` 中写入真实值。下面是形状示例，不能原样使用。

   ```env title="not executed in this run"
   AGENTSEEK_WECOM_APP_TRANSPORT_ENABLED=true
   AGENTSEEK_WECOM_CORP_ID=REPLACE_WITH_CORP_ID
   AGENTSEEK_WECOM_APP_AGENT_ID=REPLACE_WITH_POSITIVE_AGENT_ID
   AGENTSEEK_WECOM_APP_TRANSPORT_SECRET=REPLACE_WITH_APPLICATION_SECRET
   AGENTSEEK_WECOM_APP_CALLBACK_PATH=/wecom/app/callback
   AGENTSEEK_WECOM_APP_CALLBACK_TOKEN=REPLACE_WITH_ALPHANUMERIC_TOKEN
   AGENTSEEK_WECOM_APP_CALLBACK_ENCODING_AES_KEY=REPLACE_WITH_43_CHARACTER_KEY
   AGENTSEEK_WECOM_APP_ALLOWED_DIGITAL_EMPLOYEE_IDS=industry-report
   AGENTSEEK_WECOM_APP_DEFAULT_DIGITAL_EMPLOYEE_ID=industry-report
   AGENTSEEK_WECOM_APP_VISIBILITY_CACHE_TTL_SECONDS=300
   AGENTSEEK_WECOM_APP_PROACTIVE_PROBE_TRIGGER=M0.6自建应用主动探针
   AGENTSEEK_WECOM_APP_PROACTIVE_PROBE_USERID=REPLACE_WITH_VISIBLE_TEST_USERID
   AGENTSEEK_WECOM_APP_PROACTIVE_PROBE_PARTY_ID=REPLACE_WITH_VISIBLE_PARTY_ID
   AGENTSEEK_WECOM_APP_PROACTIVE_PROBE_TAG_ID=REPLACE_WITH_VISIBLE_TAG_ID
   AGENTSEEK_WECOM_APP_PROACTIVE_PROBE_FILE_PATH=runtime-m06/m06-probe.txt
   AGENTSEEK_WECOM_DURABLE_MODE=sqlite
   ```

   `AGENTSEEK_WECOM_APP_SECRET` 继续是 userid 转换辅助应用的 Secret；
   M0.6 发送、可见范围和媒体下载只使用
   `AGENTSEEK_WECOM_APP_TRANSPORT_SECRET`。

2. 创建一个大于 5 字节、小于 20 MB 的无敏感信息文本文件，权限
   `600`。不使用真实报告、日志或 `.env`。
3. 运行严格预检，必须是 0 WARN / 0 FAIL。

   ```bash title="not executed in this run"
   uv run python examples/enterprise_wecom_digital_employee/scripts/prod_check.py \
     --env-file examples/enterprise_wecom_digital_employee/.env --strict
   ```

4. 优雅重启 `:12001` canary，不动 `:12000` Callback。核对：

   - 两端口各一个 PID；
   - `:12000` PID 与 health 不变；
   - `:12001` 日志无 Secret、Token、AESKey 和 access token；
   - 启动时 `agent/get` 可见范围刷新成功；
   - `:12001/health/wecom-app` 为 `ok=true`、`transport=application`、
     `visibility_loaded=true`；
   - durable SQLite 和日志为 `600`。

## 第四阶段：活体 Oracle

### 1. 独立回调与非流式回复

1. 测试成员进入新自建应用，发送“M0.6 应用回调：请只回复
   应用回调正常”。
2. 回调 HTTP 应立即返回 `success`，Agent 回合进入同一用户会话队列。
3. 员工最终只收到一条新应用文本“应用回调正常”，不得出现流式
   半成品。
4. session 保持 `wecom:<userid>`；address transport 为 `wecom_app`，
   AgentID 只出现在内部寻址，不进入模型回复。

### 2. 指定成员、部门、标签和文件

在 M0.5 长连接机器人中逐字发送探针触发词。预期：

- AI Bot 只返回一条“探针已启动”终态确认；
- 指定成员收到一条 text 和一个 file；
- 指定部门收到一条 markdown；
- 指定标签收到一张 textcard；
- 每个 outbox 的来源均为 `industry-report`，四个 outbox 全部
  `delivered`，重发同一入站 msgid 不产生第二组通知；
- 文件 outbox 只持久化 `media_id`，不持久化本地文件内容。

验证记录只写目标类型和数量，不写 userid、department ID、tag ID 或
`media_id`。

### 3. 可见范围和局部投递

- `agent/get` 的成员或标签维度非空时，确定性测试必须证明
  超出明确范围的目标在调用 `message/send` 前被拒绝。
- `allow_partys` 非空时将其值视为授权部门根节点；必须通过
  `department/simplelist` 解析根节点的递归子树。根节点和经验证的
  后代允许发送，无关部门必须在 API 前拒绝；缺根、断链、成环或
  部门接口失败必须使可见范围刷新失败，不得降级为未知放行。
- `agent/get` 维度为空时按“范围未知”处理，允许进入官方发送 API；API 返回
  权限错误或 `invaliduser` / `invalidparty` / `invalidtag` 必须进入
  `blocked`。
- 不要在活体中向真实超范围目标发消息。
- mock API 返回任一 `invaliduser` / `invalidparty` / `invalidtag` 时，
  outbox 必须进入 `blocked`，不得标记整体成功或盲目重试。

### 4. SIGTERM 与持久化恢复

1. 用慢任务产生一条 application inbox `processing`记录，在它产生终态
   outbox 前对 `:12001` 发 SIGTERM。
2. 旧进程必须走 manager stop 并释放 `lease_owner`。
3. 重启后应立即认领 application inbox，不因缺少 AI Bot `response_url` 或
   WebSocket `req_id` 进入 `blocked`。
4. 终态通过应用 outbox 恢复投递恰好一次，inbox=`completed`、
   outbox=`delivered`。
5. 确定性测试还必须覆盖：进程在不确定 `sending` 结果后退出时改为
   `blocked`，不补发。

### 5. 回归和脱敏

- Callback `:12000` PID、health、日志和 durable mtime 全程不变。
- M0.5 长连接的单聊、群隔离、引用、媒体和主动消息确定性门禁不回归。
- 日志、events 和 durable SQLite 中的应用 Secret、Token、AESKey、
  access token、目标 ID、`media_id`、签名 URL 和密码明文命中数必须为 0。
- 共享 PostgreSQL 表和 schema 只读核对零变化。
- 不提交 `.env`、日志、上传文件、runtime 或 SQLite。

## 收尾

1. 活体完成后清空五个 `APP_PROACTIVE_PROBE_*` 字段，删除无敏探针文件，
   优雅重启 canary 并复核探针配置 0 行。
2. 保留自建应用的限定可见范围和回调，供后续 M0.6 运行。若本轮
   BLOCKED 且不继续，由管理员停用该应用。
3. 只有全部 Oracle PASS 才建议快进合入 `production`。未经维护者决定不建
   tag，不 force push，不改写 M0.1–M0.5 历史。
