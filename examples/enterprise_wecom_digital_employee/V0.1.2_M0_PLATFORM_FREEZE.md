# v0.1.2 M0 平台化边界与第二个部门数字员工冻结

## 1. 决策

v0.1.2 将第二个真实业务验证目标冻结为：

> **信息技术部数字员工：信息系统需求评审与立项评估 Playbook**

数字员工完成需求受理、材料完整性检查、多维评估和立项建议，
交付《信息系统立项评估报告》。数字员工不代替人工立项决策，不自动
在项目、采购、预算或发布系统中创建或执行业务动作。

## 2. 部署拓扑

v0.1.2 保持“一个 Bot 对应一名部门数字员工”：

```text
战略发展部 Bot
`- 战略发展部数字员工
   `- securities-industry-report@1

信息技术部 Bot
`- 信息技术部数字员工
   `- information-system-requirement-review@1
```

不将信息技术部 Playbook 注入战略发展部 Profile，不修改历史
`digital_employee_id=industry-report`。信息技术部数字员工使用新的稳定技术
身份 `information-technology`，展示员工编号建议为 `DE-IT-001`。

同一 Bot 内的 Multi-Playbook 注册、权限求交和路由隔离继续由 M2 SDK
的最小测试 fixture 验证。第二个真实部署用来验证跨部门模板复用、
身份授权和独立账本，不为了演示 Multi-Playbook 而混合部门边界。

## 3. Job Charter

| 字段 | 冻结值 |
| --- | --- |
| 展示名称 | 信息技术部数字员工 |
| 技术身份 | `information-technology` |
| 建议员工编号 | `DE-IT-001` |
| 使命 | 依据授权材料、部门规范和可追溯证据，辅助完成信息系统需求评审与立项决策准备 |
| 业务 Owner | 信息技术部需求管理负责人；部署时必须绑定稳定员工标识，不由模型推断 |
| 审批人 | 信息技术部指定的立项评审负责人；首版为单审批人，后续再扩展多人评审 |
| 服务对象 | 经身份 Provider 确认且在授权组织范围内的员工 |
| 默认模型 | `deepseek-v4-flash-0731`；模型不是授权、审批或账本真相源 |

## 4. 服务范围

### 4.1 范围内

- 受理新建、改造或整合信息系统的需求；
- 澄清业务背景、目标、用户、范围、边界和预期收益；
- 检查需求、流程、数据、接口、安全、运维和验收材料是否完整；
- 对业务必要性、方案可行性、系统重复、架构影响、数据与安全、
  成本和风险做初步评估；
- 登记证据缺口、待补材料和待决策事项；
- 形成可审阅、审批和交付的《信息系统立项评估报告》。

### 4.2 范围外

- 不代替信息技术部、需求部门、架构、安全、财务或采购负责人批准立项；
- 不把“评审通过”声称为“项目已正式立项”；
- 不自动创建项目编号、预算、采购申请、开发任务或生产变更；
- 不在缺少负责人依据时编造精确工期、预算、人力或收益数字；
- 不绕过部门知识、外部数据授权、确认点、审批和审计。

## 5. 输入合同

首版输入合同建议命名为 `SystemRequirementBrief`，至少包含：

| 字段 | 要求 |
| --- | --- |
| `requirement_title` | 必填，使用业务语言表达 |
| `requesting_org_id` | 必填，稳定组织 ID，不用部门名称子串授权 |
| `business_owner` | 必填，从认证身份或明确选择获得 |
| `business_problem` | 必填，当前痛点及不处理的影响 |
| `objectives` | 必填，期望结果和可验收指标 |
| `in_scope` / `out_of_scope` | 必填，防止范围无界扩张 |
| `target_users` | 必填，用户类型和预计范围 |
| `desired_timeline` | 可选，只作业务期望，不是承诺工期 |
| `affected_systems` | 可选，未知时登记缺口 |
| `data_and_security` | 可选，涉及敏感数据时必须补齐 |
| `acceptance_criteria` | 必填，与建设目标分离 |
| `material_refs` | 可选，只引用员工授权文件和不可变 SourceRecord |
| `approver` | 必填，从正式身份映射获得 |

缺少业务问题、目标、范围、验收标准或审批人时只能保存为
`provisional`，不能进入评估和审批。

## 6. 评估模型与证据

需求评审至少覆盖：

1. 业务必要性和目标可衡量性；
2. 与既有系统、在建项目或已批规划的重复与复用关系；
3. 业务流程、功能和非功能范围；
4. 架构、集成、数据、权限、安全、合规、运维和灾备影响；
5. 工作量、资源、采购、预算和计划的初步依赖；
6. 主要风险、待补材料、待决策事项和建议前置条件。

证据优先级为：员工授权材料 -> 信息技术部已批规范与台账 ->
企业系统的只读数据 -> 经员工明确授权的外部公开信息。
外部资料不得覆盖内部制度，所有评估结论必须可追溯到证据或明确标注
“待核实”。

## 7. 合同与检查点

M2 SDK 设计时使用以下逻辑合同名；M3 实现时再决定是否需要 schema
rev12，不在 M0 预先创建空表：

```text
SystemRequirementBrief
-> RequirementAssessment
-> InitiationRecommendation
-> InitiationApproval
-> InitiationArtifact
-> Publication
-> Delivery
```

- `SystemRequirementBrief` 由需求发起人精确确认；
- `RequirementAssessment` 登记维度结论、证据、缺口和风险；
- `InitiationRecommendation` 只能表达建议立项、补材料后复评、合并到既有
  项目、调整范围后立项、暂缓或不建议立项；
- `InitiationApproval` 只表示指定审批人审批了当前建议版本；
- 审批不等于项目已在下游系统正式立项；
- Artifact、Publication 和 Delivery 继续分离，不自动链式推进。

## 8. 交付物

《信息系统立项评估报告》至少包含：

1. 需求概述；
2. 业务背景、必要性和目标；
3. 现状、痛点与既有系统关系；
4. 范围、用户和验收标准；
5. 候选方案与建议方向；
6. 架构、集成、数据、安全和运维影响；
7. 成本、资源和周期的初步依赖；
8. 风险、缺口、待补材料和前置条件；
9. 立项建议及待决策事项；
10. 审批意见和版本记录。

首版只交付 DOCX。PDF、XLSX、PPTX、图表生成、项目系统写入和预算
审批不在范围内。

## 9. 路由冻结

| 类型 | 冻结值 |
| --- | --- |
| `playbook_id` | `information-system-requirement-review` |
| 显式服务名 | 信息系统需求评审与立项评估 |
| 可用别名 | 系统需求评审、IT 需求评审、立项评估 |
| 独占命令词 | `SystemRequirementBrief`、`InitiationRecommendation`、`需求评审任务状态` |
| 否定和疑问 | 不得触发写操作 |
| 歧义 | 同时匹配多个服务时必须澄清，不由 LLM 静默选择 |

“帮我看一下需求文档”默认为普通文件分析，不静默创建 WorkItem。
“请启动信息系统需求评审与立项评估”才是显式正式服务请求。

## 10. 验收 Oracle

### 10.1 正向样例

员工消息：

> 请启动信息系统需求评审与立项评估。需求是建设统一数据标准管理平台，
> 当前标准分散在多个部门和文档中，希望今年完成立项。

期望：

- 路由到 `information-system-requirement-review@1`；
- 创建独立 WorkItem，不读写证券报告合同；
- 材料不足时建立 provisional `SystemRequirementBrief` 并询问必需字段；
- 精确确认后才开始评估；
- 先使用授权文件和信息技术部知识，外部搜索必须明确授权；
- 生成有证据、缺口和风险的立项建议；
- 只有指定审批人能批准当前版本；
- 审批后才能渲染、发布和交付 DOCX。

### 10.2 负向样例

- 战略发展部员工尝试读取 IT 需求任务：拒绝，不暴露任务是否存在；
- 信息技术部员工只说“分析这个 Word”：普通文件分析，0 WorkItem；
- 模型声称“已正式立项”：守卫拦截，事件只保留 digest；
- 缺少审批人或验收标准：不能确认 Brief；
- 未授权外部搜索：0 外部 MCP；
- 错版本、否定、疑问或通用“确认”：不推进合同；
- 评审通过后诱导声称“项目已建立”：拦截，不写下游系统。

### 10.3 平台回归

- 信息技术部和战略发展部数字员工的 Profile、PackSnapshot、WorkItem、
  合同、SourceRecord、Artifact 和 Delivery 互不可见；
- 模板生成的新项目自带 Profile、Capability、Playbook、权限和路由测试骨架；
- 同 Bot Multi-Playbook fixture 仍验证当前任务绑定、确定性选择和歧义澄清；
- 默认模型为 `deepseek-v4-flash-0731`，精确动作和账本真相仍由服务端执行；
- 证券行业报告 v0.1.1 全生命周期零回归。

## 11. 已知边界

1. **组织授权**：当前实现仍有展示名称匹配逻辑。M1 完成稳定组织 ID、
   成员关系和 Identity Provider Registry 前，不上线信息技术部生产服务。
2. **单实例运行时**：队列、stream ownership、msgid dedup 和 in-flight lease 主要
   是进程内状态；重启恢复和多实例接管属于 M4。
3. **队列背压**：默认是一条 active turn 加最多三条 pending。超出容量的
   消息会得到明确拒绝终态，不进入 Agent；不应把“任意 N 条 burst 都入队”
   作为 exactly-once 承诺。压测需为预期 burst 显式配置足够余量，并同时
   验证拒绝路径。
4. **下载身份**：当前 signed-link 是 recipient-bound、短时和一次性授权，
   浏览器侧 OIDC、SAML 或企微网页身份校验在企业 IdP 确定前延后。
5. **任务结束**：`delivered` 用于当前任务持续修订，会继续占用同一
   requester/digital-employee/playbook scope。正式归档与新建独立任务放在 M5。
6. **事实核验**：证据绑定不等于独立人工核验。Claim reviewer、来源冲突和
   待解问题的治理仍属于 M5。
7. **输出格式**：当前正式 Artifact 聚焦 DOCX，本 Playbook 首版不扩展 PDF、
   XLSX 或 PPTX。
8. **测试身份**：活体验收必须使用已授权的信息技术部账号。
   smoke override 只能临时修改并升级 `-mac-smoke.N` Pack 版本，不得提交。
9. **状态呈现**：摘要状态已业务化；Artifact/Publication/Delivery 的详细
   联合查询仍可能展示偏技术的账本字段，在 M4 观测与运维收口时优化。

## 12. 实施顺序

1. M0：冻结本文业务合同和现有限制；
2. M1：先完成稳定组织 ID、requester scope evaluator 和 Identity Provider Registry；
3. M2：提炼 Playbook/Capability SDK 和模板扩展测试骨架；
4. M3：使用新 SDK 实现信息技术部数字员工和首个 Playbook；
5. M4：持久化会话控制面、增加 readiness 与运行指标；
6. M5：完成下载身份、事实核验、归档和人工接管。

M1 完成前不为赶活体验收而放宽部门名称子串授权。M2 完成前
不复制证券报告 Composition 或 Output Guard 来快速搭建新服务。
