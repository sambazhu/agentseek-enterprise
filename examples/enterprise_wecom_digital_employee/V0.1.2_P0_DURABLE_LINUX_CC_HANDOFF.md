# 验收 P0 第二轮长期记忆群聊隔离

将以下任务交给 Linux CC。沿用第一轮的隔离环境、脱敏和报告规范。
本轮交接不授权生产部署、存量清理或主分支合并。

## 1. 拉取版本并同步 GitLab

- 从 GitHub 拉取 `enterprise/v0.1.2-p0-memory-scope` 到独立工作树。
- 必须包含代码提交 `a22d6d51b1340d2573a3f92a3b0088ab9f15fd51`。
- 本轮基于修订报告 `d92184c`；保留“短期键互换已撤回”的修正。
- Mac 侧当前无法访问公司 GitLab，由你普通推送该分支到 GitLab，再核对双端 SHA。
- 如果远端已更新，先核对提交关系；不强推、不覆盖他人改动。
- 检查实际加载路径，尤其是 Enterprise、ContextSeek 和企业样例模块。
- 旧 `.pth` 可能指向生产工作树；必须让目标工作树源码优先加载。
- 本轮同时需要新的 EnterprisePlugin、runtime 和长期记忆工具；不能只覆盖 ContextSeek。

## 2. 核对隔离规则与兼容边界

- 用户已确认：群聊长期记忆按群隔离，私聊继续按员工共享。
- 实现保留原租户、员工边界；群聊额外加入匿名 session_key，不扩展同群跨员工访问权限。
- 私聊 namespace 保持原五段元组：enterprise / v1 / tenant_key / user_key / filesystem。
- 群聊 namespace 为七段：enterprise / v1 / tenant_key / user_key / conversation / session_key / filesystem。
- 四个长期记忆工具与 `/memories/` StoreBackend 共用 namespace 解析函数。
- 新 runtime context 携带 `conversation_type`，由原始入口信封或规范 WeCom session 推导。
- 缺失、未知、冲突类型，或群聊缺少有效 session_key 时，拒绝长期记忆访问。
- 老 runtime context 缺 `conversation_type` 也拒绝访问；不得手动补成 single 来绕过检查。
- 非 WeCom 集成使用不透明 session 时，不能默认视为私聊；报告兼容性阻塞。
- 不迁移、不删除任何旧数据；群聊不回退读取旧员工画像。
- 注意：若旧群标记已污染员工画像，私聊仍可能读取它。补丁不自动消除这种存量污染。

## 3. 重跑本地与真实存储门禁

- 运行 Enterprise、ContextSeek、LangChain、WeCom 四组件及企业样例测试。
- 多目录合并运行使用 pytest 的 `--import-mode=importlib`；核对模块实际加载路径。
- Mac 结果：678 passed、2 skipped、2 个 websockets 弃用警告。
- 两个 skip 分别需要真实 pgvector 和 department-knowledge PostgreSQL 测试库。
- 新文件 `test_durable_conversation_scope.py` 有 16 项用例。
- 新用例先在旧代码得到六项失败，再实现修复；使用真实 SQLiteStore 与工具函数，不调用 LLM。
- 覆盖双向隔离、私聊兼容、旧数据不动、四工具失败关闭、删除/整理范围、并发、StoreBackend 和入口类型传递。
- Mac 未执行本轮生产数据库或企微活体验收，不能将本地结果写成线上通过。
- 另用隔离 PostgreSQL/LangGraph Store，验证三 namespace 的真实长期记忆工具读写及交叉召回。
- 长期记忆 Store 与短期记忆表、ContextSeek pgvector 不是同一个存储接口；勿拿 pgvector roundtrip 替代。
- 重跑第一轮真实 pgvector 隔离门禁，确认语义补丁仍然有效。
- 测试库必须专用；不把生产 URL 当测试 URL，不输出凭据。

## 4. 先查明旧泄漏路径，再做干净活体验收

- 先做最小只读核验：原失败窗口是否有 `durable_memory_write`、`durable_memory_recall` 工具事件？
- 核对长期 Store 的员工 `/employee-profile.md` 是否含原合成群标记。
- 只报告合成标记命中和脱敏 namespace 对应关系，不提交完整员工画像或聊天内容。
- Mac 已用真实 SQLiteStore 复现旧代码的两个群写入、私聊同时召回；这不是线上已调用该工具的证明。
- 现场证据不足时继续写“线上来源未确认”，不要直接归因为上下文聚合层。
- 使用新合成标记和干净的测试员工/会话/存储，防止旧员工画像、短期记忆或语义桶污染结果。
- 不获准使用干净测试环境时标 BLOCKED，不擅自清理生产数据。
- 任何生产重启或切换都先请求用户单独确认，列出影响范围、版本快照、模块路径和回滚计划。
- 活体必须确认工具实际调用和数据库落点，不能仅凭模型回复“记住了”算长期存储成功。

| 用例 | 判据 |
| --- | --- |
| 私聊正向及跨私聊传输 | 写入、精确召回；LC 与自建应用同员工共享旧私聊范围。 |
| 两群正向 | 各自通过长期工具写入并召回新标记。 |
| 六向交叉 | dm、group-a、group-b 两两交叉询问均不披露对方新标记。 |
| 删除和整理 | 仅在专用合成数据上验证，当前群操作不改私聊或另一群的数据。 |
| 文件入口 | `/memories/` 读取不能绕过长期工具的群范围。 |
| 并发和快速切换 | 同员工私聊与双群交错回合，namespace 与回复不串。 |
| 提示词适配与失败关闭 | 原入口类型进入 runtime；未知/冲突信息不能触发员工桶回退。 |

- 仅有数据库落点正确不足以判交叉召回 PASS；还要核对工具返回和手机端最终回答。
- 出现串读立即停止扩散性验证，保存最小脱敏证据；不自动启用全量模型输入 dump 或外部 tracing。

## 5. 校准两个尚待解释的观测

- 私聊 `wecom_turn_started` 在身份解析前使用队列 session，加载记忆在解析后使用 canonical session。
- 原始 open_userid 到解析 userid 的转换可能解释两键差异；只比较两者哈希不同不能判错。
- 请验证同回合转换关系，并区分“预期身份转换”和“错误会话归属”。群 session 不应随员工解析改变。
- 修订报告称 `message_count=16` 是 limit 常量；本分支代码实际发出的是 `len(messages)`。
- Store 查询使用 limit 作为上限，并返回实际结果列表；请核对现场加载文件、对应事件与原查询，修正或补证该表述。
- 上述疑点不推翻群到私聊泄漏事实，也不恢复已经撤回的双群键互换结论。
