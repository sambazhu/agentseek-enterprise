## 3. A：3 个已绑定来源为什么最终没有事实 Claim？

七步链条（每步均有直接证据）：

1. 分块器 `chunk_document`（department_knowledge/ingestion.py:123-127）遇 markdown 标题块即
   flush——标题+元数据块独立成桩 chunk（33–146 字符），正文从后续 chunk 开始；
2. 六问查询共享主题前缀（"报告主题：P1ACC-A 中国证券行业发展趋势研究报告；…"），标题桩与该
   前缀词面强匹配 → top-2 恒选桩（topic 问 keyword 腿直接命中标题）；
3. 词法门是"同句含域词+问题词"的词法检查——标题句"…战略转型…"（证券+转型）、性质行"券商/
   投行内部战略参考"（券商+投行）天然满足 → **桩被当作相关内容放行**；
4. 3 源绑定成功（绑定本身"正确"——确实是该问题词法可匹配的唯一 top-2 内容）；
5. Evidence 摘录=整段 chunk=纯标题/元数据，无一句完整事实陈述；
6. 模型收到的全部证据即这三段桩；按系统提示规则"无相关完整句的章节可省略；claims=[] 合法"
   → 正确返回空批（**模型行为无过错**）；
7. `build_report_draft` 为全部 5 章节生成程序占位 risk claim → draft v1 provisional
   （quality=warning）——**账本行为按设计执行**。

结论：A 组失败=**管道级联的结构性选择问题**（桩 chunk 霸榜 top-2），不是模型/账本/门的偶然故障。

## 4. B：初稿为何未持久化？

- **勘误先行**：draft v1（5 占位）03:02:48 已持久化；未持久化的是 C 吸收后的 draft v2。
- v2 失败机制（三重证据）：模型调用 succeeded（11.2s）→ 若返回空批会合法保存占位 v2（同 v1
  路径）→ v2 合同不存在 ⇒ 模型返回了 ≥1 条事实 Claim；bot 错误文案精确命中
  `build_report_draft` 的语句级校验分支（"完整证据原句…改写或新增判断需人工核验"）⇒ 该 Claim
  未通过逐句归一化全等或语句级 relevance → **全批拒绝、零部分写入**（防改写/防虚构的设计门）。
- 可用证据=33 字符标题桩+288 字符真文 chunk；模型引文与原句未逐字对齐（改写/引号形态/句拼接
  的具体形态**不可复原**——见 §5 证据缺口）。
