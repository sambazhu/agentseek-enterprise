# P1 检索候选与正文准入补修交接

## 核对代码行为

1. F1：每问读取已有排名前四条候选，按顺序过门，最多绑定两条相关结果。
   搜索参数不变；不是扩大至任意全库扫描。现有批量读块仍是一批，载荷增加，
   后续 Evidence 读取及模型 token 可能增加，不承诺端到端零额外调用。
2. F2：正文准入版本 `securities-body-v1`；原领域规则版本仍为
   `securities-content-v1`。排除 Markdown 标题、常见元数据和无正文结构的标题桩，
   不设最短字数门槛；短事实、标题后正文、含数值表格行有正例回归。
   这是词法启发式，不是语义充分性证明；未标记且带标点的标题仍可能误过门。
   数值行仍须符合原有领域及问题规则，完整原句 Claim 校验不放宽。
3. F4a：现有事件流新增 `report.source_admission` 与 `report.draft_validation`。
   仅记录阶段、原因码、排名、版本、数量和带密钥身份指纹，不记录原文、原始参数、
   异常正文。`proposals_received` 记录归一化前提案数量及 fact/inference 数量，
   不应把它称为必然来自模型的输出。原句不匹配与相关性拒绝原因分别记录。
   诊断失败不改变拒绝结果，不向 Work 账本追加诊断事件；此前置外的解析、
   provider、超量输入及合同错误不保证覆盖。指纹不能还原原始引文。

新 Source 的身份和 metadata 含正文准入版本。旧任务 Sources/coverage 未重算，
因此必须用新隔离任务复测，不得宣称历史数据已修复。现有可读 chunk 无需重导
即可受益，但之前已清空的验收 collection 不能假定仍然存在。

## 复测与判定

- 固定候选：前两条标题桩、第三四条正文，确认只绑定后两条；第五条不读取。
  四条均无关时零绑定；前两条已相关时总绑定仍至多两条。
- 正反例：IT 制度零绑定；证券短事实、带正文标题及数字行不因长度误杀。
  真实资料需要人工逐条复核领域、研究问题和引用充分性，不能仅看 coverage。
- 初稿：对照六问 template v2.0.0 分别统计候选、准入源、Evidence、事实 Claim、
  占位及缺口，章节数量不能当作问题分母。至少追踪一条真实完整原句到 Claim。
- 守卫：缺 Evidence、非完整原句、原句不相关仍全批拒绝；账本零部分写入。
  诊断区分零提案与非事实提案被程序替换；诊断 sink 故障不影响守卫。
- 回传真实调用数、读取量、首次生成结果与人工评审，不以合成正例替代业务通过。
  用户仍为业务评审人；第二账号如需再测，重新确认窗口。
