## 5. WebUI / CubeOps 路由隔离（定点缺口一）

### 5.1 源码事实（v0.7.0）

- `CubeOps/internal/server/server.go`：`Group("/api/v1")`=公开（login/refresh）；
  JWT 组挂 `/api/v1/sdk` 与 `/api/v1/sdk/v2`；`Group("/internal/v1")` 与
  `/internal/v1/node-agent` **无鉴权**，源码注释明确
  "must not be exposed through nginx or a public Bind address"；
- `deploy/one-click/webui/nginx.conf`：WebUI 对上游做路径**改写**（见 5.3）；
- `up-webui.sh` L25-30：`WEB_UI_UPSTREAM`/`CUBE_OPS_UPSTREAM`/`SANDBOX_PROXY_UPSTREAM`
  均为 env 覆盖（默认 `http://host.docker.internal:3010`）。

### 5.2 来源隔离（不依赖"监听地址=来源"的谬误）

- **专用 docker 网络**：启动 support/webui 前先
  `docker network create --driver bridge --subnet 172.29.0.0/24 cube-webui-net`
  （先建先占，防 compose 自动分配占用该段）；
- cube-webui 启动后 `docker network connect cube-webui-net cube-webui`；
- 过滤代理**仅监听 172.29.0.1:13010**（该网络网关）+ server 块内
  `allow 172.29.0.0/24; deny all;`——该子网内**只有 cube-webui 一个容器**；
- env 覆盖：`CUBE_OPS_UPSTREAM=http://172.29.0.1:13010`、
  `WEB_UI_UPSTREAM=http://172.29.0.1:13010`（显式 IP，不依赖 host.docker.internal
  解析）；`SANDBOX_PROXY_UPSTREAM` 保持默认 :80（不走过滤代理）；
- 隔离依据链：默认 bridge（172.17.x）容器无 172.29 路由 → 不可达；外部主机对
  宿主私有网关地址无路由 → 不可达；沙箱网络（CubeVS 192.168.0.0/18）默认拒绝
  出站且无 172.29 路由 → 不可达；
- **负向测试**（并入 O4/O5）：(a) 临时容器挂默认 bridge 访问 172.29.0.1:13010 →
  超时/拒绝；(b) 沙箱内同样不可达；(c) .171 直连 3010/13010 → 不可达；
  (d) 12088 从 .171 直连 → 不可达。

### 5.3 URI 映射表（浏览器 → WebUI 改写 → 过滤代理收到 → CubeOps）

| 浏览器路径 | WebUI 改写规则（nginx.conf 原文） | 过滤代理收到 | CubeOps 接口 |
| --- | --- | --- | --- |
| `/opsapi/v1/<x>` | `proxy_pass …/api/`（前缀替换） | `/api/v1/<x>` | /api/v1 公开+JWT 组 |
| `/cubeapi/v1/<x>` | `rewrite ^/cubeapi/v1/(.*)$ /api/v1/sdk/$1` | `/api/v1/sdk/<x>` | JWT /api/v1/sdk |
| `/(sandboxes\|v2/sandboxes\|templates\|snapshots)/…`（带 Authorization） | `rewrite ^/(.*)$ /api/v1/sdk/$1` | `/api/v1/sdk/<x>` | JWT /api/v1/sdk(/v2) |
| `/health` | proxy_pass（原样） | `/health` | 公开 /health |
| `/sandbox/…` | 转发 cube-proxy（**不经 CubeOps**） | — | cube-proxy（本 PoC 在 13001 入口直接 403 屏蔽，§5.5） |
| `/assets/`、`/`（SPA） | 本地文件 | — | — |

**过滤代理白名单（按实际收到 URI 收敛，非浏览器路径）**：

```nginx
server {
    listen 172.29.0.1:13010;
    allow 172.29.0.0/24;   # 仅专用网络（内含唯一容器 cube-webui）
    deny  all;
    location ^~ /api/v1/ { proxy_pass http://127.0.0.1:3010; }   # 唯一业务前缀
    location  = /health   { proxy_pass http://127.0.0.1:3010; }  # 健康检查
    location ^~ /internal/ { return 403; }                        # 显式拒绝
    location / { return 403; }                                    # 默认拒绝
}
```

## 6. 防火墙（定点缺口二）

### 6.1 实测事实（2026-09-08 只读）

iptables v1.8.7（**nf_tables 后端**）；docker `Firewall Backend: iptables`；
`EnableUserlandProxy: true`；DOCKER-USER 空链；ip6tables 正常；nft 原生表
ip/ip6 nat+filter（iptables-nft 兼容层）；**ufw systemd 服务 active 但
`ufw status`=inactive（当前无主机防火墙）**；firewalld inactive。

### 6.2 策略（三向明确）

- **入站**：default deny incoming（v4；v6 见 6.6）；
- **出站**：default allow outgoing（节点需拉镜像/DNS/NTP；沙箱出站由 CubeEgress
  默认拒绝控制，不依赖 ufw）；
- **转发**：ufw 默认策略不动 Docker 的 FORWARD/DOCKER 链语义；本轮仅向
  **DOCKER-USER**（iptables-nft 与 ip6tables 双栈）追加显式规则。

### 6.3 保命序列（有界自动回滚）

1. 预检查：确认 SSH 管理端口=22589（ss 实测）；管理来源=192.10.50.0/24（.171 +
   管理终端所在子网，**待用户确认是否有子网外管理路径**）；
2. `ufw allow 22589/tcp from 192.10.50.0/24` →（8089 见 6.4）→
   `ufw allow from 192.10.50.171 to any port 13000,13001,13080 proto tcp` →
   `ufw default deny incoming`；
3. **回滚定时器先行**：`nohup bash -c 'sleep 120; [ -f /var/lib/cube-poc/ufw_ok ] || ufw disable' &`
   —— 120 秒内未创建成功标记则自动关闭 ufw（有界自动回滚，防失联）；
4. `ufw --force enable`；
5. **立即用全新 SSH 连接验证**（`ssh -p 22589 … exit` 新会话，非观察现有连接）；
   成功 → `touch /var/lib/cube-poc/ufw_ok` 解除定时器；失败 → 等定时器自动回滚
   或走 **vSphere 控制台**（可用性待用户与管理员确认，见 §10）；
6. DOCKER-USER 规则（v4+v6 各一组）：对外部接口拒绝 3306/6379/9000/9001/12088；
7. 发布路径实测：对每个容器发布端口从 .171 发起探测，记录 INPUT（docker-proxy
   路径）与 FORWARD/DOCKER-USER（DNAT 路径）的实际命中（`iptables -L … -v`
   计数前后对照），确认对外全拒。

### 6.4 既有业务放行

`ufw allow 8089/tcp from 192.10.50.0/24`——保持既有业务恢复后的子网内可达性
（现全开放，收敛到子网不改变实际使用面；更细的源收敛属业务方决策）。

### 6.5 既有规则保护

不清空任何既有规则（当前 ufw inactive=无既有 ufw 规则；nft 表为 docker/iptables
兼容层自动生成，不动）；不修改 Docker 自动生成链；不关闭 Docker 防火墙。

### 6.6 IPv6 证据

安装轮先取 `ip -6 addr` / `ip -6 route` 证据：若主机仅有 link-local v6（预期），
记录之；DOCKER-USER v6 规则仍创建（发布端口的 v6 路径防御），ufw v6 随
default deny 生效；不为不存在的 v6 监听创建额外规则。

### 6.7 宿主级变更确认

ufw enable 属宿主级变更：**需用户单独确认**（§10 待确认 1）。

## 7. SDK 数据面 TLS 隧道（定点缺口三）

### 7.1 源码事实

`_filesystem.py`：`http://{sandbox.get_host(ENVD_PORT)}/...`（硬编码 http）；
`_config.py`：`proxy_node_ip`/`proxy_port`（env `CUBE_PROXY_PORT_HTTP` 默认 80）；
`IPOverrideTransport` 仅改连接目标不启用 TLS；SDK 对"远端 http+api_key"发明文
告警（仅告警不阻断）。—— 结论与 Codex 一致：SDK 原生不支持数据面 https。

### 7.2 隧道结构（两跳，Host 路由与 token 保留）

```
SDK(.171) Config(proxy_node_ip=127.0.0.1, proxy_port=13080)
 → http://127.0.0.1:13080       .171 本地转发器【Python asyncio，stdlib ssl，
                                  仅 loopback 监听，随 PoC 启停；不装系统包、
                                  不碰 .171 任何既有服务/网关/venv】
 → https://192.10.50.172:13080  .172 nginx TLS 终止（cert：内部 CA 签发，
                                  SAN 含 192.10.50.172；TLSv1.2/1.3 only）
 → 127.0.0.1:80                 cube-proxy HTTP 数据面（Host 路由）
```

### 7.3 TLS 配置细节（术语区分：CA 信任 vs 公钥 pin）

本方案采用 **CA 信任**（内部专用 CA，仅本轮签发两证书），不做公钥 pin
（可选加固留待后续轮）：

- .172 nginx：`ssl_certificate`（SAN=192.10.50.172）+
  `ssl_protocols TLSv1.2 TLSv1.3`；入口 `allow 192.10.50.171; deny all;`
  （应用层来源限制，叠加 §6 ufw）；
- .171 转发器（Python ssl context）：`cafile=<内部 CA>`（`ssl.create_default_context
  (purpose=SERVER_AUTH, cafile=…)`），`check_hostname=True` 校验
  `server_hostname="192.10.50.172"`（与 SAN 匹配）；**SNI**：连接时传
  server_hostname（同时用于名称校验）——TLS 层名称与 HTTP 层 Host 严格分离：
  HTTP `Host: <port>-<sandboxId>.cube.app` 原样透传（沙箱路由必需，见
  webui nginx.conf 注释同源语义），不参与 TLS 校验；
- 流式转发：转发器按 chunk 透传（不缓冲响应体；请求体亦流式），commands
  长流不因缓冲截断；
- 无重放：转发器对每个上游连接只转发当前请求（无重试逻辑）；副作用请求
  不会被自动重发；
- 失败关闭：隧道不可用/证书错误/名称不匹配 → 转发器拒绝连接或立即断开，
  SDK 收到连接错误；**无明文回退分支**（.172 的 80/443 对 .171 不放行，
  配错也到不了明文端口）；
- 凭据不落日志：转发器不记录任何 header（含 Authorization/X-API-Key/
  TrafficAccessToken），仅记录时间戳/字节数/沙箱 ID 前缀；.172 nginx 该
  server 块 `access_log off`；
- 控制面同规格：`api_url=https://192.10.50.172:13000`，SDK venv 内
  `SSL_CERT_FILE` 指向同一 CA；负向：错 CA / 名称不匹配 / 隧道断开 →
  必须连接失败（三例均测）。

### 7.4 .171 侧约束

转发器仅 127.0.0.1 监听、仅 PoC 期间运行、位于 `/root/cube-poc-client/`，
不安装系统包、不覆盖任何既有配置（.171 现无 nginx），**不重启现网网关**。

SDK `_config.py` 注释原文："CubeAPI only enforces auth when it is started with
an auth-callback URL; in the default deployment no callback is set and every
request passes through unauthenticated."——`CUBE_API_KEY` 仅客户端携带。

执行点（双层）：

1. **主执行点**：控制面唯一远程入口 nginx :13000 强制 X-API-Key（本地密值
   比对，缺失/不匹配 → 401；无外部依赖 → 天然 fail-closed）；
2. bundle 审查确认 `AUTH_CALLBACK_URL` 消费方式：有内建回调组件则叠加启用
   （服务端第二层）；无则以 nginx 执行点为准；
3. CubeAPI :3000 仅 loopback，外部唯一路径=13000；
4. WebUI 管理入口（13001，CubeOps JWT）与 SDK 入口（13000，X-API-Key）
   权限面不同且入口隔离：负向测试含"SDK key 经 13001 无效"与
   "WebUI 会话经 13000 无效"。

### 8.2 O4 跨身份授权（合同处理，需用户确认）

源码事实：v0.7.0 CubeAPI 为**单一共享 key**模型（无每身份 key）；CubeOps 侧
JWT 属 WebUI 管理面。原生无"身份→资源归属"授权。

**提案（验收合同变更，须用户明确确认）**：M0 收敛为**单可信 PoC 身份**
（单一 X-API-Key，仅 .171 PoC 客户端持有）；O4 拆分：

- **O4a（本轮）**：入口认证——缺失/错误 key → 401；直连 3000 → 不可达；
  WebUI/SDK 入口凭据不互通；
- **O4b（移至 Broker 阶段）**：跨身份资源归属授权（A/B 身份跨资源负向）。
  依据：验证手册 §5 尾注"Broker fencing、Work 提交与消息幂等在后续切片验收，
  不能将 PoC 成功计为那些尚未实现的合同通过"——资源归属授权正是 Broker
  fencing 职责。

若用户不确认该收敛，则 O4 原样保留，本轮无法闭环（原生机制缺失），
需另行引入外部鉴权服务（超出 PoC 范围）。

## 9. 硬截止与资源限额（定点缺口五/六）

### 9.1 三层时间预算（严格区分）

| 层 | 值 | 机制 |
| --- | --- | --- |
| 单 VM 执行硬截止 | **120s（冻结值不变）** | .171 客户端墙钟：create 起 120s 到即 `kill()`；不因活动请求刷新 |
| 整轮流程总超时 | 600s | 测试编排层（每 O 项独立计时，超即停止本轮） |
| 销毁确认宽限期 | 30s | 仅用于收集销毁证据（状态/资源/TAP 三件），**禁止**发起新命令 |

### 9.2 断连兜底（独立监督，精确关联）

**节点侧独立监督脚本**（.172，`/root/cube-one-click-v0.7.0/poc-supervisor/`，
root 运行、**不受本轮任何 systemd 限额约束**、与被监督对象不同故障域）：

- 轮询 CubeMaster 本地 API（127.0.0.1:18089）列出沙箱；
- **杀灭条件（两条件同时满足，精确关联本轮 VM）**：模板 alias = 本轮 PoC
  专用别名 **且** created_at + 150s（120s 截止 + 30s 宽限）已过仍存活；
- 仅对该 alias 的沙箱 ID 调用 kill——不触碰其他资源（别名即本轮唯一指纹）；
- .171 客户端退出/链路断开不影响其运行；全程留日志证据。

### 9.3 销毁三件证据

状态=terminated/列表消失；宿主资源回收（KVM 进程退出、cgroup/内存回落、
/data 占用回落，前后快照）；无孤儿 TAP/网络规则（ip link/dmesg 前后对照）。

### 9.4 资源限额汇总账（每项落点 + 证据 + 汇总）

| 对象 | 限额 | 落点 | 证据 |
| --- | --- | --- | --- |
| VM | 1 vCPU / 1GiB | 模板资源字段（构建固定） | template inspect + 运行时 cgroup 读值 |
| cube-master | 512M | systemd drop-in MemoryMax | systemctl show MemoryMax |
| cube-api | 512M | 同上 | 同上 |
| cube-ops | 512M | 同上 | 同上 |
| cubelet | 768M | 同上 | 同上 |
| cube-lifecycle-manager | 256M | 同上 | 同上 |
| cube-egress | 256M | 同上 | 同上 |
| cube-proxy | 512M | 同上 | 同上 |
| nginx（.172） | 64M | 同上 | 同上 |
| mysql 容器 | 512m | compose 渲染补丁 limits | docker inspect Memory |
| redis 容器 | 128m | 同上 | 同上 |
| minio 容器 | 768m | 同上 | 同上 |
| coredns 容器 | 64m | 同上 | 同上 |
| **服务合计** | **4.86Gi ≤ 5Gi** | — | 汇总表 |
| VM（另行） | 1Gi | — | — |
| 既有业务+OS 预留 | ≥3Gi（节点 15Gi−4.86−1≈9.1Gi，充裕） | 不设限 | 前后 free/cgroup 快照 |

- 并发=1，O1 的 A/B 顺序创建、销毁 A 后再创建 B，不提高并发；
- 监督进程（§9.2）不受上表限额约束（否则同故障失效失去清理能力）。

### 9.5 Compose 渲染补丁规程（MySQL/Redis loopback 发布）

保留原始渲染文件（`docker-compose.yaml.orig`）→ 应用补丁（端口映射加
`127.0.0.1:` 前缀 + §9.4 limits）→ 两文件 sha256 登记 → `docker compose config`
校验有效 → 才允许 `up`；若安装器后续步骤重渲染，以补丁规程重放（检测到
.orig 与新渲染一致才重放，防覆盖）；不改上游脚本、不动数据卷、不新增全网绑定。
