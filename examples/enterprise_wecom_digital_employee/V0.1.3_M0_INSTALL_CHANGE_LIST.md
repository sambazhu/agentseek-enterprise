## 5. WebUI / CubeOps 路由隔离（定点缺口一）

### 5.1 源码事实（v0.7.0）

- `CubeOps/internal/server/server.go`：`Group("/api/v1")`=公开（login/refresh）；
  JWT 组挂 `/api/v1/sdk` 与 `/api/v1/sdk/v2`；`Group("/internal/v1")` 与
  `/internal/v1/node-agent` **无鉴权**，源码注释明确
  "must not be exposed through nginx or a public Bind address"；
- `deploy/one-click/webui/nginx.conf`：WebUI 对上游做路径**改写**（见 5.3）；
- `up-webui.sh` L25-30：`WEB_UI_UPSTREAM`/`CUBE_OPS_UPSTREAM`/`SANDBOX_PROXY_UPSTREAM`
  均为 env 覆盖（默认 `http://host.docker.internal:3010`）。

### 5.2 来源隔离（不依赖"监听地址=来源"的谬误）

- **专用 docker 网络**：启动 support/webui 前先
  `docker network create --driver bridge --subnet 172.29.0.0/24 cube-webui-net`
  （先建先占，防 compose 自动分配占用该段）；
- cube-webui 启动后 `docker network connect cube-webui-net cube-webui`；
- 过滤代理**仅监听 172.29.0.1:13010**（该网络网关）+ server 块内
  `allow 172.29.0.0/24; deny all;`——该子网内**只有 cube-webui 一个容器**；
- env 覆盖：`CUBE_OPS_UPSTREAM=http://172.29.0.1:13010`、
  `WEB_UI_UPSTREAM=http://172.29.0.1:13010`（显式 IP，不依赖 host.docker.internal
  解析）；`SANDBOX_PROXY_UPSTREAM` 保持默认 :80（不走过滤代理）；
- **隔离依据（不引用"不存在路由"作为安全依据）**：实际入口接口规则
  （过滤代理监听作用域 + nginx allow/deny）+ DOCKER-USER 入口限制 +
  负向测试实测为准；"默认 bridge/外部主机/沙箱对 172.29.0.1 无路由"
  仅作背景记录（默认路由仍可能把流量送至宿主，故不作为安全依据）；
- **负向测试**（并入 O4/O5，作为隔离判定依据）：(a) 临时容器挂默认 bridge
  访问 172.29.0.1:13010 → 拒绝/超时；(b) 沙箱内访问 → 拒绝；(c) .171 直连
  3010/13010 → 不可达；(d) .171 直连 12088 → 不可达（DOCKER-USER 与
  INPUT 双路径实测，见 §5.4/§6.3-7）。

### 5.3 URI 映射表（浏览器 → WebUI 改写 → 过滤代理收到 → CubeOps）

| 浏览器路径 | WebUI 改写规则（nginx.conf 原文） | 过滤代理收到 | CubeOps 接口 |
| --- | --- | --- | --- |
| `/opsapi/v1/<x>` | `proxy_pass …/api/`（前缀替换） | `/api/v1/<x>` | /api/v1 公开+JWT 组 |
| `/cubeapi/v1/<x>` | `rewrite ^/cubeapi/v1/(.*)$ /api/v1/sdk/$1` | `/api/v1/sdk/<x>` | JWT /api/v1/sdk |
| `/(sandboxes\|v2/sandboxes\|templates\|snapshots)/…`（带 Authorization） | `rewrite ^/(.*)$ /api/v1/sdk/$1` | `/api/v1/sdk/<x>` | JWT /api/v1/sdk(/v2) |
| `/health` | proxy_pass（原样） | `/health` | 公开 /health |
| `/sandbox/…` | 转发 cube-proxy（**不经 CubeOps**） | — | cube-proxy（本 PoC 在 13001 入口直接 403 屏蔽，§5.5） |
| `/assets/`、`/`（SPA） | 本地文件 | — | — |

**过滤代理白名单（按实际收到 URI 收敛，非浏览器路径）**：

```nginx
server {
    listen 172.29.0.1:13010;
    allow 172.29.0.0/24;   # 仅专用网络（内含唯一容器 cube-webui）
    deny  all;
    location ^~ /api/v1/ { proxy_pass http://127.0.0.1:3010; }   # 唯一业务前缀
    location  = /health   { proxy_pass http://127.0.0.1:3010; }  # 健康检查
    location ^~ /internal/ { return 403; }                        # 显式拒绝
    location / { return 403; }                                    # 默认拒绝
}
```

### 5.4 WebUI 发布与 TLS

- 12088 发布口径（修正）：up-webui.sh 以 `-p` **全地址发布**（脚本无 bind
  前缀变量，不改上游脚本）——不是 loopback 发布，对外仅由防火墙限制：
  ① DOCKER-USER 规则用 `-m conntrack --ctorigdstport 12088` 匹配 **DNAT 前
  原始目的端口**（DOCKER-USER 位于 DNAT 之后，仅按宿主端口写 `--dport`
  不保证命中），v4+v6 双栈；② userland-proxy 路径（docker-proxy 在宿主
  监听）由 ufw default deny 的 INPUT 链覆盖（无 12088 放行规则即拒绝）；
  ③ 宿主本机经 lo 访问 127.0.0.1:12088 仍可达（13001 的后端）；
  跨机唯一入口 = 13001（nginx TLS → 127.0.0.1:12088）；
- 13001 TLS（内部 CA，SAN=192.10.50.172）+ WebUI 自身 JWT 登录鉴权；
  bootstrap 初始凭据流程在 bundle 审查确认（首登改密/无默认口令），负向测试
  含"初始/默认凭据必须失效"。

### 5.5 /sandbox/ 浏览器数据代理路径

PoC 不需要浏览器访问沙箱：13001 入口 `location ^~ /sandbox/ { return 403; }`
整段屏蔽；该路径不经过滤代理，与 CubeOps 代理严格分离。

### 5.6 路径归一化与绕过负向测试

全部必须被拒（403）：`/internal/v1/...` 裸路径；`/%69nternal/...`（nginx 归一化
后命中拒绝）；`/api/v1/../internal/v1/...`（归一化后拒绝）；双重编码
`%252finternal`；大小写变体 `/INTERNAL/`（不匹配白名单 → 默认拒绝）；
`/api/v1/sdk/../../../internal/v1/node-agent/...`；未知前缀 `/metrics`、
`/debug`、裸 `/sandboxes`（WebUI 已改写，裸路径不应出现，出现即默认拒绝）。

## 6. 防火墙（定点缺口二）

### 6.1 实测事实（2026-09-08 只读）

iptables v1.8.7（**nf_tables 后端**）；docker `Firewall Backend: iptables`；
`EnableUserlandProxy: true`；DOCKER-USER 空链；ip6tables 正常；nft 原生表
ip/ip6 nat+filter（iptables-nft 兼容层）；**ufw systemd 服务 active 但
`ufw status`=inactive（当前无主机防火墙）**；firewalld inactive。

### 6.2 策略（三向明确）

- **入站**：default deny incoming（v4；v6 见 6.6）；
- **出站**：default allow outgoing（节点需拉镜像/DNS/NTP；沙箱出站由 CubeEgress
  默认拒绝控制，不依赖 ufw）；
- **转发**：ufw 默认策略不动 Docker 的 FORWARD/DOCKER 链语义；本轮仅向
  **DOCKER-USER**（iptables-nft 与 ip6tables 双栈）追加显式规则。

### 6.3 保命序列（有界自动回滚）

1. 预检查与**备份**：确认 SSH 管理端口=22589（ss 实测）；管理来源=
   192.10.50.0/24（**待用户确认是否有子网外管理路径**，§10.4）；
   **ufw inactive ≠ 无已保存规则**——先读取并备份 `/etc/ufw/user.rules`、
   `user6.rules` 及 `/etc/ufw/` 相关配置到本轮证据目录（带时间戳）；
2. 预放行（每条独立合法命令，逐条核验回显）：

   ```bash
   ufw allow from 192.10.50.0/24 to any port 22589 proto tcp
   ufw allow from 192.10.50.0/24 to any port 8089 proto tcp   # §6.4，策略变化需用户确认
   ufw allow from 192.10.50.171 to any port 13000 proto tcp
   ufw allow from 192.10.50.171 to any port 13001 proto tcp
   ufw allow from 192.10.50.171 to any port 13080 proto tcp
   ufw default deny incoming
   ```

3. **回滚定时器先行（每次尝试唯一标记）**：生成 `MARK=/var/lib/cube-poc/ufw_ok.$(date +%s)`，
   记录其路径；启动 `nohup bash -c "sleep 120; [ -f $MARK ] || ufw disable" &`
   并**验证回滚任务已启动**（记录 PID、日志文件首行）；120 秒内未创建该唯一
   标记则自动 `ufw disable`——恢复到安装前状态（inactive），不留下未经确认的
   全机默认拒绝；
4. `ufw --force enable`；
5. **立即用全新 SSH 连接验证**（新开会话执行 `exit`，非观察现有连接是否存活）；
   成功 → `touch $MARK` 解除定时器（并确认定时器进程退出）；失败 → 等定时器
   自动回滚至 inactive，或走 **vSphere 控制台**（可用性待确认，§10.4）；
6. DOCKER-USER 规则（v4+v6 各一组，`--ctorigdstport` 匹配 DNAT 前原始目的端口，
   见 §5.4）：拒绝外部到 3306/6379/9000/9001/12088 的转发；
7. 发布路径实测：对每个容器发布端口从 .171 发起探测，分别记录 INPUT
   （docker-proxy/userland-proxy 路径）与 FORWARD/DOCKER-USER（DNAT 路径）
   的实际命中（`iptables -L … -v` 计数前后对照），确认双路径对外全拒；
   IPv6 先取 `ip -6 addr/route` 证据（预期仅 link-local），按证据建规则。

### 6.4 既有业务放行（策略变化，需用户确认）

`ufw allow from 192.10.50.0/24 to any port 8089 proto tcp`——**这是访问策略
变化**：8089 当前为全地址可达，启用后收敛到子网内。不能断言"不影响实际
使用面"（子网外如存在使用方将被拒），故纳入 §10.4 用户确认项；更细的源
收敛属业务方决策。

### 6.5 既有规则保护

不清空任何既有规则（当前 ufw inactive=无既有 ufw 规则；nft 表为 docker/iptables
兼容层自动生成，不动）；不修改 Docker 自动生成链；不关闭 Docker 防火墙。

### 6.6 IPv6 证据

安装轮先取 `ip -6 addr` / `ip -6 route` 证据：若主机仅有 link-local v6（预期），
记录之；DOCKER-USER v6 规则仍创建（发布端口的 v6 路径防御），ufw v6 随
default deny 生效；不为不存在的 v6 监听创建额外规则。

### 6.7 宿主级变更确认

ufw enable 属宿主级变更：**需用户单独确认**（§10 待确认 1）。

## 7. SDK 数据面 TLS 隧道（定点缺口三）

### 7.1 源码事实

`_filesystem.py`：`http://{sandbox.get_host(ENVD_PORT)}/...`（硬编码 http）；
`_config.py`：`proxy_node_ip`/`proxy_port`（env `CUBE_PROXY_PORT_HTTP` 默认 80）；
`IPOverrideTransport` 仅改连接目标不启用 TLS；SDK 对"远端 http+api_key"发明文
告警（仅告警不阻断）。—— 结论与 Codex 一致：SDK 原生不支持数据面 https。

### 7.2 隧道结构（两跳，Host 路由与 token 保留）

```
SDK(.171) Config(proxy_node_ip=127.0.0.1, proxy_port=13080)
 → http://127.0.0.1:13080       .171 本地转发器【Python asyncio，stdlib ssl，
                                  仅 loopback 监听，随 PoC 启停；不装系统包、
                                  不碰 .171 任何既有服务/网关/venv】
 → https://192.10.50.172:13080  .172 nginx TLS 终止（cert：内部 CA 签发，
                                  SAN 含 192.10.50.172；TLSv1.2/1.3 only）
 → 127.0.0.1:80                 cube-proxy HTTP 数据面（Host 路由）
```

### 7.3 TLS 配置细节（术语区分：CA 信任 vs 公钥 pin）

本方案采用 **CA 信任**（内部专用 CA，仅本轮签发两证书），不做公钥 pin
（可选加固留待后续轮）：

- .172 nginx：`ssl_certificate`（SAN=192.10.50.172）+
  `ssl_protocols TLSv1.2 TLSv1.3`；入口 `allow 192.10.50.171; deny all;`
  （应用层来源限制，叠加 §6 ufw）；
- .171 转发器（Python ssl context，显式 `SSLContext`，见 §11 代码）：
  `ssl.create_default_context(purpose=SERVER_AUTH, cafile=<内部 CA>)`，
  `check_hostname=True` + `CERT_REQUIRED`；`server_hostname="192.10.50.172"`
  为 **IP 类型**——用于证书 **IP SAN** 校验；是否因此发送 DNS 类型 SNI 属
  实现行为，**安装轮实测记录实际行为**（不强求 SNI、不宣称必然发送）。
  TLS 层名称与 HTTP 层 Host 严格分离：HTTP
  `Host: <port>-<sandboxId>.cube.app` 原样透传（沙箱路由必需），不参与
  TLS 校验；
- 流式转发：转发器按 chunk 透传（不缓冲响应体；请求体亦流式），commands
  长流不因缓冲截断；
- 无重放：转发器对每个上游连接只转发当前请求（无重试逻辑）；副作用请求
  不会被自动重发；
- 失败关闭：隧道不可用/证书错误/名称不匹配 → 转发器拒绝连接或立即断开，
  SDK 收到连接错误；**无明文回退分支**（.172 的 80/443 对 .171 不放行，
  配错也到不了明文端口）；
- 凭据不落日志：转发器不记录任何 header（含 Authorization/X-API-Key/
  TrafficAccessToken），仅记录时间戳/字节数/沙箱 ID 前缀；.172 nginx 该
  server 块 `access_log off`；
- 控制面同规格（**requests.Session 调用链**）：`api_url=https://192.10.50.172:13000`；
  仅设 `SSL_CERT_FILE` 不足以证明 requests 使用指定 CA——PoC venv 同时设置
  **`REQUESTS_CA_BUNDLE=<内部 CA>`**（并保留 `SSL_CERT_FILE` 覆盖非 requests
  链路）；**实测两例**：正确 CA → 控制面调用成功；错误 CA（无关 CA 文件）→
  必须连接失败。数据面转发器不受影响（显式 SSLContext，不经环境变量）；

### 7.4 .171 侧约束

转发器仅 127.0.0.1 监听、仅 PoC 期间运行、位于 `/root/cube-poc-client/`，
不安装系统包、不覆盖任何既有配置（.171 现无 nginx），**不重启现网网关**。

## 8. 控制面鉴权与 O4 合同（定点缺口四）

### 8.1 鉴权执行点（源码证据）

SDK `_config.py` 注释原文："CubeAPI only enforces auth when it is started with
an auth-callback URL; in the default deployment no callback is set and every
request passes through unauthenticated."——`CUBE_API_KEY` 仅客户端携带。

执行点（双层）：

1. **主执行点**：控制面唯一远程入口 nginx :13000 强制 X-API-Key（本地密值
   比对，缺失/不匹配 → 401；无外部依赖 → 天然 fail-closed）；
2. bundle 审查确认 `AUTH_CALLBACK_URL` 消费方式：有内建回调组件则叠加启用
   （服务端第二层）；无则以 nginx 执行点为准；
3. CubeAPI :3000 仅 loopback，外部唯一路径=13000；
4. WebUI 管理入口（13001，CubeOps JWT）与 SDK 入口（13000，X-API-Key）
   权限面不同且入口隔离：负向测试含"SDK key 经 13001 无效"与
   "WebUI 会话经 13000 无效"。

### 8.2 O4 跨身份授权（合同处理，需用户确认）

准确表述（不过度断言）：**本方案仅实现共享入口认证（单一 X-API-Key 经
nginx :13000），尚未建立"身份→资源归属"授权**。v0.7.0 默认部署无服务端
鉴权（SDK `_config.py` 注释）；CubeAPI 是否存在其他每身份授权机制**未在本轮
建立或验证**，不作"只支持共享 Key"的断言。

**提案（验收合同变更，须用户明确确认后方可生效）**：M0 收敛为
**单可信 PoC 身份**（单一 X-API-Key，仅 .171 PoC 客户端持有）；O4 拆分：

- **O4a（本轮）**：入口认证——缺失/错误 key → 401；直连 3000 → 不可达；
  WebUI/SDK 入口凭据不互通；
- **O4b（移至 Broker 阶段）**：跨身份资源归属授权（A/B 身份跨资源负向）。

说明：原验证手册 O4 字面（跨身份 Oracle）并未被手册尾注自动豁免；本拆分是
**新提案**。用户确认后的同步动作：更新验证手册 O4 行（O4a/O4b 拆分）并在
Broker 阶段验收项中登记 O4b——由维护者随确认一并落地。若用户不确认，
O4 原样保留，本轮按"入口认证已验证、跨身份未验证"如实记录，不互相替代。

## 9. 硬截止与资源限额（定点缺口五/六）

### 9.1 三层时间预算（严格区分）

| 层 | 值 | 机制 |
| --- | --- | --- |
| 单 VM 执行硬截止 | **120s（冻结值不变）** | .171 客户端墙钟：create 起 120s 到即 `kill()`；不因活动请求刷新 |
| 整轮流程总超时 | 600s | 测试编排层（每 O 项独立计时，超即停止本轮） |
| 销毁确认宽限期 | 30s | 仅用于收集销毁证据（状态/资源/TAP 三件），**禁止**发起新命令 |

### 9.2 节点侧硬截止监督（实现见 §11；与代码一致）

- **硬截止 120s（单调钟 deadline）**：首次观测到平台 startedAt 时换算为
  单调钟截止点；墙钟回拨不延长执行、前跳不提前终止；终止判定与执行前
  均以单调钟复核（不用轮初快照）；30s 宽限仅用于终止确认；
- **终止授权（仅两级，无模板/时间窗兜底）**：本轮 metadata run 标记
  （create 原生参数，响应丢失亦在服务端留痕）或 manifest 精确 ID 登记；
  marker 缺失且未登记 → 只告警阻断新建，**绝不纳入删除集合**（同模板
  也不行）；他轮 marker 始终排除；
- **目标状态保留**：list 失败/畸形响应时**不清空**已知目标（deadline
  与确认宽限计时不重置）；仅"成功且通过 schema 校验的列表"可作为
  "未出现即消失"依据；非法列表响应显式抛错，不静默解释为空集合；
- **告警状态机（按轮重算，可测试恢复条件）**：manifest 无效 / 控制面
  不可达 / 同模板不可归类 / 起始时间未知 / 查询错误 / kill 失败 / 确认
  宽限超时均为显式状态；任一未解除 → 告警文件保持（存在=阻止新建）；
  全部解除且无待确认终止 → 清除；
- **创建门禁（失败关闭 + 最近心跳有效）**：`--gate-check`（exit 0=允许
  /3=阻断）供 .171 建前经 SSH 调用；允许需同时满足：无告警 + manifest
  有效且有 run_id + 最近心跳存在/可读/run_id 匹配/新鲜（过期阈值
  =3 轮 +2 次请求上限 + 余量 ≈31s；监督每轮 poll 写心跳）。**口径**：
  这是"最近心跳有效"校验，不是实时存活保证——监督退出后最迟在心跳
  过期时拒绝，31s 窗口内可能尚未发现退出；未启动（无心跳）/心跳过期/
  旧轮心跳/状态不可读 → 一律拒绝；
- **请求有界超时（单调钟总截止，覆盖连接/状态行/响应头/chunk 控制行/体）**：
  v0.7.0 SDK 控制面调用不传 timeout（源码核对），监督改用 HttpCubeClient
  ——http.client + body 循环 `read1`+剩余预算 + 响应体 4MiB 上限，外加
  **独立看门狗线程**：到点对连接 `shutdown(SHUT_RDWR)`，可中断
  getresponse 内部的状态行/响应头/chunk-size/trailer 读取（这些内部
  readline 在持续滴流下永不触发单次 socket 超时——七次复核复现）；
  看门狗触发的 HTTPException 家族（BadStatusLine/IncompleteRead 等）
  归一为总截止超时；完成即取消看门狗并关连接，不遗留后台任务。
  单请求总耗时 ≤ timeout + 调度容差 ε；最坏终止延迟公式据此成立；
  静默挂起/体滴流/状态行滴流/响应头滴流/chunk 控制行滴流/超限/
  资源回收/正常成功均有测试；
- **最坏终止延迟（如实声明）**：单调 deadline +（本轮在途目标处理时间
  （每目标 ≤1×info+1×kill 请求上限）+ 轮询间隔）；
- **manifest 原子性**：独立 .lock 文件 flock（读共享/写独占）+ 同目录
  临时文件 fsync + os.replace + 目录 fsync；写入校验旧轮拒绝（run_id
  不匹配即拒）；reload 全 schema 校验（含时间为有限数值）；并发读写
  测试保证读方只见完整 JSON；
- 独立性：独立于 .171 客户端与被 systemd 限额的服务；与 .172 整机
  同故障域。

### 9.3 销毁三件证据

状态=terminated/列表消失；宿主资源回收（KVM 进程退出、cgroup/内存回落、
/data 占用回落，前后快照）；无孤儿 TAP/网络规则（ip link/dmesg 前后对照）。

### 9.4 资源限额汇总账（按实际部署形态逐项落点；v4 修正）

**形态事实**：cube-proxy / cube-lifecycle-manager / cube-egress / coredns /
cube-webui(openresty) / mysql / redis / minio 均为 **Docker 容器**（即使由
systemd 单元拉起，systemd MemoryMax 只约束 dockerd 拉起进程本身，不等于容器
受限）→ 容器限额落点 = 容器自身限制；宿主进程（cube-master / cube-api /
cube-ops / cubelet / nginx / 监督脚本）→ systemd drop-in。

| 对象 | 形态 | 限额 | 落点（实际机制） | 证据 |
| --- | --- | --- | --- | --- |
| mysql | 容器 | 512 MiB | compose 渲染补丁 limits（§9.5） | docker inspect `.HostConfig.Memory` + cgroup `memory.max` 实读 |
| redis | 容器 | 128 MiB | 同上 | 同上 |
| minio | 容器 | 768 MiB | 同上 | 同上 |
| coredns | 容器 | 64 MiB | 同上 | 同上 |
| cube-webui（openresty） | 容器 | 64 MiB | 同上（v3 遗漏，v4 补） | 同上 |
| cube-proxy | 容器 | 512 MiB | `docker update --memory 512m --memory-swap 512m cube-proxy`（不改上游脚本） | 同上 |
| cube-lifecycle-manager | 容器 | 256 MiB | docker update 同上 | 同上 |
| cube-egress | 容器 | 256 MiB | docker update 同上 | 同上 |
| cube-master | 宿主 | 512 MiB | systemd drop-in MemoryMax=512M | systemctl show + cgroup 实读 |
| cube-api | 宿主 | 512 MiB | 同上 | 同上 |
| cube-ops | 宿主 | 512 MiB | 同上 | 同上 |
| **cubelet（含 VM）** | 宿主 | **1536 MiB = VM 1024 + 引擎 512** | systemd drop-in；**VM 进程属 cubelet cgroup 子树**（bundle 审查确认归属），限额已含 VM，不与模板限额重复计算 | cgroup 子树实读（cubelet 与其下 VM 进程） |
| nginx（.172） | 宿主 | 64 MiB | systemd drop-in（nginx 无自带单元则 noc + drop-in） | 同上 |
| 节点监督（§9.2） | 宿主 | **不设硬上限**（刻意：不得与被限额/被终止对象同失效）；容量预算估算 ≈64 MiB 仅作参考，非限额 | 独立运行（无 drop-in） | 进程驻留 RSS 实测记录 |

**汇总（MiB，逐项相加）**：容器 2560（512+128+768+64+64+512+256+256）；
宿主 3200（512×3 + 1536 + 64 + 监督 64 预估不计入上限）——
**服务合计（不含 VM）4736 MiB = 4.625 GiB ≤ 5 GiB**；**含 VM 合计
5760 MiB = 5.625 GiB ≤ 原冻结合并上限 6 GiB（服务 5Gi + VM 1Gi）**；
预留 = 15360 − 5760 − OS/既有业务（实测峰值 <1Gi）≈ **8.6 GiB ≥ 3 GiB**。
（v3 的"4.86Gi"为遗漏 webui/监督 + 单位换算错误，已修正。）
.171 侧转发器 ≈64 MiB，独立机器，不计入 .172 账目（单独实测记录）。

- 并发=1，O1 的 A/B 顺序创建、销毁 A 后再创建 B，不提高并发；
- 所有限额以**安装后实测 cgroup 值**为证据（systemctl show / docker
  inspect / `/sys/fs/cgroup/.../memory.max` 三方对照），不只写预算数字；
- cubelet 限额与 VM 归属关系在 bundle 审查时以进程树/cgroup 实测确认，
  若 VM 不在 cubelet 子树则单独为 VM 运行进程设置限额并重算汇总。

### 9.5 Compose 渲染补丁规程（MySQL/Redis loopback 发布）

保留原始渲染文件（`docker-compose.yaml.orig`）→ 应用补丁（端口映射加
`127.0.0.1:` 前缀 + §9.4 limits）→ 两文件 sha256 登记 → `docker compose config`
