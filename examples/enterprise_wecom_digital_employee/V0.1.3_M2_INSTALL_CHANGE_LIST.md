### 2.1 BLOCKED 缺陷：超限请求在 Linux 收到 RST 而非 request_rejected

- 失败测试：`test_broker_runtime.py::
  test_oversized_request_and_response_rejected`（3.10 与 3.13 均红；
  Codex 本地 3.10.20/3.13.3 各 157 passed——**开发环境内核差异**，
  与 M1 的 py3.10/3.13 标准库分叉同型教训）；
- 根因（源码+最小重现定罪）：`broker_wire.serve_connection` 读满
  `MAX_REQUEST+1` 字节即拒绝并 `sendall(request_rejected)`，但客户端
  发送的剩余字节（如结尾 `\n`）仍留在服务端接收缓冲——**Linux 对
  close 时带未读数据的 socket 发 RST，且 RST 丢弃客户端已缓冲的
  响应**。最小重现（socketpair 直驱 serve_connection）：
  - A 发 65537B+`\n` → 客户端 `ECONNRESET`（响应不可达）；
  - B 同载荷+客户端先 `shutdown(SHUT_WR)` → 仍 RST（服务端接收
    缓冲残留不变）；
  - C 恰 65536B+`\n`（不超限、非法 JSON）→ 正确收到
    `{"ok":false,"error":"request_rejected"}`（响应路径本身正常）。
- 影响：运行合同"超限/参数错误统一在线路上 request_rejected"在
  Linux 部署目标上**不可观察**（B8 类负向验收同样会踩）；
- 修复建议（由 Codex 裁定）：服务端 `sendall` 响应后做**有界 drain**
  （受 budget 与字节数上限约束循环 recv 至 EOF/上限）再返回，使
  close 走 FIN；drain 上限防洪泛，超限直接 close（此时 RST 可接受）。
  测试不应改判（手册禁止换条件放行）；
- 恢复判据：双解释器 157 passed 后重跑本表全部门禁。
