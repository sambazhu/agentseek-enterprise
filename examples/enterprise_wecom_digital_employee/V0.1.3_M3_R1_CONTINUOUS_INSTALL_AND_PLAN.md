## 三、判定 B：新轮次状态方案（只读规划，未物化任何状态/目录/token）

**1. 标识与生成时机**：拟议新 run_id（如 `agentseek-m3-r2-20260917`，最终由用户批准定名）与每槽
create_token 均由受信安装方在新轮材料准备时生成（同本轮模式：token 私有、摘要入册），批准时机=
用户对新轮材料（request/approval/preapproval/chain）的逐项审阅；不预设"换 run_id 即可重建"——
新轮创建仍需全套 approved=true 材料+窗口+执行授权。

**2. 监督绑定与所需变更（§8 重点）**：新 run_id 与现役 manifest（agentseek-m3-r1-20260917，含已登记
sandbox a934cee2…）**必然不匹配**——合同上 A 型创建（schema-2 首槽）要求 SupervisorReader.read_empty
（manifest sandboxes=={}），旧 manifest 已有登记且"重登记清空历史"被原始合同禁止；复用旧 run_id 的
新 A 因此**合同性不可行**。合规路径=**第二监督服务设计**：
- 变更内容：新 run 专用 supervisor 目录+manifest（register-run 于服务启动前）；新 unit
  （如 agentseek-m3-r2-supervisor.service，UMask=0077、脚本内 120s 冻结值、固定解释器=89be61f venv
  python -I、原样 node_supervisor.py 副本摘要 b5d66db5…、不 enable）；为新服务生成新 IdentityPins
  （新 unit/argv→新 pins，0600 存档，供新轮 precreate 引用）。
- 影响对象：仅新增 unit/目录/pins；**旧服务/旧 manifest/旧 pins 零改动**。
- 回退：新轮未创建或结束后 systemctl stop 新服务即可（目录留审计）；旧服务始终不动。
- 批准点：新 run_id 与第二服务的创建+启动须用户明确批准（列入 §四清单第 1 项）。
- 不现场修改任何 pins/manifest/unit/启动参数以使检查通过（本轮零改动）。

**3. 目录作用域**：新轮独立根 /var/lib/agentseek-m3/runs/<新run>/ 下 supervisor/vault/fence/quota/
tracking-A/tracking-B/config/receipts（本轮模式复用）；continuous 入口另需四个空互斥目录
（continuous/lifecycle/output/dispatch）。**全局共享**：平台本身（guest 集合）、控制面凭据受控源
（CA 目录与 api_key 受控源/已物化件可被新轮链引用——key 为平台级凭据与 run 无关）、用户批准权、
（可选）监督脚本副本。**按轮独立**：manifest/pins/vault key/额度/fence/W0 窗口/全部配置与回执。

**4. 与旧 A 的关联与防绕过**：旧额度（slot-0 已耗）与结束证据（closeout）留存于旧 run 目录树作为
历史，仅作文档级关联（报告/审计），新轮不触碰不重置。**防绕过机制如实**：现行合同**无跨 run 全局
额度**——技术护栏为①每轮 approved=true 材料仅经用户批准；②precreate 的 collect_empty 要求**平台
guest 列表为空**（任何来源的未批准并发 guest 会阻断新轮创建=真实并发闸）；③每 run 监督 120s 硬截止
各自生效；④W0 每轮重新确认。若需"总创建次数硬上限"属跨 run 全局状态设计变更，建议交 Codex 评估
（本轮不阻塞，标注为设计建议）。

**5. batch_sequence（§9）**：新轮安装预登记 [A',B'] 两计划（合同要求 2/4 序列，token 唯一）；
B' 仅为计划约束——不生成 B 批准、不执行 B、不消耗 B 额度（reserve 时才落 slot 文件）；B' 创建被
claim_successor/launch_successor 门禁约束为必须 A' slot-result 五行成功，**不以 B 绕过 A' 未完成矩阵**。

**6. 下一轮待用户批准清单（§10）**：①新 run_id+第二监督服务（unit/登记/启动）；②新轮 W0（writer
