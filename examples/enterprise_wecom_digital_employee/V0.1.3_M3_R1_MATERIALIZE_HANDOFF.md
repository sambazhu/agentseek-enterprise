# M3 R1 预批准配置生成器离线复验

## 1. 固定范围与候选

固定代码 `5d3c27bf1d5d15e0ad09f0ff1fcd6e3e8a70cfdc`，基线 `dbe129d`。
wheel SHA256：`188a0d2cdcd9705befe916a9b850e8791b81471ca88d455a8c97d9b94df9fceb`。
本轮只备料、独立离线安装、合成资料测试和合同审阅；不更新现用 be59e54 入口，
不生成现场有效预批准，不读取现场凭据，不调用真实平台、lifecycle 或 slot。
测试中 synthetic 批准为 true 仅用于本地 fixture，与现场批准严格分离。

## 2. .171 备料交接

1. 核验双远端、基线与固定候选。按 SLOT_HANDOFF 的隔离方法备料，不从浮动 HEAD 构建。
2. 用本候选 inventory 生成源码/测试闭包和 runtime 包项目，离线构建并核验 wheel。
   新清单 8 入口、35 运行模块；必须使用本候选安装检查工具。
3. 备齐固定运行依赖和完整测试依赖，生成逐文件 SHA256 清单。
   不含现场凭据/配置，不修改候选；缺依赖即停止，不联网补包。
4. 按既有批准通道交接给 .172，不写其安装/运行目录，不代为操作服务。

## 3. .172 独立复验

1. 先验证到货摘要，使用新 scratch、独立运行/测试 venv，全程 offline、零 Git。
   不覆盖 /opt/agentseek-m3-releases/be59e54，不改现用入口、服务、监督或 pins。
2. 新运行 venv 的 python -I 安装检查预期 35 模块摘要匹配、8 无效入口拒绝。
3. 新源码闭包测试预期 799 passed；清单工具 5 passed。
   本地基线为 macOS Python 3.12，Linux 记录实际环境，不混记。
4. 新入口 help 为 --preapproval / --sha256；仅 help 和无效输入，不传现场配置。
5. 按 test_m3_materialize 的合成 fixture 核对 A 五行、B 六行及 X1：
   输出须能被已有 read_approval、prepare_receipted 读取；不发送请求。
   若另做三轮计时，只调用交付生成器处理独立 synthetic fixture；不得以旧辅助程序速度冒充。
6. 核验失败路径：未批准、未明确委托、过期、跨 boot/创建身份、错误 pin、重复 case、
   密封回执缺失、途中预批准/回执变化、写盘失败；不得输出完整成功清单或自动续写。

## 4. 审阅预批准合同

该合同新增显式“生成精确逐行审批”的委托；不是泛化模板替换器。
文件须由受信安装方准备，用户另批后独立钉 SHA256；工具不为自己授予权限。

- 顶层精确字段：schema=1、approved、materialize_exact_rows、expires_epoch、slot、
  reserve_seconds、expected_create、create_result_file、receipt_source、installation、
  output_directory、dispatch_directory、case_ids、approval_refs。B 另有 previous_slot、donor。
- approved 和 materialize_exact_rows 必须显式 true；false 草稿不可运行。
  本工单不授权填写任何现场 true 文件。expires_epoch 不延长，reserve 无默认值。
- expected_create 是预先批准的完整 CreateBinding，intent_sha256 固定全零占位；
  实际 intent 只从创建输出读取并经 vault.read_intent 校验，sandbox ID 只从密封回执取得。
  其他创建身份字段必须逐项一致，同机 boot 必须匹配。
- receipt_source 只含 vault_directory/vault_key_file/api_key_file/domain/proxy_port；
  不允许调用方额外指定 create 或任意 token 替换。
- installation 包含 supervisor_directory/supervisor_identity/control/plan/template_pins/
  exclusive_window/create_request_file；全部为预先固定上下文，不自动补网络、身份或 W0。
  control 含现有合同的 api_key 正文，因此预批与输出安装文件必须保持私有，禁止入 Git/报告。
- case_ids、approval_refs 数量及唯一性固定；矩阵不由用户 JSON 自定义：
  A=E1正确/E2正确/E2错值/E3正确/E3缺失，B 加 E1/e2b X1。
- B 的 donor、previous_slot 按既有 X1/slot 合同固定并复核 A 成功记录。
  B 预批应在 A 结束后、B 创建前准备；本工具不生成 B 创建安装文件或 B 创建批准。
- 输出目录应为新建空私有目录，与 dispatch/vault/key 父目录分离；
  独占写 materialize-intent 后依次写 probe/approval/installation，最终才发布 slot.json 和结果清单。
- 生成的行 approval 为现有 schema 1 的精确 Binding、approved=true、固定 expiry。
  这是已批准委托的机械展开，不是将未批准草稿翻成 true。
- 全部生成成功必须有 materialize-result.json，且调用方核验其中 slot 路径与摘要。
  失败可能留有部分行审批文件；这些不等于完整交付，不得手工抽取执行或拼成另一槽配置。
  目录保留审计，不删除 intent 后重跑，不自动改用新目录规避失败。

## 5. 验证边界与待决

生成器零网络、零创建、零探针，不证明 W0/监督/模板/当前平台状态；这些仍由执行入口实时验证。
当前测试证明生成结果兼容已有审批/回执读取器，不是完整 slot→case→真实平台的端到端证明。
严格 installation 上下文的运行合法性仍需完整执行门校验，不可把“JSON 生成成功”叫配置验收通过。

本次不实现一键 create→materialize→slot，不自动批准 B，不绕过 UNKNOWN。
现场准备 B create 安装及预批模板的具体流程若仍有合同缺项，列 BLOCKED_IMPLEMENTATION 交回，
不得临时拼执行器。真实生成耗时、平台耗时、余量值及现场审批仍待批准。
5 秒只是未批准的建议值；BUDGET_ADJUDICATION_PENDING 维持，非 M3_READY。
