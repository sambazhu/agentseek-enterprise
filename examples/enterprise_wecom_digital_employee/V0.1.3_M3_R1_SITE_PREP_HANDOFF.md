# M3 R1 两阶段现场准备与真实窗口批准点

## 1. 确认当前授权

用户本次仅批准阶段一：安装 M3 独立副本、准备私有材料与禁用的批准草稿、核验现场。
阶段二真实创建/终止 guest、进程探针及矩阵发送，仍需用户再次批准。
不能以“确认准备”生成 `approved=true` 或声明 W0 已接受。

固定代码 `aa9e1e55bb04a5246673b9f63a8fc387647697b8`；
沿用 `52677d1e31eac637a8c641f8f43e711bfb8bf4ee` 的 `R1_LAUNCHER_OFFLINE_PASS`。
不重复 741 项测试；移至另一主机或新 venv 时须重新验证安装来源/32 模块摘要/5 无效配置拒绝。
不修改 production、标签、网关、MCP、DB、WORK、M0/M2 服务或旧 manifest。

## 2. 阶段一先核对拓扑，未满足不得安装

1. 只读核对 production 完整 SHA，确认是否仍为此前 `b226413`。
   用户回执中的 `b224 613` 疑似笔误；核实后只纠正文档，不切换代码。
2. 查明准备运行 launcher 的主机以及 M3 supervisor 主机。
   当前 `SupervisorReader` 读取本地私有文件，`verify_identity` 读取本机 `/proc`、boot ID 和 systemd。
   二者必须同机；不支持复制远端心跳、伪造 PID 或由 SSH 输出替代本机身份。
3. 预期节点监督在 .172；若 launcher 尚仅装在 .171，则先回报 `BLOCKED_TOPOLOGY`，
   列出在 .172 安装独立执行环境所需动作，等待拓扑变更批准。
   不自行把节点监督搬到 .171，也不新增远程调用协议。
4. 同机条件满足后，核验控制面 TLS/CA、数据面 loopback 代理端口、模板摘要与既有路由。
   不修改隧道、firewall、hosts、代理或凭据权限来绕过失败；缺少已批准路径则停止。
5. 实查 guest=0，确认拟用新 run ID 从未用于现有 guest、账本或旧 manifest。
   若非空或无法确定，停止；不能清理现有 guest 取得空列表。

## 3. 阶段一安装独立监督与私有目录

仅在第 2 节通过且安装主机处于已批准拓扑内执行：

1. 清点拟用 `/opt/agentseek-m3-supervisor`、`/var/lib/agentseek-m3`、`/etc/agentseek-m3`。
   路径已存在时只读盘点并回报，不覆盖、重置或递归 chmod。
2. 在新建 M3 专用子目录安装原样 `node_supervisor.py` 与候选独立 venv；
   不借生产 venv，依赖仅用已批准离线来源，缺项停止。脚本 root 所有、0600、父目录 0700。
3. 每个 run 使用独立 supervisor、vault、fence、quota、tracking-A、tracking-B、配置与回执输出目录。
   私有目录 0700、文件 0600；tracking 不与其余目录互用。
   密钥仅按既有授权安全复制或为新 vault 本地生成，不打印、不入 Git、不复用历史 traffic token。
4. 新建 `agentseek-m3-r1-supervisor.service`，root、UMask=0077、原 120 秒截止、固定解释器与脚本。
   使用独立 manifest/heartbeat/alarm；不得与 M0/M2 共用或改其 unit。
   若 unit 已存在，停止核对，不覆盖。凭据不能写入可公开读取的 unit 或命令日志。
5. 在仍为 guest=0 时，为新独立 manifest 登记本轮 run 与精确模板；不得重登记已有 run 以清空历史。
   启动新 M3 服务但不 enable 开机自启。只允许读取当前空平台，不执行测试创建来证明监督可用。
6. 核对真实心跳、无告警、MainPID、boot、start_ticks、可执行文件/脚本/unit/cmdline 摘要。
   根据实际进程生成 IdentityPins；不手填猜测 PID 或借用 M2 心跳。
   摘要材料需匹配候选的本机身份读取合同；不打印 argv 中的秘密。

## 4. 阶段一准备配置，不生成有效运行批准

按 `V0.1.3_M3_R1_LAUNCHER_HANDOFF.md` 准备 A/B 私有配置草稿与清单。
只用当前真实安装路径与来源可核验的完整摘要；候选 SHA256 与 Git SHA 分开标注。

- A/B 两槽均 restricted，固定 sequence，create_token 唯一，quota/fence/vault 共用本轮目录。
- A schema 2；B schema 3 的 previous_create 与 A 输出尚未知，标为待生成，不能伪造 binding/intent。
- approval 草稿 `approved=false`、`w0_accepted=false`；不把用户准备批准转换为创建批准。
- W0 仅登记责任人、所有已知创建入口与拟议时窗；禁创确认不齐不得声称有效。
- 各槽 approval/precreate/create/launcher 文件独立保留，不覆盖 A 来准备 B。
- A 成功输出保存方案必须是 root 私有、完整性核对、独立摘要；保存不确定时停止，不重跑创建。
- 不执行 launcher 的有效 `--config`、`--attach`、`--closeout`，不占用 intent/fence/quota。
- 如需脚本生成现场材料，只能生成禁用草稿并人工核对；不得增加创建、批准或探针发送逻辑。

本阶段批准草稿不可运行，因此不能用“有效预检全部通过”作为验收条件。
报告区分安装/身份已核验与批准/动态绑定待阶段二生成。

## 5. 回传阶段一结果并停止

提交 `V0.1.3_M3_R1_SITE_PREP_RESULTS.md`，只提交脱敏报告：

- production SHA 核实与笔误处置；拓扑是否满足本机身份合同。
- 实际新建路径、服务与副本摘要，启动前后 guest 数、M0/M2 状态及新服务心跳。
- 禁用配置清单、未填的动态字段、未批准的动作与依赖缺项。
- W0/G2 待确认事项，以及每一项现场新增对象的回退方案。
- 下一轮逐行矩阵：精确 E1/E2/E3 端点、头别名、正确/错误/缺失/跨 guest 状态、阳性对照、
  调用次数、当前实现的超时上限与总预算。不能只写“guest 数据面”或“≤6 秒”。

未覆盖的另一别名、端点、UID、本地访问或 public 行明确 NOT_RUN，不写“无需 NOT_RUN”。
两 guest 均最多一次创建，串行；B 的 X1 算入 B 预算，不将其遗漏。
原 M2 勘误继续有效：未识别的 X-Access-Token 403 不是识别头错误值拒绝证据。

结果只记 `SITE_PREPARED_PENDING_APPROVAL` 或具体 BLOCKED，不记 M3_READY。
普通推送执行分支核验双端；不合并 production。

## 6. 阶段二批准点（本次禁止执行）

用户审阅阶段一结果后，逐项批准主机/窗口、独立监督部署终态、A/B 创建额度、
restricted 模板与网络、探针矩阵及终止权限、W0 责任人禁创确认和停止预算。
届时才能将批准材料置为有效、固定摘要并生成精确执行命令。
本页不是阶段二执行命令集；有未解决安装或拓扑缺口不得进入创建。

阶段二拟议顺序：重新实时预检 → A 创建/登记 → A 获批探针 → 监督结束/closeout →
独立固定 B 材料 → B 实时后继门禁/创建/登记 → B 获批探针及 X1 → B 结束确认。
每次 UNKNOWN 立即停止，不重试创建、不延时、不追加 C/D、不删栅栏或重置额度。

## 7. 阶段一回退边界

只在确认本轮从未创建 guest、无本轮活动目标后，允许停止本轮新 M3 服务；
保留新私有目录和材料供审计，不批量删除，M0/M2 服务始终不动。
若出现未知或本轮标记目标，保持监督、停止客户端并报告，不擅自清空平台。
既有服务与配置本轮不改，无需“恢复”旧生产环境。
