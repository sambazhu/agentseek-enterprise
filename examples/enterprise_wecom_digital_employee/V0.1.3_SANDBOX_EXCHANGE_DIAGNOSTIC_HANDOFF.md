## 核对诊断行为

1. BusinessHttpClient 每次 exchange 生成独立 exchange_id，关联原 attempt 摘要、operation、
   PID 与原生线程 ID。每次调用的状态独立，不在共享 client 上存储可变阶段。
2. 使用同步 HTTPX trace 回调记录 tcp、tls、send_headers、send_body、response_headers、
   response_body 的 started/complete/failed。额外阶段为 prepare/client/pool、响应校验、decode、complete。
   trace 的 info 完全忽略，不输出 headers、SSL/socket 对象、异常文本或响应正文。
3. business_exchange 日志仅含固定标量字段：exchange_id、attempt、operation、stage、event、
   status、error、cause_error、elapsed_ms、http_status、pid、thread_id。
   error/cause_error 使用固定异常类型名白名单，未知类型输出 other。
   不输出 URL、凭据、文件路径、用户指令、CSV 或 traceback；不启 httpx/httpcore DEBUG。
4. 最终状态 succeeded 仅表示传输返回了可解码字典，不代表 BusinessOutcome 成功或已回写。
   ConnectError/ConnectTimeout/PoolTimeout 仍沿原 not_sent 规则；其他异常仍 unknown 并原样传播。
   stage=tcp,event=complete 后 unknown 只表示最后观察到 TCP 完成，不能推断服务端收到请求。
5. 网关额外记录 resolve/execute_thread/workspace_thread/result_thread/exchange_or_mirror 的
   固定错误类型。CancelledError 记录后继续传播，不吞掉、不改写为失败终态。
   工具取消不证明同步线程停止；后台交换可能仍在进行，禁止自动重试或释放额度。
6. HTTPX trace 依据本地实际安装的 httpx 0.28.1/httpcore 1.0.9 接口核对。
   连接 TCP 完成与 start_tls 事件之间还有 TLS 参数设置；没有异常分类就不能把该区间归因为取消。
   诊断事件只是观察，不用于扩大“可安全重试”的异常集合。

## Linux 回传后的下一步

判定上限 EXCHANGE_DIAGNOSTIC_OFFLINE_PASS，不记 W6_ROOT_CAUSE_FIXED 或 BUSINESS_E2E_PASS。
若 Linux 图测试失败，保留白名单日志及失败用例，交 Codex 定位，不开始 W7。

若 Linux 图测试通过而 W6 自然故障未复现，.171 提交受控进程内只读诊断方案供用户批准：
固定本候选加载路径，在实际网关进程只走 get_sandbox_task_result 的恢复查询，不允许 run/execute，
保留 W6 意图；按 exchange_id/attempt/PID/thread_id 对齐阶段日志与已批准范围内的网络证据。
明确恢复查询可能按节点权威结果更新镜像，不能宣称完全无写入；not_found 仍不得关闭意图。
该方案及网关切换须另批，本工单不授权实施。不能用独立 shell 成功替代网关进程内成功。

先取得失败阶段和异常类别，再决定是否修改传输实现；不猜测性加超时、不加自动重试、
不换 request 绕过 W6 未决记录。受控诊断后按原标准生产启动方案恢复代码路径，账本保留。
创建权限另批；后续业务验收仍须真实模型→guest CSV→终止/closeout→用户工作区自动回写，
逐项核对，不把本轮合成 HTTPS 成功拼接成现场全链 PASS。
