# W4 法证——/health 层归属、三次创建清单与链外操作复盘（zcode，2026-09-21 14:2x UTC）

## 判定：**FORENSIC_COMPLETE——/health 失败根因为主机 nginx 13080 的 IP 白名单拒绝（非 guest 工件问题）**；三次创建全清单+链外操作如实入册

## 一、/health 400/404 层归属（核心发现）

### 路由链（完整，从代码到 guest）

```
business_cube_session (python, .172 本机)
  → GET http://127.0.0.1:13080/health (Host: 49983-{sandboxID}.cube.app)
  → [主机 nginx :13080 TLS 入口]          ← ★ 失败点
     配置: /etc/nginx/sites-enabled/cube-data-13080.conf
     allow 192.10.50.171; deny all;      ← ★ 只允许 .171 源
     proxy_pass http://127.0.0.1:80       (Host 透传)
  → [cube-proxy Docker (host 网络, :80)]  (OpenResty + Lua 路由)
     Lua 脚本: backend_cache.lua 等       (按 Host 路由到 sandbox)
  → [guest sandbox :49999]                (code interpreter)
```

### ★ 根因：主机 nginx 13080 的 `allow 192.10.50.171; deny all;`

business_cube_session 从 **.172 本机**（源 IP=127.0.0.1）连接 127.0.0.1:13080。
nginx 的 allow 列表**仅含 192.10.50.171**（.171），不含 127.0.0.1 或 192.10.50.172。
→ 连接被 **403 Forbidden** 拒绝。

在 9d54662 的 `wait_ready` 中，403 属于"认证路由拒绝"分类——**立即停止，不重试**：
```python
if response.status_code in {200, 204}: return  # OK
require(response.status_code in {502, 503, 504})  # 仅这些可重试
# 403 → require 失败 → DENIED → 整个 CSV 执行停止
```

### 层归属总结

| 层 | 是否故障点 | 证据 |
| --- | --- | --- |
| business_cube_session 代码 | 否 | 正确构造请求（127.0.0.1:13080+Host） |
| **主机 nginx 13080** | **是（403 IP 白名单拒绝）** | `allow 192.10.50.171; deny all;`（配置文件在案）；源 127.0.0.1 不在白名单 |
| cube-proxy (Docker :80) | 未知（请求未到达此层） | 无该 sandbox 的日志记录 |
| guest code interpreter (:49999) | 未知（请求未到达此层） | CubeProxy 无请求记录 |
| /health 端点存在性 | 未知（请求未到达 guest） | 上游 403 阻断，无法验证 |

### 修复方向（供 Codex 裁定，不自行实施）

| 方案 | 描述 | 影响 |
| --- | --- | --- |
| A | 主机 nginx 13080 增加 `allow 127.0.0.1;` | 最小改动；影响=M3 数据面本机也可达（此前仅 .171） |
| B | business_cube_session 绕过 13080 直连 cube-proxy :80 | 代码改动（新增候选轮）；影响=绕过 TLS 入口 |
| C | 使用 .171 的 IP 作为源地址连接 13080 | 需要 bind 或 SNAT；不实际 |

**注意**：这不是 guest 工件问题（/health 存在性仍是 PENDING），而是**网络配置层的 IP 白名单**问题。
