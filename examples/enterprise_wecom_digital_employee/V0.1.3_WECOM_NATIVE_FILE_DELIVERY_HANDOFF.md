# 复验企业微信原生工作区文件投递

本轮只交付网关代码与合成离线复验。不发送真实消息，不创建 guest，
不切换服务，不改 .60、HTTPS 下载键、broker、监督、pins 或历史状态。
基线为调查归档 `d558506`。业务 execution wheel 源码未改；
不需要重新制作业务 wheel，不要求 .172 安装或复跑节点创建闭包。

## 先确认首版边界

1. 仅用户明确请求时投递。任务完成不会自动发文件。
2. 从当前认证 tenant/user/session 对应的工作区 outbound 记录选文件，
   不查询最新 succeeded attempt，不依赖 broker、grants 或沙箱 spec。
3. 当前仅私聊、自建应用单员工目标。不支持群发、指定其他收件人或批量投递。
4. 模型只能提出 `file_ref`。收件人、原始用户文本、消息 ID、应用身份来自入站通道。
5. 工作区正常过期规则继续生效。既有产物过期则拒绝，不续期、不重新生成、不触发沙箱。
6. 正式 ReportArtifact 工作流不新增原生文件交付；本工具仅装配在普通助手分支。

## 复验工具与授权接线

1. 检查 `list_workspace_delivery_files` 只列当前 scope 的未过期 outbound 文件。
   返回不含本机路径、正文或收件人。`file_ref` 钉住记录位置与完整内容摘要，
   不使用可能跨日期重复的短 file_id 作为唯一投递标识。
2. 检查 `deliver_workspace_file` 的模型参数只有 `file_ref`，没有 recipient、
   confirmed、resend、nonce、request_id 或凭据参数。
3. 验证原始入站消息的整句解析，以下为产品输入示例，不是本轮执行指令：

   - 首次：`把 summary.csv 发给我` 或 `发送工作区文件 <file_ref>`。
   - 明确重发：`把 summary.csv 再发给我` 或 `重发工作区文件 <file_ref>`。
   - 可加前缀“请”；“确认”、引用文本、自动发送要求不授权。
   - 同名文件不唯一时，先列出文件让用户选择，再由用户发送含精确 file_ref 的新消息。
   - 首版为确定性短句合同，不声称理解所有自然语言发送意图。
4. 核对能力句柄从通道发出，经 WeCom plugin 的私有 state 字段传入 ToolRuntime。
   句柄不进入模型消息，绑定 scope，进程内有效 600 秒，重启失效；每轮无句柄时清空旧值。
   此 600 秒不是下载链接期限，也不改变文件保留期限或企微素材有效期。
5. 核对正式数字员工 profile 的 tool_grants：若启用 profile 限权，必须同时列入
   `list_workspace_delivery_files` 和 `deliver_workspace_file`；不自动修改现场 profile。
   沙箱只读诊断 spec 仍仅保留原有结果查询工具，不挂本工具。

## 复验持久化与异常边界

1. 私有投递目录须预先存在、规范绝对路径、当前进程属主、0700。
   `native-file-deliveries.sqlite` 以 0600 建立，先原子占位、再读回文件、上传和发送。
2. 投递键绑定 scope、应用/收件人散列和 file_ref。首次发送的重复请求共用键；
   明确重发才加入真实入站 message_id。模型重复调用不能铸新键。
3. 初次读取校验 scope、方向、有效期、完整 SHA256、字节数及普通文件；拒绝符号链接。
   单文件受代码的 6 字节至 20 MiB 限制；工作区写入端自身限制仍独立生效。
4. 同一键并发只有一个上传/发送调用方。既有 inflight 一律返回 uncertain，
   不接管租约、不自动重做。崩溃或取消后宁可保留不确定状态，不重发。
5. 上传失败不调用发送，不自动重新执行工具。既有 transport 对明确 token 失效响应
   的刷新逻辑保持不变；HTTP 超时不会被本工具重试。
6. 调用现有 `send_application_message` 时将 manual_recovery_only 存入加密 outbox。
   异常进入 blocked；恢复循环对 pending/failed/sending/sent 均禁止再次发送。
   其他既有应用文字消息的恢复语义不变。
7. 回执分层：api_accepted 仅表示接口接受；uncertain 的 api_accepted 为 null。
   user_receipt_confirmed 始终 false，首版没有伪造或自动推定用户实收的入口。
   实机用户收到、打开、核摘要的证据另行记录。
8. 不存文件正文、media_id、收件人或 API 凭据到新增投递账本；
   现有 outbox 的素材标识和目标继续密封保存。模型结果不包含异常原文。
9. 不宣称分布式 exactly-once。人工确认重发可能产生第二份文件，这是新的用户请求，
   不是自动恢复；不确定结果需先告知用户，不能替用户决定再发。

## 另行申请现场采用

1. .171 先只读复核现役应用、测试用户可见范围、工作区产物未过期及归属/摘要。
   W17 原件如已过期，不擅改 expires_at，不以创建沙箱作为本轮默认补救。
2. 申请新的私有投递目录与两个配置项：
   `AGENTSEEK_WECOM_NATIVE_FILE_DELIVERY_ENABLED=true`，
   `AGENTSEEK_WECOM_NATIVE_FILE_DELIVERY_DIRECTORY=<已批准的0700绝对目录>`。
   支持相应 BUB_ 前缀别名，沿既有优先级；实际进程加载值需核验。
   还需既有 APP_TRANSPORT_ENABLED、durable sqlite outbox、Files enabled。
3. 网关采用本候选的 wecom/files/example 源码及既有依赖；
   必须独立核验导入来源、WeComPlugin.load_state 接线与正常普通助手工具集。
   不切 sandbox_spec、不加载创建授权、不启 broker，不部署 .172。
4. 另批一次真实文件投递后，用户在原私聊明确请求现有文件。
   先验“接口接受→用户实收→打开→本地摘要一致”；重发验收需要另一个明确用户请求。
5. 恢复：关闭新增开关，按批准操作单恢复原网关启动配置；
   两份投递账本、outbox、产物、旧实例配置保留，不自动重试或清理。
   回退旧代码前，须只读确认没有带 manual_recovery_only 的可恢复 outbox 行；
   若存在 pending/failed/sending/sent 行，停止回退并由新代码收敛为 blocked，
   或经单独审阅处置。禁止让不认识此标志的旧恢复循环重发。
