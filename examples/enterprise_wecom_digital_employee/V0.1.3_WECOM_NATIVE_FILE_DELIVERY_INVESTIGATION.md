## 四、官方接口核对（附来源）

| 事实 | 来源 |
| --- | --- |
| `POST /cgi-bin/media/upload`，type 含**普通文件(file)**；**所有文件 size 必须大于 5 字节**；图片 10MB、语音 2MB、视频 10MB、**普通文件 20MB**；**"素材上传得到media_id，该media_id仅三天内有效"**；"media_id在同一企业内应用之间可以共享"；filename 控制发消息时展示的文件名 | 官方文档《上传临时素材》developer.work.weixin.qq.com/document/path/90253（最后更新 2024/07/22，已抓取原文引用） |
| `message/send` msgtype=file 携带 media_id；接收人须在应用可见范围；media_id 无效/过期返回 40007 等 | 官方文档《发送应用消息》developer.work.weixin.qq.com/document/path/90236 +《全局错误码》附录（搜索确认，未逐字抓取） |
| 调用频率限制（官方 90312 逐字，最后更新 2023/08/28） | 基础频率：每企业调用单个 cgi/api ≤1万次/分、15万次/小时（每IP ≤2万次/分、60万次/小时）；**发送应用消息**：每应用 ≤账号上限数×200人次/天；**"每应用对同一个成员不可超过 30次/分钟，1000次/小时，超过部分会被丢弃不下发"**；"发消息频率不计入基础频率"；官方声明阈值可能按运营情况调整 |

**两种期限的独立语义（明确区分）**：**素材有效期=3 天**（企微侧 media_id 生命期，过期须重传素材）≠ **工作区文件保留=7 天**（本地 FileRecord `expires_at`+retention）。两者独立计时：文件未过期但 media_id 过 3 天 → 重传素材即可再发；文件过期 → 该记录不可再按原记录交付（见 §三备用源）。

## 五、最小接线方案（待批开发，范围刻意收窄）

**新工具 `deliver_workspace_file`**（挂入现有 sandbox tools 集，spec 变更点仅 `sandbox_remote.py`+`sandbox_spec.py`）：

1. **触发与身份**：模型在会话内调用；`runtime_scope(runtime)` 取可信身份（收件人=会话地址派生 userid，工具无收件人参数）；
2. **读取与核验**：`runner.store.latest_request(scoped_owner)` → 最新 **succeeded** attempt → `artifact_ref` → `store.read` 字节；核 sha256+大小（≤20MB、>5B）+scope 匹配（tenant+employee 与当前身份一致，不一致即拒绝）；文件记录未过期；
3. **上传与发送**：`upload_media(media_type="file", filename="summary.csv")` → `send_application_message(target=WeComAppTarget(users=(派生userid,)), message_type="file", idempotency_key=f"artifact:{sha256前16}:{attempt前16}")`；
4. **结果记录**：返回 outbox 回执状态；**发送失败只处理投递**（blocked/failed 如实回报，含 partial_delivery/visibility_denied），**绝不重跑沙箱、不创建、不换 request**；
5. **去重**：同一产物+attempt 的 idempotency_key 相同 → outbox claim 判重返回 "skipped"（已投递）；用户再次明确索取=新 key 新投递（重发语义显式化）；
6. **脱敏日志**：沿现有 `safe_error`/企业事件模式——不落文件内容、不落 media_id 明文全文、不落完整 userid/token。

**依赖**：零 .60 依赖、零 broker 依赖（投递链不触执行面；run_sandbox_task 在无 grants 下本就不可执行）、监督零触碰。**broker 保持 inactive 完全兼容。**
**开发量评估**：一个工具函数+spec 接线+合成测试（不实发）；底座零改动。
**验收（另批一次真实投递）**：用户实收并打开文件、核对摘要 28B=`376b7875…85a32`；**接口成功≠用户已收到已打开**——以用户确认为准。

## 八、补齐事实（2026-09-28 二轮只读）

1. **可见范围运营证据（现役 store 只读查询）**：durable outbox 存在 `wecom_app_text` **status=delivered ×3**，最近一条 **2026-09-28T05:05:53Z（今日）**——自建应用今日对至少一名目标用户成功送达应用消息（可见范围校验通过）。目标名单在密封信封内（设计使然，不绕读）；"测试用户本人在范围"的逐人确认仍待管理员后台或只读 agent/get，不以上述旁证替代。
2. **身份解析接线事实**：现役 `.env` `AGENTSEEK_WECOM_USERID_RESOLVE_MODE=openuserid_to_userid` → `WeComChannel` 自动构建 `WeComOpenUseridResolver`（`make_userid_resolver`，corp_id+app_secret 就绪即生效，带缓存 TTL）——**机器人会话 open_userid→明文 userid 解析已接线运行**；自建应用会话 userid 直取（无需解析）。
3. **频率限制官方原文（[90312](https://developer.work.weixin.qq.com/document/path/90312)，最后更新 2023/08/28，已抓全文逐字）**：
   - 基础频率：每企业调用单个 cgi/api ≤1万次/分、15万次/小时；每IP ≤2万次/分、60万次/小时（media/upload 属基础频率口径）；
   - **发送应用消息频率**：每应用 ≤账号上限数×200人次/天；**"每应用对同一个成员不可超过 30次/分钟，1000次/小时，超过部分会被丢弃不下发"**；发消息频率不计入基础频率；
   - 官方声明"企业微信后台可能会根据运营情况调整此阈值"。
   - **对本方案的直接影响**：超频消息被**静默丢弃（接口不报错）**——"接口接受"与"用户实收"必须分列记录的硬依据。

## 九、开发合同补充（用户 2026-09-28 指令，作为后续候选的硬性验收条款）

1. **精确选择当前 scope 的目标产物，不默认取最新**：工具按当前 runtime scope（tenant+employee）匹配产物；匹配多于一件时枚举给用户选，不隐式取 latest；
2. **上传前判重**：同产物（sha256）+同 scope 已有 delivered/进行中的投递记录时不再上传素材（media_id 3 天内可复用，但复用前校验记录在案）；
3. **相同请求重复调用返回既有状态**（幂等：同 idempotency_key → 返回既有 outbox 状态，不新建）；
4. **只有用户明确要求重发才创建新投递请求**（新 key）；模型不得自作重发；
5. **发送结果不确定不自动重发**（超时/网络类不确定态如实标 uncertain，等待人工/用户指令）；
6. **接口接受与用户实收分列**：结果字段分离 `api_accepted`（errcode=0 即接受）与 `user_receipt_confirmed`（仅用户实收+打开确认后置位，另批真实投递验收时人工确认）。

**合成离线测试矩阵（候选先过，全部合成数据、不实发、不创建沙箱）**：
① 越权（scope 不匹配→拒绝，不泄露存在性）；② 文件过期（expires_at 已过→拒绝，含"仅文件过期而素材未过期"组合）；③ 摘要不符（记录 sha≠文件字节 sha→拒绝，不上传）；④ 重复调用（同 key 二次调用→返回既有状态、零新上传零新发送）；⑤ 并发（同 key 并发→恰一次投递，其余得"skipped"）；⑥ 上传失败（media/upload 异常→failed 记录、不发送、不自动重试）；⑦ 发送超时（不确定态→uncertain 标记、不自动重发）；⑧ 明确重发（用户显式重发指令→新 key 新投递，旧记录保留）。

真实投递另批；不发送探针、不创建沙箱；HTTPS 方案继续暂缓保留。
